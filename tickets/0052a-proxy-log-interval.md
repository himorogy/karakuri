# proxy-log の書き出しを、1時間ごとに起きて前回の成功から N 時間経っていれば書き出す形に変える

## 内容

egress-guard と egress-proxy の配布・記録・経路を見直す束で、3つの流れからなる。

- egress-guard の配布をイメージだけにする（0046 / 0047）。各イメージが npm を経由せず、このリポジトリのソースから焼く
- egress-proxy のアクセスログを、LLM を通らない経路（パッケージのインストールスクリプト、git hooks、エディタ拡張、常駐プロセスなど）の通信を後から照会できる記録にする（0052 / 0052a / 0049）。拒否された宛先の判定はこのリポジトリの外の監査側が持ち、ここでは保管庫とその契約までを提供する
- dev から DNS で外へデータを持ち出す経路を、dev を internal ネットワークだけに載せて塞ぐ（0048 / 0050 / 0051）。issue `#83` が起点で、`#83` は 0051 の close で閉じる

順序の依存は次のとおり。
0052a は 0052 の追補で、0052 の着地だけを待つ。
0049 と 0048 は 0046 を待つ（0049 は 0046 と同じファイルに触るため、0048 は npm の新版を出さないので 0046 が無いと改修がイメージへ届かないため）。
0050 は 0048 入りの devcontainer-base のタグを待つ。
0051 は 0050 の着地と、0048 入りの devcontainer-base・0049 入りの egress-proxy のタグを待ち、karakuri の pin をまとめて上げる。

### 解きたい問題

0052 の LaunchAgent は `StartCalendarInterval` で毎日 3:17 に1回だけ起きる。
利用者の PC はその時刻に電源が切れているかスリープしていることが多い。
電源が切れていた回は launchd が後から取り返さないので、PC を夜に落とす使い方では書き出しが一度も走らない日が続く。
書き出しが走らない間はログがボリュームにしか無く、`down -v` などで失われうる範囲が日単位で伸びる。

### 作るもの

plist の契機を `StartCalendarInterval` から `StartInterval` 3600（1時間ごと）に替え、ジョブ本体が起きるたびに「前回の書き出し成功から N 時間経っているか」を判定して、経っていなければ何もせずに終わる形にする。
N は利用者が install で選ぶ。

```
proxy-log-setup.sh install [--interval <時間>]
```

- `<時間>` は 1 以上 168 以下の整数。既定は 24（0052 の日次と同じ間隔）
- 範囲外・整数でない値・未知の引数は、install が非ゼロで終わり何も配置しない（docker が見つからないときと同じ扱い）
- 引数なしの install は既定の 24 にする。前回の install で選んだ値は引き継がない。アップグレードで install を打ち直す利用者は、値を選び直す必要があることを README に書く
- N をどこに持つか（plist の引数、`docker-bin` と同じ置き方のファイルなど）は実装の判断

`uninstall` と `run` は引数を取らないまま変えない。

### 1回の起動で起きること

起動の経路は2つある。
launchd からの起動（以下「スケジュール実行」）と、`proxy-log-setup.sh run` による手動の実行である。
ジョブ本体がどちらから起動されたかを区別する手段（plist の引数など）は実装の判断。

```
if スケジュール実行:
    if 状態ファイルがあり、result が ok か partial で、run_start から N 時間経っていない:
        何もせず 0 で終わる（状態ファイルに触れない。標準エラーにも出さない）
    # 状態ファイルが無い・読めない・result が failed・run_start が今より未来 のときは書き出しへ進む
if Docker に繋がらない:
    状態ファイルに触れずに終わる
    スケジュール実行なら 0、手動の run なら非ゼロで終わる。どちらも標準エラーに1行出す
0052 の書き出し（ボリュームごとの書き出し・保持期間の掃除・状態ファイルの書き込み）をそのまま行う
```

「前回の書き出し成功」は、状態ファイルの `result` が `ok` か `partial` の実行を指す。
`partial` を成功に数えるのは、`no-container`（`docker compose down` のあとのボリューム）のように何時間経っても解消しない状態があり、それを失敗に数えると1時間ごとに書き出しが走って保管庫に小さなファイルが積もるからである。
`partial` で書き出せなかったボリュームの行は、ボリュームに残ったまま次の書き出しで回収される（0052 の退避ファイルの扱いによる）。
判定に `run_start` を使うのは、状態ファイルは書き出しを行った実行だけが書くので、最後に書かれた `run_start` がそのまま前回の書き出しの時刻になるからである。
`failed` は、Docker には繋がったがボリュームの列挙に失敗した場合など、Docker 不在以外の失敗に限られるようになる。

run_start が今より未来のとき（時計の巻き戻り）に書き出しへ進むのは、判定が永久に「経っていない」を返し続けて書き出しが止まる経路を作らないためである。

手動の `run` は間隔を見ずに書き出す。
書き出した結果は状態ファイルに残り、次のスケジュール実行はそこから N 時間を数える。

`RunAtLoad` は使わない。ログイン直後は Docker Desktop が立ち上がっていないことが多く、走っても Docker 不在で終わるだけだからである。
Docker の起動を契機にする案も採らない。Docker Desktop に起動を外へ知らせる公式の仕組みが無く、socket を `WatchPaths` で見る方法は socket のパスと作り直しの挙動に依存して脆い。

launchd の `StartInterval` について、次は**未確認**である（実装者が `man launchd.plist` で確かめ、確かめられないものは検収に回す）。

- スリープ中に過ぎた起動は、復帰時に1回にまとめて走る
- 電源が切れていた間の起動は取り返されない（ログイン後、次の間隔で起きる）
- `RunAtLoad` を書かなければ、`bootstrap` の直後には走らない

### 状態ファイルの変更

0052 の状態ファイルに `interval_hours=<N>` の行を足す。
監査側が「ジョブが止まっていないか」を判定するとき、期待する鮮度を状態ファイルだけから読めるようにするためである。

Docker 不在の回が状態ファイルを書かなくなるので、状態ファイルの `run_start` が古いことは「ジョブが動いていない」「PC が止まっていた」「Docker が動いていなかった」のどれでもありうる。
監査側がこの3つを状態ファイルから区別できないことは受け入れる。
README の状態ファイルの説明にこの読み方を1文で書く。

### 文書

`host-tools/README.md` の proxy-log の節で、「日次で」を新しい契機（1時間ごとに起き、前回の成功から N 時間経っていれば書き出す）に直し、`install --interval` と既定値、`interval_hours` の行、`run` が間隔を見ないこと、Docker が動いていない回は状態ファイルが更新されないことを書く。
plist と本体の冒頭コメントの「日次で」も直す。

### やらないこと

- Docker の起動を契機にした書き出し、`RunAtLoad`（上記の理由）
- 電源が切れていた間の取り返し（launchd の仕様で、ジョブの側から補えない）
- 前回の install で選んだ N の引き継ぎ
- 書き出しを抑止した回の記録（何もせず終わった回はどこにも残さない）
- 状態ファイルの既存のキーの名前と値の書式の変更（足すのは `interval_hours` だけ）
- 検査の深さ: 間隔の判定は時間単位の大小だけを見る。状態ファイルが部分的に壊れている形（`result` はあるが `run_start` が無いなど）は「読めない」に含めて書き出しへ進めばよく、壊れ方ごとの分岐はテストしない。時計の巻き戻りは「未来の run_start」1点だけを見る

### 検収

ホストで、0052 の検収で使ったサンプル（label 付きのボリュームと egress-proxy、client を持つ compose と、それを流す検収スクリプト）を流用する。
検収スクリプトのうち、launchd の経路を確かめる段（0052 の検収 5）は、`launchctl kickstart` が直前の手動 `run` から N 時間以内に走ることを前提にしていないので、次のように直す。

1. 0052 の検収 2〜4 がそのまま通ること（`install` は `--interval 1` で打つ）
2. 手動の `run` の直後に `launchctl kickstart -k` し、状態ファイルの `run_start` が変わらず、保管庫のファイルも増えないこと
3. 状態ファイルの `run_start` を2時間前に書き換えてから `kickstart -k` し、書き出しが走って状態ファイルが更新されること
4. Docker Desktop を終了した状態で `run_start` を2時間前に書き換えて `kickstart -k` し、状態ファイルが書き換えた内容のまま残ること（`failed` にならないこと）
5. `launchctl print gui/<uid>/com.karakuri.proxy-log-export` で、間隔が 3600 秒の起動として登録されていること
6. スリープと復帰をまたいで、復帰後に書き出しが走ること（未確認の挙動の確認。走らなければ実装者に戻す）

## 保証

### 新たに宣言する保証

台帳 §26 の節に次の行を足す。
テスト名は実装時に決め、各行に併記する。

- スケジュール実行は、状態ファイルの最終実行が `ok` か `partial` で、その開始から install で選んだ時間が経っていなければ、何も書き出さず状態ファイルにも触れずに 0 で終わる。経っているとき、状態ファイルが無い・読めないとき、最終実行が `failed` のとき、最終実行の開始時刻が未来のときは書き出す（テスト: 新設）
- `proxy-log-setup.sh run` は、最終実行からの経過時間によらず書き出す（テスト: 新設）
- Docker に繋がらない実行は、状態ファイルに触れない。スケジュール実行なら 0 で、`run` なら非ゼロで終わる（テスト: 新設）
- `proxy-log-setup.sh install` は `--interval <時間>` で 1 以上 168 以下の整数を受け付け、省略時は 24 にする。それ以外の値や未知の引数では非ゼロで終わり、何も配置しない（テスト: 新設）
- Docker が動いている間は、PC が起きていれば、前回の書き出しの開始から選んだ時間 + 1時間以内に次の書き出しが走る — `未検証の約束 (テスト困難: launchd の起動の間隔とスリープからの復帰は macOS の実機でしか観測できない。検収 2〜6 で確かめる)`

### 維持する保証

台帳 §26 の既存の行のうち、次の3行は書き換える（理由は「内容」）。

- 先頭の行の「1回の実行ごとに …… 書き出される」を「書き出しを行う実行ごとに …… 書き出される」に直す。間隔に満たないスケジュール実行と Docker に繋がらない実行は書き出さないので、元の文のままでは偽になる。「次の実行で重複しない」「次の実行で書き出される」の「次の実行」も「次の書き出し」に直す。テスト名は変えない

- 「各実行は、最終実行の時刻と結果を状態ファイルに残す。Docker に繋がらないときも、失敗として残す」を「書き出しを行った各実行は、その時刻と結果を状態ファイルに残す」に直す。既存のテストのうち "docker unreachable: status is failed" は上の新しい行のテストに置き換わり、ほかのテスト名はこの行に残る
- 状態ファイルの形の行（「保管庫のファイル名は ……」）に、状態ファイルが `interval_hours`（install で選んだ時間）を持つことを足す。"docker unreachable: status is failed" はこの行からも外す

ほかの行（書き出した行が欠けず重複しない、保持期間、label の検証、macOS 以外での無動作、docker が見つからないときの install、install の冪等性と uninstall）は変えない。
install の冪等性の行の「2回打っても」は、同じ引数で2回打つ場合として読む。

### 廃止する保証

- 「Docker に繋がらないときも、失敗として残す」（上の書き換えで取り下げる。Docker 不在は失敗ではなく、書き出しを行わなかった回として扱う）
