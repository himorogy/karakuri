# README の機能節に型を与え、git の認証の解説を正本へ集約する

## 内容

保証台帳は「何が守られているか」を現在形の事実として持つが、「何をしたかったか」は構造上そこに
載らない。索引がテストファイル単位である以上、台帳を読んでも機能の意図は再構成できない。この
欠落は台帳の不備ではなく、置き場が無いことによる。

置き場を README とし、機能節が持つ3要素（何のために / どう動くか / 保証への参照）を規約として
`docs/conventions.md` に定める。あわせて、型が実際に持つかを確かめるために `runtime-base` の
「git の認証（github.com）」節へ適用する。

この節を最初の適用先に選んだ理由は3つある。設計判断が新しく材料が揃っていること、台帳に対応する
節が既にあること、そして進行中の 0014 / 0015 のどちらもこの節に触れないため衝突しないこと。

型を定める過程で確定した事項が3つあり、規約に書いてある。

- **「何のために」には打ち消す相手を書く。** 適用してみて分かったのは、目的だけを書いても
  「なぜホスト側の資格情報がコンテナに入るのか」が読めないことだった。打ち消し型の機能は、
  相手の挙動を前提として書かなければ目的が成立しない
- **台帳への参照はテストファイル名で書く。** 台帳の見出しは `### 10. <テスト名> — <実装>` の形で
  連番を含み、節を途中に挿すと番号がずれる。番号やアンカーで指すと参照が腐る
- **1つの機能は複数の台帳節に着地する。** 台帳の索引はテストファイル単位であり機能単位ではない。
  git の認証は helper 側（`git-credential.test.sh`）と prod の clone 側
  （`entrypoint.test.sh`）に分かれて載っている

型が README だけで閉じないことも適用して分かった。同じ解説が README・Dockerfile・3 本の
スクリプトへ散っており、README を直しても二重状態が残る。正本を「制約を書いている場所」
（打ち消しを書いている Dockerfile の ENV 直上）に定め、他は自分の1行の理由だけを持って
そこをパスで指す形へ寄せた。この切り分けも規約に書いてある。

`/etc/gitconfig` へ打ち消しを書いても効かないという実測は、台帳 §10 が「守れない側の事実」
として持ちテストが固定しているため、散文からは落とした（正本に1行だけ残し、固定先を指す）。

### やらないこと

- `docs/conventions.md` へ、今回の適用で確かめていない規約を書くこと（kuda 同梱の雛形にある
  「置き場所の原則」「回避路の封鎖」「発見しにくい事実」は、実体が伴ってから書く。空欄の
  節を作らない）
- `docs/features/` への分離。「git の認証」節は正本への集約で 138 行から 55 行になり、分離の
  必要が無くなった。他の機能節で必要になったときに判断する（後続チケット）
- `docs/prod-secret-isolation-design.md` の該当箇所の整理
- 他の機能節（secret の受け渡し、shim、prod-entrypoint、git hook）への適用
- git identity の供給経路（`copyGitConfig` の扱いと token からの導出）。台帳に新しい節を採るため、
  0014 / 0015 の着地後に別チケットとして起票する
- 台帳の変更
