# git identity の導出を鍵注入後の対話シェル起動時へ移し、実効の identity を毎回報告する

## 内容

0018 で入れた `git-identity-setup` が、実際には一度も成功していない。0018 の検収で発覚した
実行点の誤りを直す。

### 何が起きているか

`git-identity-setup` は雛形の `postCreateCommand` から呼ばれる。一方 `/run/secrets/GH_TOKEN` を
作るのはホスト側の `dev-inject.sh` で、起動済みのコンテナへ `docker exec` する経路である。
**注入は必ず `postCreateCommand` より後になる。**

- `gh` の shim は `/run/secrets/GH_TOKEN` が無ければ素通しするので、`gh api user` は未認証で走る
- 未認証の `gh api user` は非ゼロで終わる（実機で `rc=4`。`gh auth login` を促す案内が stderr に出る）
- `git-identity-setup` はこれを取得失敗として扱い、`アカウント情報を取得できないため identity は
  変更しない` の1行を出して 0 で終わる

`postCreateCommand` はコンテナ作成時の1回きりで、再実行される経路が無い。したがって identity は
**そのコンテナの生涯にわたって未設定のまま**になる。実機の dev container で `~/.gitconfig` が
存在しないことを確認済みで、コミットできているリポジトリは利用者が手で local に
`user.name` / `user.email` を入れたものだった（0018 が避けようとした個人アドレスがそこに入っている）。

`postStartCommand` へ移しても直らない。firewall の適用も注入より前だからである。**鍵注入の後に
走るライフサイクルコマンドは存在しない。**

### なぜ気づけなかったか

対話シェルの起動時に出る報告は `karakuri-context`（注入済みの鍵名）と `git-auth-check`（実効
helper とイメージ固定の生死）の2種類で、どちらも push 側の経路しか映さない。commit 者情報は
報告の対象外なので、identity の欠落は「全部緑」の表示の裏に隠れる。

台帳の 22 番も緑のまま通る。22 番の否定対照は「取得に失敗しても identity を触らず 0 で終わる」で、
今の壊れ方はまさにその通りの挙動である。22 番は導出のロジックだけを固定していて、**それが呼ばれる
時刻にトークンがあるか**は誰も見ていない。

### 直し方

**(1) 実行点を鍵注入の後へ移す。** devcontainer-base が `/etc/bash.bashrc` と `/etc/zsh/zshrc` へ
足す行から `git-identity-setup` を呼ぶ。`karakuri-context` の source 行より後に置く（bash 側の
`karakuri-context` の行は runtime-base の層で既に足されているので、devcontainer-base の追記は
自然に後になる。zsh 側は同じ `printf` ブロック内で後ろに並べる）。

対話シェルの起動は鍵注入の後にしか起きないので、これが「トークンがある状態で走る」唯一の
確実な時点になる。

**(2) 導出の要否は「注入されているトークン」を基準に決める。** `~/.gitconfig` はコンテナの
ファイルシステムにあり、`/run/secrets`（tmpfs）と違って停止・再起動で消えない。そのため
「identity が未設定なら導出する」という条件にすると、**トークンを差し替えたときに前の
アカウントの identity が残り続ける**——push するアカウントと commit する identity をずらさない
という 0018 の目的を、別の入口から破ることになる。

そこで、導出済みであることを示すマーカーを `/run` （tmpfs。compose が `uid=1000` 所有で
マウントしており、実測でも `node` が書ける）へ置き、マーカーが無ければ導出する。tmpfs なので
コンテナの停止・再起動で消え、起動のたびに1回だけ導出が走る。対話シェルの起動ごとに
ネットワークを叩くことはない。

**マーカーには、そのとき使ったトークンの版を書く。** 版が違えば、マーカーがあっても導出し直す。
再起動時の再導出は tmpfs が消えることで既に得られているので、版を書くことが効くのは
**コンテナを起動したまま別のトークンで `dev-inject` を打ち直した場合だけ**である。マーカーを
1つ置くこと自体は「導出済みか」を覚えるために要るので、そこへ何も書かないか版を書くかの差
でしかなく、実装のコストは変わらない。上の追随を成り立たせるほうを採る。

版はトークンの値そのものではなく、`/run/secrets/GH_TOKEN` というファイルの版を示す情報
（inode と更新時刻）で足りる。`secrets-ingest.sh` は注入のたびにこのファイルを書き直すので、
差し替えは版の変化として現れる。同じトークンを入れ直したときに1回余計に取得しにいくが、
実害は無い。

22 番が固定している「食い違えば警告して上書きする」振る舞いはそのまま生きる——差し替えは
まさにその経路を通る。引数なしの直接起動は、マーカーを見ずに無条件で取得して上書きする。

**既知の限界: 既に開いているシェルは自分では追随しない。** rc は起動時にしか読まれないので、
`dev-inject` を打ち直しても、その時点で開いているターミナルが導出をやり直すことはない。
ただし影響範囲は「そのセッションの残り全部」ではない——git は commit のたびに `~/.gitconfig` を
読むので、**どこか1つでも新しいターミナルを開けば、既に開いていたシェルの以降の commit も
新しい identity になる**。ずれが残るのは「打ち直してから次にターミナルを開くまで」の間だけで、
その間も報告の1行は各シェルが起動時に見た値を映すので、食い違いは目に見える。これを
埋めるには常駐監視か commit 前フックが要り、得られるものに対して重いので受け入れる。

そもそもこのずれが起きるのは、コンテナを止めずに**別アカウントの**トークンへ入れ替えたときに
限られる。同じアカウントのトークンを更新した場合は導出結果が同じなので何も変わらない。
別アカウントへの入れ替えは実務上まれで、実質的に問題にならないと見込む。

**呼ぶのは rc（対話シェル）であって profile（ログインシェル）ではない。** `zprofile` /
`profile.d` はログインシェルでしか読まれず、雛形が設定する統合ターミナルの zsh プロファイルは
`{"path": "zsh"}` で引数を渡さない（＝非ログイン）ため、そこへ置くと VS Code のターミナルでは
一度も走らない。`docker exec -it <c> bash` も同じく非ログインで取りこぼす。`karakuri-context` を
`profile.d` ではなく `/etc/bash.bashrc` から読ませているのと同じ理由で、その判断は
`bin/karakuri-context` の冒頭コメントに既にある。

**(3) 取得を有界時間で打ち切る。** 対話シェルの起動から呼ぶ以上、応答しない宛先が
プロンプトを止め続ける形は許さない。egress-guard は許可外の宛先を DROP するので、
`firewall.json` に `api.github.com` を含まないプロジェクトでは接続がぶら下がる
（karakuri 自身の既定の許可リストには含まれるが、利用側が絞れば外れうる）。打ち切ったときは
取得失敗と同じ扱いにする——identity には触らず、理由を1行出して 0 で終わる。

この打ち切りは**台帳には載せない**（裁可で「保証に積むには粒度が細かい」と判断された）。
実装の要求としては残し、テストを書いてよい。台帳に載っていない振る舞いにテストがあるのは
境界宣言の想定どおりで、約束にはならない。

**「author 名とメールアドレスは両方設定されるか、どちらも変わらないか」も同じ扱いにする。**
実装レビューの段階で、これを約束として書くと「利用者が手で片方だけ入れた状態で取得に失敗した
場合」を第1文が誤って含んでしまうことが分かり、裁可で台帳から落とした。粒度としても上の
打ち切りと同型である。仕様としては正しいので実装とテストは残す。

**(4) 実効の identity を毎回1行で報告する。** 報告の出口は `git-identity-setup` 自身に持たせ、
引数の有無にかかわらず最後に1行出す。設定されていれば `user.name` と `user.email` の値そのものを
出す。導出されるアドレスは GitHub の転送用アドレスであり、表示名と併せて公開情報なので値を
出してよい。未設定なら未設定と分かる1行を出す。これが無いと、(1)〜(3) が将来また別の理由で
失敗したとき、今回と同じく沈黙する。

**報告を `karakuri-context` へ足さない。** `karakuri-context` は runtime-base にあり prod にも
載るが、prod は detached HEAD で commit しないので identity は prod に無い能力である。そこへ
「未設定」の行を常設すると、prod では直しようのない行を毎回出すことになる。0018 が
`git-identity-setup` を devcontainer-base へ置いたのと同じ配置規約（能力は最小に、制約は最大に）
に従う。

**(5) 雛形の `postCreateCommand` から `git-identity-setup` の呼び出しを落とす。**
`/personal/setup.sh` がトークンを入れる想定は無いので、`postCreateCommand` の時点で成功する
経路は存在しない。残すと「1回は必ず失敗して警告を出す」だけの呼び出しになり、報告に嘘の
1行が混ざる。あわせて雛形のコメントと README の「ネットワークが要るので `postCreateCommand`
に置く」という説明を、新しい実行点の理由（鍵注入の後でなければ成功しない。firewall の適用後に
なるので `api.github.com` が許可されている必要がある）に書き換える。

**(6) `git-identity-setup` の利用者向けメッセージを英語へ寄せる。** (4) で報告の1行を新設したところ、
このスクリプトの出力が日本語（既存の警告）と英語（新設の報告）で混ざった。検収の過程で気づき、
人間の判断で英語側へ統一すると決めた。出荷物の利用者向けメッセージの言語について規約は定めが
無く、これが最初の決定になる。変えるのは実行時に出力される文字列だけで、コード内のコメントと
テスト名は日本語のまま残す——テスト名は台帳 22 番の索引が参照しているため、変えると索引がずれる。
台帳 22 番はメッセージの本文を引用していないので、この変更で動く保証の行は無い。

runtime-base 側の出荷物（`git-auth-check` 1 行、`karakuri-context` 2 行、
`prod-entrypoint.sh` 19 行）も同じ扱いにすべきだが、別イメージでリリースの順序も別なので
このチケットではやらない。backlog へ積む。

### やらないこと

- `karakuri-context` の表示内容は変えない。identity の行は devcontainer-base 側から出す
- runtime-base 側の出荷物のメッセージは英語化しない。(6) は devcontainer-base の
  `git-identity-setup` に閉じる
- 導出の中身（表示名→ログイン名の順、`<id>+<login>@users.noreply.github.com` の組み立て、
  登録メールアドレスを使わないこと、食い違ったときの警告つき上書き）は変えない。今回直すのは
  実行点と報告だけである
- 利用者が手で設定した identity を尊重する仕組みは入れない。トークンのアカウントが勝ち、
  食い違えば警告して上書きする——0018 が決めたこの優先順位は変えない
- イメージのタグ発行はこのチケットの範囲外。`bin/` と `Dockerfile` に触るので CI の
  devcontainer-base ビルドは走るが、`devcontainer-base-vX.Y.Z` タグを切るのはマージ後の別手順
- 0018 のチケット本文（`tickets/done/0018-git-identity-derive.md`）は履歴層なので直さない

## 保証

### 新たに宣言する保証

台帳 22 番（`images/devcontainer-base/tests/git-identity.test.sh`）へ追記する。イメージ内の
`/etc/bash.bashrc` / `/etc/zsh/zshrc` への配線と、雛形 `devcontainer.json` の内容は、境界宣言の
公開面 E（devcontainer-base イメージと `examples/` の雛形）に属し、台帳の規約どおり候補層
（`docs/guarantee-candidates/0018a-git-identity-after-inject.md`）へ置く。

- 注入されているトークンが差し替わると、identity はそのトークンのアカウントへ追随する。
  差し替え前のアカウントの author 名・author メールアドレスが残り続けることはない
  （テスト: "トークンが差し替わると identity が追随する" /
  "否定対照: 同じトークンのままなら identity は変わらない"）
- 実行のたびに、実効の author 名と author メールアドレスが1行で報告される。設定されていれば
  その値そのものが行に入り、未設定ならそれと分かる行が出る。呼び出し方や導出の成否によって
  黙ることはない
  （テスト: "設定済みの値がそのまま報告に出る" / "未設定のときは未設定と分かる1行が出る" /
  "否定対照: 導出が失敗しても報告は黙らない" / "取得を省略する起動でも報告は出る"）
- 導出も報告も、失敗を呼び出し元へ伝播させない。常に 0 で終わり、読み込んだシェルの起動を
  止めない（テスト: "導出が失敗しても 0 で終わる"）

### 維持する保証

- 台帳 22 番の既存の各行（表示名が未設定ならログイン名へ落ちること、`\` を含む表示名が壊れないこと、
  登録メールアドレスが author に現れないこと、既存 identity と食い違うときに両方の値を示して
  警告したうえで上書きすること、取得に失敗しても identity を触らず 0 で終わること、取得部を
  差し替えた状態で導出結果が固定されること）。実行点と呼び出し方を足すだけで、導出そのものは
  変えない
- 台帳 9 番（`karakuri-context`）の各行。identity の報告を runtime-base 側へ足さないので、
  prod を含む `karakuri-context` の出力は 1 行も変わらない
- 台帳 11 番（出荷物の記号検査）の、受け取った側で解決できない記号を出さないという行。報告文を
  1本新設するので、この行の対象が増える

### 廃止する保証

- なし。台帳 22 番は導出の中身だけを宣言していて、それがいつ呼ばれるかを書いていない。
  実行点の記述は雛形のコメントと README にしかなく、どちらも台帳の外なので取り下げる行が無い
