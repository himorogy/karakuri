# ホスト上のコマンドへ秘密を渡す経路を作る

## 内容

ホストでしかビルドできないプロジェクト（Electron・ネイティブ拡張を持つもの）では、ホストが補助環境ではなく本番の作業場になる。karakuri は broker（秘密の取り出し）と `dev-inject.sh`（コンテナへの受け渡し）を持つが、**ホスト上で実行するコマンドへ渡す経路**を持たない。そのため利用側は dotenvx の私鍵ファイルをワークツリーへ置く運用に落ちるが、env-guard がワークツリー内の私鍵ファイルを無条件で拒否するため、その状態ではコミットができない。このチケットはホスト側の受け渡し経路を足して詰みを解く。

**着手の順序。** このチケットは台帳敷設束の**後**に置く（0007 → 0008 → 0009 → 0010 → 0011 → **0014**）。敷設束は `## Guarantees` の末尾へ `§4` から `§18` を順次追記するため、このチケットが先に `§19` 以降を入れると、以降の5枚がすべて `§3` の直後への挿入になって毎回衝突の解決が要る。最後に回せば末尾追記だけで済む。この順序により、着手時点で `§13`（`karakuri.test.sh` を出典とする節）は台帳に存在している。

**不変条件（3本のファイル全体で守る）:**

- 秘密をディスクへ書かない。渡すのは environ だけ
- 鍵が environ に無いときは必ず非ゼロで終わる。素通しはしない。dotenvx は復号に失敗しても非ゼロ終了せず、暗号文をそのまま値として注入して rc=0 を返すため、素通しは「静かに間違った成果物」になる
- broker 契約（`templates/host/broker-bitwarden.sh` 冒頭に書かれている5項）は変更しない。足すのは消費側だけで、契約の緩和を伴わない

**targets が11ファイルで粒度の目安（7以下）を超えている。** 分割の検討結果として、供給層・消費層・配線の3本は「配線されていない中間状態」を挟む価値がなく（配られただけのスクリプトは誰も呼べない）、テストも3本が揃って初めて経路として成立する。README は公開面が変わるチケットが更新する規定なので、この枚から外せない。Windows 用のラッパーとその検証ジョブも、消費層が成立する条件そのものなので分けられない。検収の観点は「供給層を通した実行が通り、鍵の無い実行が落ちる」の2点に収まるため、目安を超えることを承知の上で1枚にしている。

### `templates/host/host-run.sh`（供給層・新規）

`HOST_BROKER` が指す broker を1回だけ呼び、dotenv 形式の stdout を environ へ取り込んで、引数で与えられたコマンドを exec する。

- 呼び出し形は `host-run.sh <cmd> [args...]`。引数は逐語で扱い、シェルを経由しない
- **broker を呼ぶ前に、environ から `DOTENV_PRIVATE_KEY` で始まる変数をすべて削除する。** 利用者のログインシェルに古い鍵や別環境の鍵が export されていると、それが子プロセスへ継承される。dotenvx は対象ファイル名の規約で鍵変数を選ぶため、サフィックスが衝突しない鍵が残っていると誤った鍵が選ばれる。鍵違いは鍵無しより悪い（鍵無しは下記 shim が落とすが、鍵違いは dotenvx が rc=0 で暗号文を返す）。削除を先に置くことで、この木に居る鍵は broker が今返したものだけになる
- 取り込みは dotenv 形式の行単位パース。パースに失敗した行は**値を出さず行番号だけを報告して**非ゼロで終わる（`images/runtime-base/bin/prod-entrypoint.sh` の取り込みと同じ規律。ログの保持期間と可視範囲が秘密の置き場と違うため）
- `HOST_BROKER` が未設定・broker が非ゼロ終了・broker の出力が空・コマンドが未指定は、いずれも非ゼロで終わる。fail-closed
- **broker 項目名の規約はこのスクリプトの責務ではない。** `dev-inject.sh` が `DEV_BROKER` に broker のパスだけを受け取るのと同じ形で、`HOST_BROKER` にパスを受け取る。項目名の組み立ては `karakuri.sh` 側に置く。これにより、このスクリプトを直接叩いても誤った項目を引く経路にはならない（`HOST_BROKER` が無ければ落ちるだけ）

### `templates/host/shims/_dotenvx`（消費層・新規）

利用側プロジェクトの `package.json` から `_dotenvx` として呼ばれ、鍵が environ にあることを確かめて、PATH 上の `dotenvx` を exec する。

- **ホストへ置くのは `_dotenvx` の1名だけ。** コンテナ側の shim は素の名前とアンダースコア付きの名前で実体の解決先を切り替えるが、ホストには karakuri 所有の dotenvx 実体が無いため素の名前に対応する実体を持てない。加えて素の名前で置くと、karakuri と無関係なプロジェクトのグローバル dotenvx を覆う
- **通す条件は `DOTENV_PRIVATE_KEY*` が environ にあることだけ。** 鍵の出どころを問わない。無ければ非ゼロで終わり、鍵の供給手段（`karakuri-run`、または CI のように環境変数で渡す形）を stderr へ示す
- **鍵が karakuri 由来かを判定しない。** 供給層が印を立てて shim がそれを要求する形を検討したが、shim には正当な帯域外供給（CI の secrets）と不当な帯域外供給（利用者が手で export した古い鍵）を区別する手段が無い。どちらも環境変数であり、env を書ける主体は印も書ける。区別できない判定を必須にすると、鍵が正しく供給されている環境まで巻き添えで落ちる
- **コンテナ側 shim の「鍵ファイルが無ければ素通し」とは意味論が違う。** コンテナでの不在は「このコンテナは秘密を要らない」を意味する（dev と prod で持つ鍵が違う設計のため）。ホストと CI での不在は「渡されるはずの鍵が無い」を意味し、素通しは暗号文の混入になる。この差は意図的であり、ファイル内にその理由を書く
- 鍵の値を検査しない・出力しない。exec するだけ
- **`--strict` 忘れの警告をコンテナ側 shim と揃える（この枚で入れるかは裁可の判断に委ねる）。** コンテナ側 shim は prod の鍵が注入されているのに `--strict` が無いとき、強制はせず警告を出す（「強制はしないが、忘れたときに黙ってはいない」）。dotenvx が復号失敗を rc=0 で返すため、prod でだけ効かせている観測である。ホスト側は `-e prod` で同じ状況が起きるので、警告が無いとホストだけ静かに弱い。観測対象は `/run/secrets` のファイル名ではなく environ の変数名になる（`DOTENV_PRIVATE_KEY_PROD*` の有無）

**Windows 用のラッパー `_dotenvx.cmd` を同梱する。** 利用側の CI が Windows runner でこのスクリプトを呼ぶ経路があり（Electron の Windows 配布ビルドでは dotenvx を呼ぶジョブが Windows しか無いことが実測されている）、拡張子の無い `#!/bin/sh` のファイルは PATH に置いても Windows では実行可能ファイルとして解決されない（`PATHEXT` に該当しない）。`pnpm` は Windows で run-script を cmd.exe から起動するため、workflow のステップ側でシェルを指定しても `_dotenvx` の解決は cmd.exe 側で起きる。

- 配るのは `.cmd` の 1 本だけで、`.ps1` は配らない。`pnpm` の run-script は cmd.exe を使うので `.cmd` で解決する。PowerShell から直接叩く経路は契約に無い。同一挙動を保つ維持対象を増やさない
- **`.cmd` の失敗が非ゼロで返ることを実測で固定する。** cmd の `errorlevel` の伝播漏れは古典的な罠で、落ちるべきときに 0 で返る形になる。それが起きると Windows の署名済みリリースビルドに暗号文が焼かれる。手書きする以上、テストで押さえる
- 利用側に `script-shell=bash` を設定させる形は採らない。karakuri の命名規約の都合で、利用側の Windows ビルド全体の run-script 実行シェルを差し替えることになり、無関係なスクリプトまで巻き込む

### CI 経路

利用側の `package.json` を `_dotenvx` へ揃えると、その `package.json` のスクリプトは CI からも呼ばれる。CI の runner には karakuri も shim も無く、鍵はリポジトリの secrets から環境変数で渡る。

この経路が通ることを設計に織り込む。

- **shim の通過条件に鍵の出どころを入れない。** 上記のとおり、鍵が environ にあれば通す。CI の帯域外供給は正当な供給であり、shim にはそれと「利用者が手で export した古い鍵」を区別する手段が無い（どちらも環境変数で、env を書ける主体は印も書ける）。区別できない判定を必須にすると、鍵が正しく供給されている環境まで落ちる
- **名前解決は CI 側で PATH を足して解く。** `_dotenvx` という名前は捨てられない（コンテナは鍵をシェルの environ に出さず `/run/secrets` から読むため、素の名前では `node_modules/.bin` が勝って鍵が入らない）。この shim は broker も `/run/secrets` も読まないので karakuri への依存が無く、単体で動く。CI はタグ指定の浅い clone で shim のディレクトリを取り、PATH へ足せばよい。karakuri が既に持つ配布機構をそのまま使うので、新しい配布単位は作らない
- **CI は Windows でありうる。** レシピは Windows で成立する形で書く。PATH へ足すディレクトリのパスは runner のテンポラリを使い、POSIX 固定のパスを書かない。`_dotenvx.cmd` の同梱が前提になる（上記）
- README にこのレシピを書く（下記）

#### shim を npm パッケージの `bin` として配る形は採らない

npm の `bin` にすれば `.cmd` と `.ps1` は npm が生成するため、Windows のラッパーを手書きせずに済む。それでも採らない。

- **関門が workspace の内側へ降りる。** `karakuri.sh` の冒頭が「ツールの置き場は dev container へ bind mount される workspace の外にすること」を、常駐するエージェントに書き換えられるという理由で明文にしている。`node_modules` はその内側であり、しかも `node_modules/.bin` は PATH 先頭なので、イメージ側の shim に黙って勝つ。私鍵の関門を、守るべき相手が書ける場所へ移すことになる
- **配達経路が増える。** レジストリ側の侵害・publish 権限の侵害・install 時の typosquat・lockfile のドリフトが、全ビルドが通る経路に乗る。このリポジトリは既に npm 経由で届くセキュリティ経路のコードを sha256 で照合してから実行する扱いにしており、その 2 本目を commit 時より熱い経路へ置くことになる
- **Windows の検証は省けない。** Node で書けばラッパーは npm が生成するが、環境変数名の大文字小文字（Windows は case-insensitive で、列挙は設定されたままの綴りを返す）・`.cmd` である実体の起動・その経路での終了コードの伝播は、いずれも我々のコードの Windows 挙動である

#### `-e prod` の到達範囲

`prod` を選ぶと、**本番の私鍵がホストのビルド木全体に入る**——その木で走る全ての依存・postinstall・ビルドツールの子プロセスから読める（下記「開いたままにする穴」と同じ性質だが、鍵の重みが違う）。

karakuri の prod 系は他の経路では隔離されている（`prod-run.sh` は tmpfs のコンテナで走り、workspace を mount しない）。ホストでのビルドはその隔離が構造的に取れない場所であり、`-e prod` はその代償を受け入れる操作である。既定を `dev` にし、`prod` を明示的に打たせるのはこのため。README の限界に書く。

#### この設計で開いたままにする穴

利用者がログインシェルへ手で古い鍵を export した状態で、供給層を通さずビルドを叩くと、その鍵で通ってしまう。shim からは CI の正当な供給と区別できないため、ここは閉じない。閉じる手段は shim ではなく、成果物や `package.json` に対する検査（別チケットの静的検査）の側にある。README の限界として書く。

なお `karakuri-run` を通る経路ではこの穴は開かない——供給層が先に既存の私鍵を全削除する。

### 置き場所

shim は `templates/host/` へ直接置かず、専用の `templates/host/shims/` へ置く。`templates/host/` には broker と注入スクリプトが同居しており、そのディレクトリを PATH へ載せると broker が名前で叩ける状態になる（PATH を継承する任意のプロセスから）。ディレクトリ名を `shims` にするのは、コンテナ側の `images/runtime-base/shims/` と同名にして対応物であることを見て分かるようにするため。

### `templates/host/karakuri.sh`（配線）

```
karakuri-run -b <broker-key> [-e dev|prod] -- <cmd> [args...]
```

- **`-b` は必須。** `karakuri-dev-inject` と `karakuri-dock` では省略時に `-p` の値へ落ちるが、この関数は compose プロジェクトを持たないため既定の供給元が無い
- **`-e` は `dev`（既定）か `prod`。** ホストでのビルドには本番の鍵を要する経路がある（Electron の配布ビルドなど）。既定を `dev` にするのは、`prod` を打つときだけ意識させるため
- `--` を終端子とし、それ以降は一切解釈しない。位置引数を先頭に取る形にしないのは、既存の2関数が位置引数を意図的に廃止しているのと語彙を揃えるため
- broker 項目名の組み立ては既存の `karakuri-broker-command <-e の値> <key>` と `_karakuri_broker_env_into <-e の値> <key>` をそのまま使う。**項目の並びは既存の規約がそのまま出る**——`dev` は全プロジェクト共通の個人項目を挟む3項目、`prod` は挟まない2項目。この非対称は既存の意図なので、この関数で揃えたり足したりしない。broker 側のロジックは新規に書かない
- 名前の検証と、共通名を項目キーにする指定の拒否は `karakuri-dev-inject` と同じ関数・同じメッセージ語彙で行う。**共通名の拒否は `-e` の値によらず常に行う。** `prod` の並びには共通項目が入らないので同じ項目を二度読むことにはならないが、予約名が片方のモードでだけプロジェクトキーになれる状態は罠になる
- `-e` に `dev` / `prod` 以外を渡したときは、broker を一度も起動せずに非ゼロで拒否する
- 実体は `host-run.sh` を既存のツール解決で見つけ、`HOST_BROKER` に broker のパスを渡して起動する（`karakuri-dev-inject` が `DEV_BROKER` を渡すのと同じ形）

**PATH への追加。** source した時点で `templates/host/shims` を PATH へ **append** する。

- 前置きしない。`_dotenvx` は衝突しない名前なので前置きに利得が無く、利用者のコマンドを覆うリスクだけが増える
- 複数回 source されても重複しないガードを置く（このファイルがツール探索ディレクトリの環境変数を「既に値があれば上書きしない」扱いにしているのと同じ配慮）
- **PATH をここで足す理由**: shim ディレクトリのパスは karakuri 側が決めた規約である。利用者の設定ファイルへ書かせると、規約は karakuri にあるのに実装は各利用者の設定ファイルにある状態を新しく1件作ることになる。PATH が通っていない場合は `_dotenvx` が見つからずビルドが落ちるため、失敗は静かにならない

**併せて直すもの。**

- ファイル冒頭の関数の目次と `karakuri-help` の両方。関数を増減させたときにこの2箇所を直す規律はファイル内に書かれている
- broker 実装の差し替え候補を数行のメモとしてファイル冒頭へ置く。macOS Keychain を Bitwarden の前段キャッシュにする案と、秘密を自プロセスのメモリだけで保持する常駐 agent の案がある。**書くのは差し替え点が `karakuri-broker-command` であることと候補の名前だけで、設計は書かない**（どちらも実装するかが未決であり、現時点で拘束力を持たない）

### `package.json`

新規のファイルは既存の列挙に入っていないため、次の2つを足す。

- `test`: 新しいテスト2本（`templates/tests/host-run.test.sh`、`templates/tests/host-shim.test.sh`）
- `lint:sh:images`: `images/runtime-base/templates/host/shims/_dotenvx` を `--shell=sh` の側へ足す（`templates/host/*.sh` の glob は shims を拾わず、shim は拡張子を持たない）。**ディレクトリごとの glob にはしない**——`_dotenvx.cmd` は shellcheck の対象ではなく、glob で巻き込むと lint が落ちる

### `.github/workflows/ci.yml`

`test` ジョブ（`ubuntu-latest`）の隣に Windows のジョブを足す。`_dotenvx.cmd` を手書きする以上、その振る舞いを実測で固定しないと約束にできない。

- 検査するのは `.cmd` ラッパーの 2 点だけ: **鍵が無いときに非ゼロで返る**こと、**鍵があるときに実体が起動する**こと。既存のテスト一式を Windows で回すことは目的ではない（対象は POSIX 側の成果物であり、二重に回す意味が無い）
- 実行は cmd.exe から行う。bash から呼ぶと `.cmd` の解決と `errorlevel` の伝播という検査したい経路を通らない

### `images/runtime-base/README.md`

このチケットは公開面を変えるため、README（現在形4種のうち「公開面の使い方」）の更新はこのチケットの責務である。更新経路が「公開面が変わるチケットで更新」と定められている。

既存の節へ書き足す形にし、新しい章立てを作らない。

- `## shim の仕組み` へ、ホスト側 shim を1節。**置く名前が `_dotenvx` の1つだけであること**と、**コンテナ側 shim と意味論が違うこと**を書く。コンテナ側には「鍵ファイルが無ければ素通し」の節（素通しは fail-open ではない、という説明を持つ）があり、ホスト側はそこだけ反転する。既存の説明と隣に並ぶので、反転していることと理由が読み取れる形にする
- `## shim の仕組み` の `pnpm run` の内側では効かない、という既存の節との関係を明示する。ホスト側では `_dotenvx` の名前がその制約への答えになっている
- `## 使い方` へ `karakuri-run` の呼び出し形を1節。`-e` で `dev` / `prod` を選べること、既定が `dev` であること、項目の並びが既存の dev 注入・prod 起動と同一であること（鍵の置き場を増やさなくてよいこと）を書く
- **`-e prod` の限界を書く。** 本番の私鍵がホストのビルド木全体に入る。`prod-run.sh` の経路が持つ隔離はホストのビルドでは取れない
- `## 使い方` の `### ホスト側ツールを入手する` へ、shim のディレクトリの PATH が `karakuri.sh` の source で通ること。**導入手順の行数は増えない**ことが読み取れるようにする

- `## 使い方` へ **CI 経路のレシピ**を1節。`_dotenvx` の名前を解決させるために shim のディレクトリを PATH へ足す手順と、鍵は環境変数で渡せば通ること。Windows runner でも成立する形で書く（パスは runner のテンポラリを使い、POSIX 固定のパスを書かない）。**npm の `bin` として配る形を採らない理由**も1行添える——関門が `node_modules`、すなわち workspace の内側へ降りるため
- **移行時に CI が赤くなりうることを書く。** `_dotenvx` へ揃えると、鍵が供給されていない CI ジョブは「鍵が無い」として明示的に落ちる。それまでは dotenvx が rc=0 で暗号文を値として注入していたため成功に見えていた。落ちたら既存の鍵未供給が顕在化したものであって、この経路が壊したのではない、と読み取れる形にする
- **限界を書く。** 手で export した古い鍵での実行は shim からは CI の正当な供給と区別できないため通る。閉じる手段は shim の側には無い

利用側が受け入れのために必要な作業（`package.json` の呼び出しを `_dotenvx` へ揃える、ホスト実行の入口を `karakuri-run` 経由にする、ワークツリーの私鍵ファイルを消す、CI に PATH を足す）も README に書く。これが無いと、契約を知らない利用者は経路を使えない。
