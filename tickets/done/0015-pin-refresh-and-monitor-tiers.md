# 固定した版を一括で上げ、追従漏れの監視を段階化する

## 内容

この変更は3つを1枚で行う。分けないのは、監視の鳴り方を直さないまま監視対象だけを増やすと、増やした分がそのままノイズになり、装置として先に壊れるためである。順序は「鳴り方を直す → 版を上げる → 規則を書く」で、上げた結果が監視の緑として観測できる並びにしてある。

### いま何が起きているか

`monitor.yml` は毎日走り、`ARG EGRESS_GUARD_VERSION`（runtime-base）と `ARG CRIT_VERSION`（devcontainer-base）の2つだけを上流の最新と照合している。判定は「最新と文字列が違えば warn」の二値である。

crit の固定は `v0.18.0`、上流の最新は `v0.19.1`。すなわちこの通知は、上げるまで毎日 warn を出し続ける。上げる判断が月単位である以上、二値の判定では鳴りっぱなしが常態になり、即時に動く必要のある差分（security advisory）が、月次の棚卸しで見ればよい差分と同じ見た目で埋まる。

一方で、固定してあるのに監視されていない版がある。`PNPM_VERSION` / `DOTENVX_VERSION` / `WRANGLER_VERSION`（いずれも runtime-base）、`FROM node:24`（runtime-base）、`FROM golang:1.26-bookworm`（devcontainer-base の crit builder）。固定は上流の侵害リリースを自動で流入させないための措置なので、追従漏れを人が覚えているわけにいかない。

### やること

**1. 追従の遅れを判定する実体をワークフローから切り出す。**

`.github/scripts/pin-lag.sh`（新規）に、固定値と上流の最新値から遅れの段階を決める判定を置く。`monitor.yml` はこれを呼んで文面を組み立てるだけにする。

切り出すのは、この判定が黙って壊れる向きの故障を持つためである。semver の比較と日付の差を扱う以上、条件を1つ書き損じれば「差があるのに何も鳴らない」側へ倒れうる。監視装置が黙る故障は、監視対象の不具合と違って誰も気づかない。ワークフローに直書きのままでは実行のたびに本番でしか確かめられないので、テストが書ける形へ出す。

**2. 深刻度を期限ではなく即時性で分け、2つにする。**

固定値の遅れについて `pin-lag.sh` が返す深刻度は次の2つだけとする。

- `alert` — **即時に動く。** 固定している版が security advisory の影響を受けているとき。既存の用法（経路を通らない公開の検出）もそのまま `alert` に残す
- `info` — **上記以外のすべて。** `STATUS` を上げない。月次の棚卸しで「上げるか、見送るか」を確定する対象になる

`warn` は固定値の遅れには使わない。既存の用法（未 publish 等）はそのまま残す。

**段階を対応期限で切る形をやめる。** 前の案は `info` を「月次」、`warn` を「当月中」としていたが、この2つはほとんど同じ期限であり、区別が文面の上にしかなかった。加えて期限の切り方として向きが逆だった。major の遅れは破壊的変更を伴い、利用側のプロジェクトが複数ある以上、調整に要する時間は minor の追従より**長い**。それを短い期限の側（`warn`）へ置けば、期限を守れないことが常態になり、守れない期限は無いのと同じになる。

かわりに、即時に動く必要があるもの（`alert`）だけを深刻度で分け、それ以外は月次の棚卸しへ集める。棚卸しでは各対象について「上げる」か「見送る」かを確定させる。見送ったものが次の月にまた同じ顔で並ぶのは正しい。確定させることと、期限内に上げることは違う。

**判断の材料は深刻度ではなく文面で渡す。** `pin-lag.sh` は深刻度とは別に、棚卸しで判断するのに要る値を返す。

- 遅れの大きさと種別（何版遅れているか、`major` / `minor` / `patch` のどれか）
- advisory を照会できたかどうか（後述）
- node については maintenance 入り・EOL までの残り日数

major の遅れは、深刻度を上げるのではなく文面で目立たせる。着手の時期は棚卸しで決めるものであり、通知が期限を決めるものではない。

node の日付は `nodejs/Release` の `schedule.json` を引く。実測（2026-09-03 時点）では v24 が maintenance 2026-10-20 / EOL 2028-04-30 である。残り日数を毎回文面に出すことで、棚卸しのたびに期日が見える。日数がいくつを下回ったら深刻度を上げる、という閾値は置かない。閾値を置けば「その日までは動かなくてよい」という読み方が生まれ、移行に要る期間の見積もりを通知の側が勝手に決めることになる。node を上げる判断そのものは GitHub issue が持つ。

**3. 固定している版が advisory の影響下にあるかを照会する。**

npm 由来の3つ（pnpm / dotenvx / wrangler）について、固定値そのものが影響範囲に入る advisory があるかを GitHub Advisory API（`gh api /advisories?ecosystem=npm&affects=<pkg>@<ver>`）へ問い合わせ、あれば `alert` を返す。

**照会できる範囲を宣言として書き、できない範囲は明示して残す。** node（Node.js の security release）、crit（GitHub リポジトリの advisory）、golang builder、egress-guard（npm 由来だが本チケットが追加する照会対象には含めない）はそれぞれ同じ照会には乗らない。ここで半端に全部を拾いにいくより、上記の npm の3つだけが自動で拾われ、残る4つは拾われないことを文書に書く方を採る。拾えていない範囲が見えていれば人が補える。「全部見ているつもり」で穴が隠れる形にはしない。

**照会の可否は Slack の文面に出す。** `pin-lag.sh` は遅れの段階とは別に、その対象について advisory を照会できたかどうかを返す。`monitor.yml` はそれを行ごとの印として出し、照会に乗らない対象・照会に失敗した対象が、照会して該当なしだった対象と文面の上で区別できるようにする。

区別が要るのは、`info` の行が2つの意味を持ってしまうためである。「patch が遅れているが advisory は無いと確かめた」と「patch が遅れていて advisory を確かめていない」は、全体が緑であっても人が取るべき行動が違う。後者は棚卸しのときに人が上流のリリースノートを読む必要があり、その必要があることが文面から読めなければならない。

**4. 監視対象を固定値の全体へ広げる。**

runtime-base の `PNPM_VERSION` / `DOTENVX_VERSION` / `WRANGLER_VERSION` / `FROM node:`、devcontainer-base の `CRIT_VERSION` / `FROM golang:`、および既存の `EGRESS_GUARD_VERSION`。読み出しは既存の `sed -n 's/^ARG .../p'` と同じ形でよい。

**5. 固定した版を上げる。**

- pnpm `11.20.0` → `11.25.0`
- dotenvx `2.19.2` → `2.23.0`
- wrangler `4.119.0` → `4.128.0`
- crit `v0.18.0` → `v0.19.1`

pnpm はルート `package.json` の `packageManager` も同じ版へ動かす。Dockerfile 側のコメントが述べているとおり、片方だけを動かすとイメージと各プロジェクトの宣言が乖離する。

crit の 0.18 → 0.19 で入ったのは GitLab の merge request 対応、コードフォント設定、コメント markdown の HTML 許可、大規模レビューの読み込み性能、live mode のリバースプロキシ対応である。`CRIT_PORT` / `CRIT_HOST` / `CRIT_NO_UPDATE_CHECK` の扱いは変わっていない。0.19.1 には共有経路（`crit share`）の変更も含まれるが、この経路は使っていないため実測の対象にしない。

**6. README に更新の規則を足す。**

`docs/conventions.md` は作らない。現在形の文書を1つ増やせば維持の義務がそこに生まれるので、既存の README に節を足す方を採る。書く内容は3つ。

- node は Active LTS を追う。LTS 化から数パッチ寝かせて移る。移行できない利用側が出た場合に旧 LTS の fork を検討する
- 固定値の棚卸しは月に1度。security advisory は例外として即時に上げる。自動で拾えるのは npm 由来の3つ（pnpm / dotenvx / wrangler）だけで、node / crit / golang builder / egress-guard の advisory は照会に乗らない
- `monitor.yml` は上げ忘れを拾う装置であって、上げる判断はしない。`alert` だけが即時に動く合図で、それ以外は月次の棚卸しで「上げるか、見送るか」を確定する。見送った対象が翌月も同じ顔で並ぶのは正しい
- 文面に「advisory 未照会」の印が付いている対象は、棚卸しのときに上流のリリースノートを人が読む。自動で拾えるのは npm 由来の3つだけである

### 順序依存

イメージは runtime-base → devcontainer-base の順で焼く。逆にすると devcontainer-base が古い `:1` を掴んだまま焼き上がり、失敗として現れない。

**台帳の番号は `§21` から始める。** 統合ブランチの台帳は `§18` までだが、`0014` が `§19` と `§20` を使う。0014 と本チケットはどちらも `.github/` を触るため CODEOWNERS の関門で同じように止まり、マージ順を 0014 → 0015 に固定できる。番号を `§19` のままにすると、0014 が先に入った台帳へ本チケットをマージする時点で同じ場所への追記としてコンフリクトし、その解決の中で採番をやり直すことになる。先に繰り下げておけば解決は並べるだけで済む。

順序が入れ替わるのは 0014 が取り下げられた場合に限られ、そのときは `§19` と `§20` が欠番になる。番号を詰めるかどうかはその時点で単独に判断する。

### やらないこと

- **node を上げること。** `FROM node:24` はこの枚では動かさない。v26 の LTS 化（2026-10-28）を待つ判断と、runtime-base のタグが `:2` へ上がることに伴う旧系統の扱い（fork の要否）は別の場所で持つ
- `FROM node:` を digest まで固定すること。他の固定値と不揃いであることは事実だが、締める判断は node のメジャーを動かす回と同じ場所に置く
- npm の版を明示して固定すること。プロジェクト側に出る「新しい npm がある」旨の警告は、node:24 の同梱が 11.19.0、npm 単体の最新が 12.0.2 という乖離によるもので、node の系統を動かしても解消しない。固定を1本増やす複雑さに見合わないため放置する
- node / crit / golang builder の advisory を自動で照会すること。供給元が npm と別で、同じ問い合わせに乗らない。拾えない範囲として文書に書くところまでを行う
- dotenvx の実体の挙動を新たに実測すること。`shim.test.sh` は shim が何を注入したかだけを見ており、実体は偽物に差し替えている。2.x の resolver 経由でも `DOTENV_PRIVATE_KEY*` の環境変数注入が効くことは設計書 §10 の実測項目として別に立っている。この枚は 2.19 → 2.23 のマイナー移動であり、系統をまたがない

## 保証

### 新たに宣言する保証

`pin-lag.sh` の判定について、`.github/scripts/tests/pin-lag.test.sh` を出典として台帳へ `§21` として足す（番号の根拠は上の「順序依存」）。宣言する内容は次のとおり。

- 固定値と上流の最新が同一のとき、遅れは `none` を返す
- 遅れがあるとき、その大きさ（何版遅れているか）と種別（`major` / `minor` / `patch`。3桁とも一致するが文字列が異なる場合は `differs`）を返す
- **遅れの大きさや種別だけでは深刻度が `alert` にならない。** major が遅れていても、advisory の影響を受けていなければ深刻度は `info` に留まり、`STATUS` を上げない
- 版の文字列が `v` 前置の有無で食い違っていても、同一の版として扱う（`v0.19.1` と `0.19.1`）
- **否定対照:** 上流の版を取得できないとき、遅れ `none` を返して黙るのではなく、取得できない旨を返す。取得の失敗が「最新に追いついている」と区別できない形で通ることはない
- **否定対照:** 固定値を読み出せないとき（`ARG` の行が消えた・名前が変わった場合を含む）、読めない旨を返す。監視対象が構成から消えたことが、緑として通らない
- node の系統について、`schedule.json` の日付から maintenance 入り・EOL までの残り日数を返す。**残り日数がいくつであっても、それ自体では深刻度を上げない**
- 固定値が npm の security advisory の影響範囲に入るとき `alert` を返す。遅れが patch 1つでも、遅れが無くても（固定値が最新でも advisory の影響下にありうる）、advisory があれば `alert` になる
- **否定対照:** advisory の照会に失敗したとき、該当なしとして `alert` を返さずに通ることはない。照会できなかった旨を返す。「advisory が無い」と「advisory を確かめられなかった」が同じ緑にならない
- 深刻度とは別に、その対象について advisory を照会できたかどうかを返す。照会に乗らない対象（node / crit / golang builder / egress-guard）では、遅れの有無にかかわらず照会していない旨が付く
- **否定対照:** 照会して該当なしだった対象と、照会に乗らない対象・照会に失敗した対象が、同じ値では返らない

### 維持する保証

- `images/runtime-base/tests/run.sh` が並べる既存のテスト一式。版を上げた後も無傷であること
- `monitor.yml` の既存の判定（タグとレジストリの照合、および `alert` の用法）
- `shipped-symbols.test.sh` の記号検査。README へ足す節が、このリポジトリの外で参照先を持たない記号を含まないこと

### 廃止する保証

なし。既存の判定を取り下げず、固定値の遅れに対する深刻度の付け方を warn 一色から alert / info の2値へ組み替えるだけである。
