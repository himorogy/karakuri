# エージェント向け詳説

このファイルは、**egress 規制下のコンテナで動くエージェントが、allowlist を変更する作業を頼まれたときに読む**ためのものです。

常時読み込ませる前提では書いていません。エージェントのコンテキストに常駐させるのは、README の[エージェントへの指示書](../README.md#エージェントへの指示書)にある短い断片だけで足ります。日常の作業に必要なのは「遮断は設計であること」「迂回しないこと」「repo 側の編集は再ビルドまで効かないこと」の 3 つで、それ以上はこの作業のときにしか要りません。

イメージビルド時に `/etc/egress-guard/agent-brief.md` へ置いておくと、エージェントが必要になった時点で読めます。

---

## このコンテナは egress 規制下にある

開発環境は [`@himorogy/egress-guard`](https://www.npmjs.com/package/@himorogy/egress-guard) による allowlist ベースの egress ファイアウォールの下で動きます。**allowlist に無い宛先への外向き通信は遮断されます。**

**遮断は故障ではなく設計です。** 目的は、プロンプトインジェクションやエージェントの暴走が起きたときに、秘密やソースコードを書き出せる先を限定することにあります。想定している敵は**このコンテナの中で動くエージェント自身**です。

したがって次の 2 つを守ってください。

* 遮断をネットワーク障害・DNS 障害・プロキシ設定の不備と診断しない
* 遮断を自力で迂回しようとしない（詳細は[やってはいけないこと](#やってはいけないこと)）

---

## 遮断はどう見えるか

| 状況 | 現れ方 |
|---|---|
| 許可されていないホストへの TCP 接続（`enforce`） | ICMP `admin-prohibited` による即時の接続失敗。クライアント側では `No route to host` などになります。**ハングやタイムアウトではなく即座に落ちます** |
| 割り当てられたリゾルバ以外への DNS 問い合わせ（`dig @8.8.8.8` など） | 無応答（DROP）。応答待ちのタイムアウトになります |
| IPv6 での外向き通信 | ICMP6 `adm-prohibited` による即時の失敗。IPv6 は全モードで拒否されます |
| WebFetch（許可されていないドメイン） | **失敗し、出力が返りません。** Anthropic 側の取得へフォールバックすることはありません |

**名前解決が成功しても、そのドメインが許可されているとは限りません。** 許可されたリゾルバは再帰問い合わせを行うため、任意のドメインの `dig` は通ります。遮断されるのはその後の接続です。**`dig` が引けたことを「許可されている」の根拠にしないでください。**

### 遮断かどうかの切り分け

まず何が許可されているかを見ます。ネットワークアクセスを伴わないので、遮断された状態でも実行できます。

```sh
init-project-firewall.sh --print-allowlist
```

出力に載っているドメインのどれか 1 つに到達できて、目的のホストにだけ到達できないなら、それは egress-guard による遮断であって、ネットワーク障害ではありません。

```sh
curl -sS -o /dev/null --connect-timeout 5 https://<出力に載っているドメイン>/  # 通るはず
curl -sS -o /dev/null --connect-timeout 5 https://<目的のホスト>/              # ここだけ落ちるなら遮断
```

**「常に許可されているドメイン」は存在しません。** ベースプロファイルはプロジェクトごとに選べるため、`api.anthropic.com` や `github.com` が入っていない構成もあり得ます。切り分けの基準は必ず `--print-allowlist` の出力から取ってください。

## あなたにできること・できないこと

### できること

* **許可されている宛先を読む** — 非特権で実行できます。ネットワークにも触りません

  ```sh
  init-project-firewall.sh --print-allowlist
  ```

* **実効設定そのものを読む** — `/etc/egress-guard/firewall.json` は root 所有で書き換えられませんが、既定の手順どおり配置されていれば（`644`）読めます

* **設定ファイルの妥当性を検証する** — 非特権で実行できます。書き換えを提案する前に、その JSON が受理されるかを確かめられます

  ```sh
  init-project-firewall.sh --check-config --config <検証したいファイル>
  ```

* **ポリシーを再適用する** — sudoers で許可されています。何度実行しても同じ結果になります（冪等）

  ```sh
  sudo /usr/local/bin/init-project-firewall.sh
  ```

  **これは意図された設計です。** 再適用が行うのは root 所有の実効設定の**再解決**だけで、ポリシーそのものは変わりません。allowlist は起動時に解決した IP の集合なので、**CDN のアドレスが動いて「許可されているはずのドメイン」に到達できなくなった場合はこれで回復します。** 遮断に当たったとき、自分で試してよい復旧手段はこれだけです。

### できないこと

* **ポリシーを変えること。** 効力を持つのは `/etc/egress-guard/firewall.json` だけで、これは root 所有です
* **リポジトリ側の設定ファイルを直して直すこと。**
  <!-- 記入欄: リポジトリ側のコピーのパス。既定は .devcontainer/firewall.json -->
  リポジトリ内の `.devcontainer/firewall.json` は**ソースにすぎません**。ここを編集しても、**イメージを再ビルドするまで一切反映されません。** 編集しただけで「直った」と報告してはいけません
* **遮断された宛先の一覧を読むこと。** 記録先の ipset `egress-audit-v4` を読むには root が必要です。必要なら人間に依頼してください

**まとめると、遮断に自分で対処する手段は「再適用を 1 回試す」以外にありません。** それで直らなければ人間の操作が要ります。

## 遮断に当たったときの手順

1. 上の[切り分け](#遮断かどうかの切り分け)で、egress-guard による遮断であることを確かめる
2. `--print-allowlist` の出力に目的のホストが載っているかを確認する
3. **載っているのに落ちる場合** — CDN のアドレス変動の可能性があります。`sudo /usr/local/bin/init-project-firewall.sh` を 1 回実行して再試行する
4. **載っていない場合** — 作業を止めて人間に報告する。**勝手に迂回しない**

報告には次を含めてください。

* **必要なホスト名**（ワイルドカードではなく具体名。IP ではなく名前）
* **何をするために必要か**（どのコマンド・どのツールが、どの工程で使うか）
* **代替手段の有無** — 特に、その取得を**イメージビルド時に移せないか**。egress-guard は `postStartCommand` で適用されるため、**起動後に外部から何かを取ってくる作業は原理的に不利です。** ビルド時に移せるなら、それが第一選択になります
* 遮断を確認したコマンドとその出力

報告の雛形:

> `<ホスト名>` への接続が遮断されました（`<コマンド>` が `<エラー>` で失敗）。
> `<用途>` に必要です。再適用は試しましたが変わりませんでした。
> allowlist への追加が必要か、あるいはこの取得をイメージビルド時に移すのが適切か、判断をお願いします。

## やってはいけないこと

いずれも**遮断の回避**にあたります。ファイアウォールが防ごうとしていることを、内側から無効化する行為です。

* プロキシ・トンネル・VPN・リバースシェルを立てる、あるいはそれらを提案・設定する
* 許可済みのホストを踏み台にして別の宛先の内容を取ってくる
* DNS クエリに情報を載せて外へ出す
* 別の CDN・ミラー・第三者のプロキシサービスなど、**allowlist を通る経路を探して回る**
* `mode` を `audit` に変える、あるいは変えるよう促す
* `/etc/egress-guard/` 以下、`/usr/local/bin/init-project-firewall.sh`、sudoers を書き換えようとする
* リポジトリ側の `firewall.json` を編集して「修正した」と報告する（**再ビルドまで反映されません**）
* 遮断を「一時的なネットワーク障害」として報告し、リトライを繰り返す

## Web 検索と Web 取得

Claude Code の 2 つの Web ツールは、egress から見て性質が違います。**2026-08-03 に Claude Code v2.1.220 で実測した結果です。**

| ツール | コンテナからの egress | 使えるか |
|---|---|---|
| **WebSearch** | 検索実行中、コンテナから外部への新規接続は観測されませんでした（Anthropic 側で完結する） | **追加設定なしで使えます** |
| **WebFetch** | コンテナ内の `claude` プロセスが**取得先ドメインへ直接 TCP 443 を張ります** | **`allowDomains` に入っているドメインだけ** |
| `curl` などの自前の取得 | そのドメインへ直接 | `allowDomains` に入っているドメインだけ |

**したがって調査の起点は WebSearch にしてください。** 追加設定が要らず、遮断にも当たりません。

**WebFetch が失敗したら、それはドメインが allowlist に無いということです。** 別の URL を次々に試すのではなく、[遮断に当たったときの手順](#遮断に当たったときの手順)に従って人間に伝えてください。

> WebFetch の取得内容は、ふつう小型モデルの要約を経由します。ただし Claude Code が事前承認している 91 のドキュメントドメインでは要約がバイパスされ、**原文がそのままコンテキストに入ります。** そのドメインが侵害されていれば prompt injection の緩衝材はありません。

## 設定の書き方（追加を提案するとき）

人間から「必要なドメインを `firewall.json` に足す変更を出してほしい」と頼まれた場合に限り、リポジトリ側のコピーを編集します。**編集しただけでは反映されない**ことは、必ず添えて報告してください。

```json
{
	"version": 1,
	"profile": ["anthropic", "npm", "github"],
	"mode": "enforce",
	"allowDomains": ["registry.example.com"],
	"allowCidrs": ["203.0.113.0/24"],
	"allowHostPorts": [5432],
	"sshdPort": 22
}
```

守るべき制約:

* **フィールドは上の 7 つだけです。** 未知のキーがあると設定全体が拒否され、コンテナは panic テーブル（loopback 以外すべて遮断）で起動します
* **`profile` は減らす方向にしか触らないでください。** 既に入っているバンドルを外すと、それに依存していた作業が止まります。増やす提案も、必要な理由を添えてください
* **JSON にコメントは書けません。** `jq` でパースするため、JSON5 / JSONC は不正な JSON として拒否されます
* **ワイルドカードは書けません**（`*.example.com` は拒否されます）。必要なホスト名を具体的に列挙してください
* **私設アドレス帯の CIDR は書けません** — RFC1918、CGNAT（`100.64.0.0/10`）、loopback、link-local、multicast / 予約。`0.0.0.0/0` やプレフィックス長 8 未満も拒否されます
* `169.254.169.254`（クラウドのメタデータサービス）は link-local なので**許可できません。遮断されているのが正しい状態です**
* 書いたら `--check-config --config <パス>` で検証してから出してください

**`firewall.json` は PR レビュー必須ファイルとして扱われます。** 許可先を増やす提案は、増やす理由を添えてください。
