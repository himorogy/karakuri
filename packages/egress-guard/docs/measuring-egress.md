# 宛先の実測とバンドルの保守

**このパッケージが埋め込んでいるドメインは、実測しないと正しさを保てません。** 基底プロファイル（[`spec.md`](./spec.md) §3.3）のバンドルは他社製品のエンドポイントを列挙したものであり、**製品側の都合で動きます。** 一度書いたら終わりではなく、定期的に測り直す対象です。

この文書は、その測り方と判断基準をまとめたものです。プロジェクト固有の `allowDomains` を決めるときにも同じ手順が使えます。

---

## なぜ実測が要るか

初版の基底プロファイルは [claude-code の devcontainer](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh) にある 13 ドメインをそのまま持ってきたものでした。**2026-08-04 に実測したところ、この 13 件は既に現実と合っていませんでした。**

* **入っているのに使われていないもの** — `sentry.io`、`statsig.com` への接触は観測されませんでした
* **使われているのに入っていないもの** — Datadog のログ収集エンドポイントと `downloads.claude.ai` が観測されました

**リストを信じて写した場合、この 2 種類のずれはどちらも見えません。** 前者は allowlist を無駄に広げ、後者は「入れたはずなのに動かない」として現れます。

## 測り方

### 1. `audit` で起動する

`firewall.json` を `mode: "audit"` にして**イメージを再ビルド**します。再接続では反映されません。

**`enforce` で代用しないでください。** 記録自体は両モードで行われますが、`enforce` で得られるのは**依存の連鎖の最初の 1 段だけ**です。ドメイン A の応答をもとに B へ接続する処理では、A が遮断された時点で B への接続は試行されず、記録にも現れません。理由の詳細は [`design.md`](./design.md) §2.11。

### 2. 測りたい操作を一通り行う

**観測窓の長さがそのまま結果の信頼度になります。** 短い窓では、次のものが漏れます。

* **起動時にしか出ない通信** — 一度キャッシュされると再取得されないもの（feature flag など）
* **異常時にしか出ない通信** — エラー送信など
* **定期的にしか出ない通信** — 更新確認など

「観測されなかった」は「使われていない」ではありません。**窓の長さと、その間に何をしたかを記録に残してください。**

### 3. 記録を読む

```sh
# ホストから。コンテナの取り違えに注意（README「適用されているか確かめる」）
docker exec -u root <container> ipset list egress-audit-v4
```

**`timeout` の残量が新旧の順序です。** 残量が大きいほど後に追加されたものです。上限は 604800（7 日）なので、`604800 - 残量` が経過秒数になります。**`--exist` で再追加されると残量がリセットされる**ため、これは「最後に接触した時刻」です。

### 4. IP を名前に戻す

**逆引きから始めないでください。** CDN やクラウドのロードバランサは PTR を持たないか、`*.bc.googleusercontent.com` のような事業者名しか返しません。

**順序はこうです。**

1. **候補ドメインを解決して突き合わせる。** 心当たりのあるドメインを `dig +short` し、記録された IP と一致するか見ます。**ネットワークに何も足さない**ので、これを最初に試します

   ```sh
   dig +short statsig.com sentry.io deb.debian.org
   ```

2. **一致しなければ TLS 証明書の SAN を見る。**

   ```sh
   echo | openssl s_client -connect 35.190.46.17:443 2>/dev/null \
     | openssl x509 -noout -subject -ext subjectAltName
   ```

   専用のアドレスを持つサービスでは、これが決定的です（`downloads.claude.ai` と Datadog はこれで確定しました）

### どちらの方法も CDN 上では決定的にならない

**1 つの IP が 1 つのホスト名に対応するのは、専用アドレスを持つサービスだけです。**

* **共有 anycast（Cloudflare など）では、1 つの IP が多数のゾーンを同居させます。** DNS で一致した名前は「その IP に載っている名前の 1 つ」でしかなく、**接続先がその名前だった証明にはなりません**
* **同じ理由で TLS SAN も効きません。** SNI 無しでは証明書を返さず、SNI を指定すれば**指定した名前の証明書が返ってくるだけ**です。こちらの推測を追認する装置になります
* **逆に、同じホスト名が複数の IP を返し、そのうち 1 つにしか接続していない**こともあります（`auth.openai.com` の実例）

**したがって CDN 上の宛先は、名前を「特定した」ではなく「候補まで絞った」と扱ってください。** 確定させる手段は 1 つだけです。

**候補を `allowDomains` に入れて `enforce` で動かし、目的の操作が通ることを確かめる。** 通れば候補は十分だったと言えます。落ちれば、そのとき積まれた記録が次の候補です。**実測 → 候補 → `enforce` で確認、までを 1 周と考えてください。**

> **この手順自体、まだ改善の余地があります。** L7 の可視性が無い以上、L3/L4 の記録から名前を復元する作業には原理的な限界があります（[`spec.md`](./spec.md) §10.1 の proxy 移行で消える種類の問題です）。**新しい当て方を見つけたらこの節に足してください。**

> **手順 2 は記録を汚染します。** `openssl` の接続自体が `egress-audit-v4` に記録されます。既に記録済みの IP を叩いた場合も、その **`timeout` がリセットされて挿入時刻の情報が失われます。** 名前解決は別のコンテナで行うか、**記録を読み終えてから**行ってください。

### 5. 記録機構が生きていることを確かめる

「何も出ていない」が「接触が無かった」なのか「記録が壊れている」なのかを区別できません。**allowlist に無いホストへ意図的に接続し、それが記録されることを確認してください。**

```sh
curl -sS -o /dev/null -w '%{remote_ip}\n' https://example.com/
```

`audit` では接続は成功します。出力された IP が記録に現れれば、機構は動いています。

> `example.com` は自己検証の未許可先プローブにも使われますが、**そのプローブは `audit` ではスキップされます**（[`spec.md`](./spec.md) §5）。`audit` 中に現れた `example.com` は自分で叩いたものです。

## 何を許可し、何を許可しないか

観測された宛先を機械的に allowlist へ写さないでください。**性質ごとに扱いが違います。**

| 性質 | 例 | 扱い |
|---|---|---|
| **その道具が動くために要る** | `api.anthropic.com` | バンドルに入れる |
| **更新チャネル** | `downloads.claude.ai` | **選べるようにする。** 下記参照 |
| **テレメトリ・ログ・feature flag** | Datadog、`sentry.io`、`statsig.com` | **入れない。** 失敗しても動作は続く。allowlist に載せた宛先はそのまま漏洩先になる |
| **自己検証のプローブ** | `8.8.8.8`、`example.com` | 無視する。このスクリプト自身が出したもの |
| **起動後セットアップ** | `deb.debian.org` | **allowlist では解けない**（[`spec.md`](./spec.md) §9.7）。イメージビルド時に移すか、`audit` の窓で行う |
| **個人の後付けセットアップ** | 同上 | プロジェクトの設定に混ぜない |

**更新チャネルには判断が要ります。** 遮断すると道具は動き続けますが、更新されないまま古いバージョンに固定されます。

* **固定したい側の理由** — 再現性。このパッケージ自身の設計原則（「すべての変更はイメージ再ビルドを経由する」。[`spec.md`](./spec.md) §11 の I1）とも揃います。バージョン依存の不具合を追っているとき、環境が勝手に動くと切り分けになりません
* **最新を使いたい側の理由** — 修正が届かない。更新の失敗が無音なら、古いまま気づかないことになります

**どちらが正しいということはないので、バンドルを分けて選べるようにしています。**

## 実測記録

### 2026-08-04（UTC）— 初版バンドルの検証

**環境:** Docker Desktop / macOS arm64、`mode: "audit"`、`profile: ["anthropic", "npm", "vscode", "github"]`、Claude Code v2.1.221

**観測窓:** コンテナ起動から約 30 分。Claude Code での対話作業（ファイル編集、テスト実行、git 操作）。**エラーは発生させていません。**

| 観測された IP | 特定結果 | 特定方法 | 判断 |
|---|---|---|---|
| `8.8.8.8` | 自己検証の外部 DNS プローブ | 既知 | 無視 |
| `199.232.162.132` | `deb.debian.org`（Fastly） | DNS 一致 | 個人セットアップ。対象外 |
| `34.149.66.165` | `*.logs.us5.datadoghq.com` | TLS SAN | **入れない**（テレメトリ。送信元は未特定） |
| `35.190.46.17` | `downloads.claude.ai` / `downloads.claude.com` | TLS SAN | `anthropic-updates` バンドルとして追加 |
| `172.66.147.243` | `example.com` | 自分で叩いた | 記録機構の動作確認 |

**観測されなかったもの:** `sentry.io`、`statsig.com`。初版バンドルに入っていた 2 件です。

**留保:** 窓が短く、エラーを発生させていません。`sentry.io` はエラー送信なので出なくて当然です。`statsig.com` はホームに残ったキャッシュが効いていた可能性があります。**「不要」と結論づけるにはこの観測だけでは足りません。** それでも、無条件に許可し続ける根拠にはならないと判断してバンドルから外しました。

**分かったこと:** 元の 13 ドメインには Datadog も `downloads.claude.ai` も入っていませんでした。**リストをそのまま写していたら、この 2 つは見えないまま塞がっていました。**

**Datadog の送信元は特定できていません。** 観測したのは「コンテナ内の誰かが Datadog のログ収集エンドポイントへ継続的に送っている」ことだけです。Claude Code 本体とは限らず、**この環境に後から入ったリモート接続のブートストラップである可能性があります**（同じ窓で `openssh-server` などの起動後 apt が走っています）。**送信元を特定していない宛先をパッケージのバンドルに入れてはいけません。** 誰の都合か分からないものを全利用者に配ることになります。

これは実測一般の注意でもあります。**「観測された」は「その道具が必要としている」ではありません。** コンテナには複数の主体が同居します。

#### `downloads.claude.ai` の扱い

`anthropic` バンドルには入れず、**`anthropic-updates` として独立したバンドル**にしました。

* 遮断しても Claude Code は動き続けます。**失敗は無音ではなく、コンソールにエラーメッセージが出ます**（利用者による観察）。気づかないまま古いバージョンで使い続ける、という形にはなりません
* バージョンを固定したい利用者がいます。再現性のため、バージョン依存の不具合を追うため、組織のツール承認プロセスのため。**このリポジトリの `docs/` 自体、「Claude Code v2.1.221 で実測」のようにバージョンを添えた記録を持っています。** 測っている最中に自動更新が走れば、その記録は何のバージョンのものか分からなくなります
* 最新を使いたい利用者もいます。修正が届かないのは実害です

**どちらが正しいということはないので、バンドルを分けました。** 雛形（`templates/*.json`）には含めてあるので、既定の体験では更新が通ります。固定したい側は 1 語落とします。

### 2026-08-04（UTC）— `openai` バンドルの作成

**環境:** 同上。`codex` CLI v0.146.0。測定のため、それまで `allowDomains` に推測で書いていた `chatgpt.com` / `api.openai.com` / `auth.openai.com` を**外してから**再ビルドしました（許可されている宛先は記録されないため）。

| 操作 | 出現した IP | 一致したドメイン | 判断 |
|---|---|---|---|
| `codex login` | `172.64.146.15` | `auth.openai.com` | **バンドルに入れる** |
| `codex exec`（1 往復、read-only） | `172.64.155.209` | `chatgpt.com`（`ab.chatgpt.com` も同じ IP 対） | **バンドルに入れる** |
| 同上 | `172.64.144.52` | `web-sandbox.oaiusercontent.com` | **入れない。** 下記 |

**`api.openai.com` は観測されませんでした。** 推測で書いていた 3 つのうち、実際に使われたのは 2 つです。API キー経路は測っていないため、バンドルには入れていません。

**`172.64.144.52` を入れなかった理由。** DNS では `web-sandbox.oaiusercontent.com` と一致しますが、**Cloudflare の共有 anycast なので一致は証明になりません**（上記「CDN 上では決定的にならない」）。このホスト名は ChatGPT 側の機能（ChatGPT 内で動くアプリのサンドボックス）で使われるもので、**`codex` が使うかどうかは分かっていません。** 単純な算術質問への応答という操作内容とも噛み合いません。**用途を説明できない宛先はバンドルに入れない**という基準を適用しました。

**未解決として残します。** `openai` バンドルを `enforce` で使って `codex` が動けば、この宛先は codex の依存ではなかったと確定します。落ちたらそのとき積まれる記録が答えです。

## バンドルを測り直すとき

* **利用者から「入れてあるのに通らない」と言われたとき** — エンドポイントが移った可能性があります
* **対象製品のメジャーバージョンが上がったとき** — 送信先が変わります（Datadog がその実例です）
* **少なくとも年に一度**

測り直したら、この文書の「実測記録」に追記してください。**観測窓の長さと、その間に何をしたかを必ず書いてください。** それが無い記録は、後から信頼度を判断できません。
