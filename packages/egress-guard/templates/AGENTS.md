## このコンテナは egress 規制下にある

このリポジトリの開発環境は
[`@himorogy/egress-guard`](https://www.npmjs.com/package/@himorogy/egress-guard)
による allowlist ベースの egress ファイアウォールの下で動く。**allowlist に無い宛先への外向き通信は遮断される。**

**遮断は故障ではなく設計である。** 目的は、プロンプトインジェクションやエージェントの暴走が起きたときに、秘密やソースコードを書き出せる先を限定することにある。想定している敵は**このコンテナの中で動くエージェント自身**、つまりあなたである。

したがって次の 2 つを守ること。

* 遮断をネットワーク障害・DNS 障害・プロキシ設定の不備と診断しない
* 遮断を自力で迂回しようとしない（詳細は[やってはいけないこと](#やってはいけないこと)）

---

## 遮断はどう見えるか

| 状況 | 現れ方 |
|---|---|
| 許可されていないホストへの TCP 接続（`enforce`） | ICMP `admin-prohibited` による即時の接続失敗。クライアント側では `No route to host` などになる。**ハングやタイムアウトではなく即座に落ちる** |
| 割り当てられたリゾルバ以外への DNS 問い合わせ（`dig @8.8.8.8` など） | 無応答（DROP）。応答待ちのタイムアウトになる |
| IPv6 での外向き通信 | ICMP6 `adm-prohibited` による即時の失敗。IPv6 は全モードで拒否される |
| WebFetch（許可されていないドメイン） | **失敗し、出力が返らない。** Anthropic 側の取得へフォールバックすることはない |

**名前解決が成功しても、そのドメインが許可されているとは限らない。** 許可されたリゾルバは再帰問い合わせを行うため、任意のドメインの `dig` は通る。遮断されるのはその後の接続である。**`dig` が引けたことを「許可されている」の根拠にしないこと。**

### 遮断かどうかの切り分け

`api.anthropic.com` と `github.com` は常に許可されている（[基底プロファイル](#常に許可されているもの基底プロファイル)）。この 2 つに到達できて目的のホストにだけ到達できないなら、それは egress-guard による遮断であって、ネットワーク障害ではない。

```sh
curl -sS -o /dev/null --connect-timeout 5 https://api.anthropic.com/   # 通るはず
curl -sS -o /dev/null --connect-timeout 5 https://<目的のホスト>/       # ここだけ落ちるなら遮断
```

## あなたにできること・できないこと

### できること

* **実効設定を読む** — `/etc/egress-guard/firewall.json` は root 所有で書き換えられないが、既定の手順どおり配置されていれば（`644`）読める。現在のモードと許可ドメインはここで確認できる

  ```sh
  cat /etc/egress-guard/firewall.json
  ```

* **設定ファイルの妥当性を検証する** — 非特権で実行できる。書き換えを提案する前に、その JSON が受理されるかを確かめられる

  ```sh
  /usr/local/bin/init-project-firewall.sh --check-config --config <検証したいファイル>
  ```

* **ポリシーを再適用する** — sudoers で許可されている。何度実行しても同じ結果になる（冪等）

  ```sh
  sudo /usr/local/bin/init-project-firewall.sh
  ```

  **これは意図された設計である。** 再適用が行うのは root 所有の実効設定の**再解決**だけで、ポリシーそのものは変えられない。allowlist は起動時に解決した IP の集合なので、**CDN のアドレスが動いて「許可されているはずのドメイン」に到達できなくなった場合はこれで回復する。** 遮断に当たったとき、あなたが自分で試してよい復旧手段はこれだけである。

### できないこと

* **ポリシーを変えること。** 効力を持つのは `/etc/egress-guard/firewall.json` だけで、これは root 所有である。あなたには書き換えられない
* **リポジトリ側の設定ファイルを直して直すこと。**
  <!-- 記入欄: リポジトリ側のコピーのパス。既定は .devcontainer/firewall.json -->
  リポジトリ内の `.devcontainer/firewall.json` は**ソースにすぎない**。ここを編集しても、**イメージを再ビルドするまで一切反映されない。** 編集しただけで「直った」と報告してはならない
* **遮断された宛先の一覧を読むこと。** 記録先の ipset `egress-audit-v4` を読むには root が必要で、あなたには権限がない。必要なら人間に依頼すること

**まとめると、遮断に自分で対処する手段は「再適用を 1 回試す」以外に無い。** それで直らなければ人間の操作が要る。

## 遮断に当たったときの手順

1. 上の[切り分け](#遮断かどうかの切り分け)で、egress-guard による遮断であることを確かめる
2. `/etc/egress-guard/firewall.json` を読み、目的のホストが既に許可されているかを確認する
3. **既に許可されているのに落ちる場合** — CDN のアドレス変動の可能性がある。`sudo /usr/local/bin/init-project-firewall.sh` を 1 回実行して再試行する
4. **許可されていない場合** — 作業を止めて人間に報告する。**勝手に迂回しない**

報告には次を含めること。

* **必要なホスト名**（ワイルドカードではなく具体名。IP ではなく名前）
* **何をするために必要か**（どのコマンド・どのツールが、どの工程で使うか）
* **代替手段の有無** — 特に、その取得を**イメージビルド時に移せないか**。egress-guard は `postStartCommand` で適用されるため、**起動後に外部から何かを取ってくる作業は原理的に不利である。** ビルド時に移せるなら、それが第一選択になる
* 遮断を確認したコマンドとその出力

報告の雛形:

> `<ホスト名>` への接続が遮断されました（`<コマンド>` が `<エラー>` で失敗）。
> `<用途>` に必要です。再適用は試しましたが変わりませんでした。
> allowlist への追加が必要か、あるいはこの取得をイメージビルド時に移すのが適切か、判断をお願いします。

## やってはいけないこと

いずれも**遮断の回避**にあたる。ファイアウォールが防ごうとしていることを、あなたが内側から無効化する行為である。

* プロキシ・トンネル・VPN・リバースシェルを立てる、あるいはそれらを提案・設定する
* 許可済みのホストを踏み台にして別の宛先の内容を取ってくる
* DNS クエリに情報を載せて外へ出す
* 別の CDN・ミラー・第三者のプロキシサービスなど、**allowlist を通る経路を探して回る**
* `mode` を `audit` に変える、あるいは変えるよう促す
* `/etc/egress-guard/` 以下、`/usr/local/bin/init-project-firewall.sh`、sudoers を書き換えようとする
* リポジトリ側の `firewall.json` を編集して「修正した」と報告する（**再ビルドまで反映されない**）
* 遮断を「一時的なネットワーク障害」として報告し、リトライを繰り返す

## Web 検索と Web 取得

Claude Code の 2 つの Web ツールは、egress から見て性質が違う。**2026-08-03 に Claude Code v2.1.220 で実測した結果である。**

| ツール | コンテナからの egress | 使えるか |
|---|---|---|
| **WebSearch** | 検索実行中、コンテナから外部への新規接続は観測されなかった（Anthropic 側で完結する） | **追加設定なしで使える** |
| **WebFetch** | コンテナ内の `claude` プロセスが**取得先ドメインへ直接 TCP 443 を張る** | **`allowDomains` に入っているドメインだけ** |
| `curl` などの自前の取得 | そのドメインへ直接 | `allowDomains` に入っているドメインだけ |

**したがって調査の起点は WebSearch にすること。** 追加設定が要らず、遮断にも当たらない。

**WebFetch が失敗したら、それはドメインが allowlist に無いということである。** 別の URL を次々に試すのではなく、[遮断に当たったときの手順](#遮断に当たったときの手順)に従って人間に伝えること。

> WebFetch の取得内容は、ふつう小型モデルの要約を経由する。ただし Claude Code が事前承認している 91 のドキュメントドメインでは要約がバイパスされ、**原文がそのままコンテキストに入る。** そのドメインが侵害されていれば prompt injection の緩衝材は無い。

## 常に許可されているもの（基底プロファイル）

プロジェクト設定によらず、スクリプトに埋め込まれた次のドメインは常に許可される。**これで足りる作業は遮断に当たらない。**

| 用途 | ドメイン |
|---|---|
| Anthropic API | `api.anthropic.com`、`console.anthropic.com` |
| （用途はスクリプトに明記されていない） | `sentry.io`、`statsig.com` |
| npm レジストリ | `registry.npmjs.org` |
| VS Code | `marketplace.visualstudio.com`、`vscode.blob.core.windows.net`、`update.code.visualstudio.com` |
| GitHub | `github.com`、`api.github.com`、`codeload.github.com`、`objects.githubusercontent.com`、`raw.githubusercontent.com` |

計 13 ドメイン。これに加えて GitHub meta API から取得した CIDR が許可される。

**注意が要るもの:**

* **上のリストに無いパッケージレジストリは通らない。** PyPI、crates.io、Docker Hub、`deb.debian.org` などは基底プロファイルに含まれていない
* **`nodejs.org` も含まれていない。** `node-gyp` によるヘッダ取得などはそのままでは失敗する
* **VS Code 拡張のインストールは、カタログが許可されていても失敗することがある。** 実体を配る CDN（`*.gallerycdn.vsassets.io`）は allowlist に載せる手段が無い既知の問題である。**「`marketplace.visualstudio.com` が入っているのに拡張が入らない」という形で現れる。** 迂回を試みず、拡張はイメージビルド時に入れてもらうこと

## 設定の書き方（追加を提案するとき）

人間から「必要なドメインを `firewall.json` に足す変更を出してほしい」と頼まれた場合に限り、リポジトリ側のコピーを編集する。**編集しただけでは反映されない**ことは、必ず添えて報告すること。

```json
{
	"version": 1,
	"profile": "default",
	"mode": "enforce",
	"allowDomains": ["registry.example.com"],
	"allowCidrs": ["203.0.113.0/24"],
	"allowHostPorts": [5432],
	"sshdPort": 22
}
```

守るべき制約:

* **フィールドは上の 7 つだけ。** 未知のキーがあると設定全体が拒否され、コンテナは panic テーブル（loopback 以外すべて遮断）で起動する
* **JSON にコメントは書けない。** `jq` でパースするため、JSON5 / JSONC は不正な JSON として拒否される
* **ワイルドカードは書けない**（`*.example.com` は拒否される）。必要なホスト名を具体的に列挙する
* **私設アドレス帯の CIDR は書けない** — RFC1918、CGNAT（`100.64.0.0/10`）、loopback、link-local、multicast / 予約。`0.0.0.0/0` やプレフィックス長 8 未満も拒否される
* `169.254.169.254`（クラウドのメタデータサービス）は link-local なので**許可できない。遮断されているのが正しい状態である**
* 書いたら `--check-config --config <パス>` で検証してから出すこと

**`firewall.json` は PR レビュー必須ファイルとして扱われる。** 許可先を増やす提案は、増やす理由を添えること。
