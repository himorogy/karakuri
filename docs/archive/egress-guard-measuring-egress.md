# 宛先の実測とバンドルの保守

**このパッケージが埋め込んでいるドメインは、実測しないと正しさを保てません。** 基底プロファイル（[`spec.md`](./spec.md) §3.3）のバンドルは他社製品のエンドポイントを列挙したものであり、**製品側の都合で動きます。** 一度書いたら終わりではなく、定期的に測り直す対象です。

この文書は、その測り方と判断基準をまとめたものです。プロジェクト固有の `allowDomains` を決めるときにも同じ手順が使えます。

---

## なぜ実測が要るか

初版の基底プロファイルは [claude-code の devcontainer](https://github.com/anthropics/claude-code/blob/main/.devcontainer/init-firewall.sh) にある 13 ドメインをそのまま持ってきたものでした。**2026-08-04 に実測したところ、この 13 件は既に現実と合っていませんでした。**

* **入っているのに使われていないもの** — `sentry.io`、`statsig.com`、`console.anthropic.com`。実測でも観測されず、`claude` の実行ファイル（v2.1.221）にも文字列として存在しませんでした。**13 件のうち 3 件です**
* **使われているのに入っていないもの** — Datadog のログ収集エンドポイントと `downloads.claude.ai` が観測されました

**リストを信じて写した場合、この 2 種類のずれはどちらも見えません。** 前者は allowlist を無駄に広げ、後者は「入れたはずなのに動かない」として現れます。

## 測り方

### 1. `audit` で起動する

`firewall.json` を `mode: "audit"` にして**イメージを再ビルド**します。

**再接続では駄目です。** 実効設定は `/etc/egress-guard/firewall.json` で、そこへ配置されるのはイメージビルド時だけです。加えて、**測りたい対象がホームディレクトリに残っていると再インストールが走らず、その通信が観測できません。**

#### `enforce` で代用しない

記録自体は両モードで行われます。それでも収集は `audit` で行ってください。理由が 2 つあります。

* **`enforce` では依存の連鎖が途中で切れます。** ドメイン A に接続してから、その応答をもとに B へ接続する、という処理は珍しくありません。A が遮断されるとそこで止まり、**B への接続はそもそも試行されないため記録にも残りません。** A を許可して再実行するまで B の存在は分かりません。**必要な宛先を一度に洗い出せるのは `audit` だけです**
* **`enforce` で「動いているように見える」ことは、必要でなかったことの証明になりません。** テレメトリやログ送信のように、失敗しても呼び出し側が黙って続行する通信があります。feature flag のように、遮断された結果として**静かに挙動が変わる**ものもあります。遮断して支障が出るかどうかを目で見て確かめる方法では、この種の依存を取りこぼします

設計上の位置づけは [`design.md`](./design.md) §2.11。

### 2. 測りたい操作を一通り行う

**観測窓の長さがそのまま結果の信頼度になります。** 短い窓では、次のものが漏れます。

* **起動時にしか出ない通信** — 一度キャッシュされると再取得されないもの（feature flag など）
* **異常時にしか出ない通信** — エラー送信など
* **定期的にしか出ない通信** — 更新確認など

「観測されなかった」は「使われていない」ではありません。**窓の長さと、その間に何をしたかを記録に残してください。**

### 3. 記録を読む

allowlist を通らなかった宛先 IP が ipset `egress-audit-v4` に自動で溜まります。**`enforce` / `audit` の両モードで記録されます。** 読むには root が要ります。

```sh
# ホストから。コンテナの取り違えに注意（[`../README.md`](../README.md)「適用されているか確かめる」）
docker exec -u root <container> ipset list egress-audit-v4
```

```
Name: egress-audit-v4
Type: hash:ip
Members:
93.184.216.34 timeout 603412
104.16.132.229 timeout 604233
```

**`timeout` の残量が新旧の順序です。** 残量が大きいほど後に追加されたものです。上限は 604800（7 日）なので、`604800 - 残量` が経過秒数になります。**`--exist` で再追加されると残量がリセットされる**ため、これは「最後に接触した時刻」です。

**割り当てられたリゾルバ以外への 53 番宛（＝ DNS トンネリングの試行）もここに記録されます。** DNS の DROP は allowlist より前段にあるため、専用の記録ルールを置いています。

#### コンテナを取り違えていないか

`shutdownAction: none` を使っていると、他プロジェクトの devcontainer が同時に動いたままになります。**`docker ps` でコンテナ ID を確かめてから読んでください。**

**取り違えは時刻で気づけます。** `追加時刻 = 現在 - (604800 - 残量)` で逆算し、**コンテナの起動時刻より前のエントリが混ざっていたら、それは別のコンテナの記録です。**

**もう 1 つ、モードでも判別できます。** `example.com` と `8.8.8.8` が 2 秒差で並んでいたら、それは自己検証（未許可ホストの到達確認と外部 DNS の確認。[`spec.md`](./spec.md) §5）です。**`audit` では前者がスキップされるため、この組が出ていればそのコンテナは `enforce` で動いています。**

**エントリは 7 日で自動的に消えます。** set はスクリプトを再実行しても**作り直されません**（蓄積が目的のため）。測定を始める前に空にしたい場合:

```sh
ipset flush egress-audit-v4
```

> `169.254.169.254`（クラウドのメタデータサービス）のような link-local アドレスが記録されることがあります。これらは `FORBIDDEN_CIDRS` に含まれるため `firewall.json` では許可できません。**遮断されているのが正しい状態です。**

> `SET` ターゲットが使えないカーネルでは、この記録ルールを外した構成に自動でフォールバックします。その場合は起動ログに `retrying without the blocked-destination recorder` が出ます。**そのカーネルでは、この文書の手順は使えません。**

#### カーネルログは当てにしない

`fw-drop:` / `fw-audit:` / `fw-dns-drop:` / `fw-drop6:` の `LOG` ルールも入っていますが、**多くの環境では出力されません**（コンテナ内の `dmesg` は `CAP_SYSLOG` が無く読めない。`net.netfilter.nf_log_all_netns` が既定 `0` のためホストからも読めない）。**測定の前提にしないでください。** 経緯と却下した回避策は [`design.md`](./design.md) §2.11。

### 4. IP を名前に戻す

**逆引きから始めないでください。** CDN やクラウドのロードバランサは PTR を持たないか、`*.bc.googleusercontent.com` のような事業者名しか返しません。

**順序はこうです。**

1. **候補ドメインを解決して突き合わせる。** 心当たりのあるドメインを `dig +short` し、記録された IP と一致するか見ます。**ネットワークに何も足さない**ので、これを最初に試します

   ```sh
   dig +short statsig.com sentry.io deb.debian.org
   ```

2. **一致しなければ TLS 証明書の SAN を見る。**

   ```sh
   echo | openssl s_client -connect 35.190.46.17:443 2>/dev/null \
     | openssl x509 -noout -subject -ext subjectAltName
   ```

   専用のアドレスを持つサービスでは、これが決定的です（`downloads.claude.ai` と Datadog はこれで確定しました）

### どちらの方法も CDN 上では決定的にならない

**1 つの IP が 1 つのホスト名に対応するのは、専用アドレスを持つサービスだけです。**

* **共有 anycast（Cloudflare など）では、1 つの IP が多数のゾーンを同居させます。** DNS で一致した名前は「その IP に載っている名前の 1 つ」でしかなく、**接続先がその名前だった証明にはなりません**
* **同じ理由で TLS SAN も効きません。** SNI 無しでは証明書を返さず、SNI を指定すれば**指定した名前の証明書が返ってくるだけ**です。こちらの推測を追認する装置になります
* **逆に、同じホスト名が複数の IP を返し、そのうち 1 つにしか接続していない**こともあります（`auth.openai.com` の実例）

**したがって CDN 上の宛先は、名前を「特定した」ではなく「候補まで絞った」と扱ってください。** 確定させる手段は 1 つだけです。

**候補を `allowDomains` に入れて `enforce` で動かし、目的の操作が通ることを確かめる。** 通れば候補は十分だったと言えます。落ちれば、そのとき積まれた記録が次の候補です。**実測 → 候補 → `enforce` で確認、までを 1 周と考えてください。**

### 実行ファイルの文字列を読む

**手元にバイナリがあるなら、これがいちばん強い方法です。** 送信元の候補になるプログラムから、埋め込まれたホスト名を直接抜きます。

```sh
strings -a "$(readlink -f "$(command -v claude)")" \
  | grep -oE '[a-z0-9.-]+\.(anthropic\.com|claude\.ai|datadoghq\.com)' | sort -u
```

**CDN の同居問題を受けません。** 名前がそこに書いてあるかどうかを見ているので、アドレスの共有は関係ありません。

**まだ接触していない宛先まで列挙できます。** `audit` の観測は「その窓で起きたこと」しか映しませんが、文字列は使われうる宛先の候補を先に見せます。

**「無い」と言えるのが最大の利点です。** 観測されなかったことは不要である証明になりませんが、**実行ファイルに存在しないことは、そのバージョンが使わないことのかなり強い根拠になります。** `sentry.io` と `statsig.com` をバンドルから外した判断は、これで裏が取れました。

**留保:**

* **在ることは、使われることを意味しません。** デッドコード、staging 用（実際に `api-staging.anthropic.com` が入っています）、feature gate で到達しない経路が混ざります
* **動的に組み立てている名前は出ません。** `"console." + domain` のような形は文字列としては現れません
* **ローカルにバイナリがある場合しか使えません。** 相手がリモートのサービスなら手が出ません

**`audit` の実測と組み合わせてください。** 文字列で候補を列挙し、実測で実際に使われるものを絞り、`enforce` で足りることを確かめる。**この 3 つで、どれか 1 つでは届かないところまで詰められます。**

> **この手順自体、まだ改善の余地があります。** L7 の可視性が無い以上、L3/L4 の記録から名前を復元する作業には原理的な限界があります（[`spec.md`](./spec.md) §10.1 の proxy 移行で消える種類の問題です）。**新しい当て方を見つけたらこの節に足してください。** 上の「実行ファイルの文字列を読む」は、そうやって後から足したものです。

> **手順 2 は記録を汚染します。** `openssl` の接続自体が `egress-audit-v4` に記録されます。既に記録済みの IP を叩いた場合も、その **`timeout` がリセットされて挿入時刻の情報が失われます。** 名前解決は別のコンテナで行うか、**記録を読み終えてから**行ってください。
>
> **実際に踏みました。** 別のコンテナから取った 17 件の IP を `openssl` で順に叩き、**その 17 件すべてを自分のコンテナの記録に書き込みました。** 下記の時刻の逆算で切り分けられますが、最初からやらないほうが速く済みます。

### 5. 記録機構が生きていることを確かめる

「何も出ていない」が「接触が無かった」なのか「記録が壊れている」なのかを区別できません。**allowlist に無いホストへ意図的に接続し、それが記録されることを確認してください。**

```sh
curl -sS -o /dev/null -w '%{remote_ip}\n' https://example.com/
```

`audit` では接続は成功します。出力された IP が記録に現れれば、機構は動いています。

> `example.com` は自己検証の未許可先プローブにも使われますが、**そのプローブは `audit` ではスキップされます**（[`spec.md`](./spec.md) §5）。`audit` 中に現れた `example.com` は自分で叩いたものです。逆に `enforce` では自己検証が入れるので、上記「コンテナを取り違えていないか」の判別材料になります。

## 何を許可し、何を許可しないか

観測された宛先を機械的に allowlist へ写さないでください。**性質ごとに扱いが違います。**

| 性質 | 例 | 扱い |
|---|---|---|
| **その道具が動くために要る** | `api.anthropic.com` | バンドルに入れる |
| **更新チャネル** | `downloads.claude.ai` | **選べるようにする。** 下記参照 |
| **テレメトリ・ログ・feature flag** | Datadog、`sentry.io`、`statsig.com` | **入れない。** 失敗しても動作は続く。allowlist に載せた宛先はそのまま漏洩先になる |
| **自己検証のプローブ** | `8.8.8.8`、`example.com` | 無視する。このスクリプト自身が出したもの |
| **起動後セットアップ** | `deb.debian.org` | **allowlist では解けない**（[`spec.md`](./spec.md) §9.7）。イメージビルド時に移すか、`audit` の窓で行う |
| **個人の後付けセットアップ** | 同上 | プロジェクトの設定に混ぜない |

**更新チャネルには判断が要ります。** 遮断すると道具は動き続けますが、更新されないまま古いバージョンに固定されます。

* **固定したい側の理由** — 再現性。このパッケージ自身の設計原則（「すべての変更はイメージ再ビルドを経由する」。[`spec.md`](./spec.md) §11 の I1）とも揃います。バージョン依存の不具合を追っているとき、環境が勝手に動くと切り分けになりません
* **最新を使いたい側の理由** — 修正が届かない。更新の失敗が無音なら、古いまま気づかないことになります

**どちらが正しいということはないので、バンドルを分けて選べるようにしています。**

## 実測記録

### 2026-08-04（UTC）— 初版バンドルの検証

**環境:** Docker Desktop / macOS arm64、`mode: "audit"`、`profile: ["anthropic", "npm", "vscode", "github"]`、Claude Code v2.1.221

**観測窓:** コンテナ起動から約 30 分。Claude Code での対話作業（ファイル編集、テスト実行、git 操作）。**エラーは発生させていません。**

| 観測された IP | 特定結果 | 特定方法 | 判断 |
|---|---|---|---|
| `8.8.8.8` | 自己検証の外部 DNS プローブ | 既知 | 無視 |
| `199.232.162.132` | `deb.debian.org`（Fastly） | DNS 一致 | 個人セットアップ。対象外 |
| `34.149.66.165` | `*.logs.us5.datadoghq.com` | TLS SAN | **入れない**（テレメトリ。送信元は未特定） |
| `35.190.46.17` | `downloads.claude.ai` / `downloads.claude.com` | TLS SAN | `anthropic-updates` バンドルとして追加 |
| `172.66.147.243` | `example.com` | 自分で叩いた | 記録機構の動作確認 |

**観測されなかったもの:** `sentry.io`、`statsig.com`。初版バンドルに入っていた 2 件です。

**留保:** 窓が短く、エラーを発生させていません。`sentry.io` はエラー送信なので出なくて当然です。`statsig.com` はホームに残ったキャッシュが効いていた可能性があります。**「不要」と結論づけるにはこの観測だけでは足りません。** それでも、無条件に許可し続ける根拠にはならないと判断してバンドルから外しました。

**分かったこと:** 元の 13 ドメインには Datadog も `downloads.claude.ai` も入っていませんでした。**リストをそのまま写していたら、この 2 つは見えないまま塞がっていました。**

**Datadog の送信元は、この時点では特定できていませんでした。** 観測したのは「コンテナ内の誰かが Datadog のログ収集エンドポイントへ継続的に送っている」ことだけです。コンテナには複数の主体が同居します（同じ窓でリモート接続のブートストラップが `openssh-server` などを入れていました）。**送信元を特定していない宛先をパッケージのバンドルに入れてはいけません。** 誰の都合か分からないものを全利用者に配ることになります。

**後日、実行ファイルの文字列から Claude Code 本体だと確定しました**（下記「2026-08-04 — 実行ファイルの走査」）。**入れないという判断は変えていません。** 送信元が分かってもテレメトリであることは変わらないためです。

これは実測一般の注意でもあります。**「観測された」は「その道具が必要としている」ではありません。**

#### `downloads.claude.ai` の扱い

`anthropic` バンドルには入れず、**`anthropic-updates` として独立したバンドル**にしました。

* 遮断しても Claude Code は動き続けます。**失敗は無音ではなく、コンソールにエラーメッセージが出ます**（利用者による観察）。気づかないまま古いバージョンで使い続ける、という形にはなりません
* バージョンを固定したい利用者がいます。再現性のため、バージョン依存の不具合を追うため、組織のツール承認プロセスのため。**このリポジトリの `docs/` 自体、「Claude Code v2.1.221 で実測」のようにバージョンを添えた記録を持っています。** 測っている最中に自動更新が走れば、その記録は何のバージョンのものか分からなくなります
* 最新を使いたい利用者もいます。修正が届かないのは実害です

**どちらが正しいということはないので、バンドルを分けました。** 雛形（`templates/*.json`）には含めてあるので、既定の体験では更新が通ります。固定したい側は 1 語落とします。

### 2026-08-04（UTC）— `openai` バンドルの作成

**環境:** 同上。`codex` CLI v0.146.0。測定のため、それまで `allowDomains` に推測で書いていた `chatgpt.com` / `api.openai.com` / `auth.openai.com` を**外してから**再ビルドしました（許可されている宛先は記録されないため）。

| 操作 | 出現した IP | 一致したドメイン | 判断 |
|---|---|---|---|
| `codex login` | `172.64.146.15` | `auth.openai.com` | **バンドルに入れる** |
| `codex exec`（1 往復、read-only） | `172.64.155.209` | `chatgpt.com`（`ab.chatgpt.com` も同じ IP 対） | **バンドルに入れる** |
| 同上 | `172.64.144.52` | `web-sandbox.oaiusercontent.com` | **入れない。** 下記 |

**`api.openai.com` は観測されませんでした。** 推測で書いていた 3 つのうち、実際に使われたのは 2 つです。API キー経路は測っていないため、バンドルには入れていません。

**`172.64.144.52` を入れなかった理由。** DNS では `web-sandbox.oaiusercontent.com` と一致しますが、**Cloudflare の共有 anycast なので一致は証明になりません**（上記「CDN 上では決定的にならない」）。このホスト名は ChatGPT 側の機能（ChatGPT 内で動くアプリのサンドボックス）で使われるもので、**`codex` が使うかどうかは分かっていません。** 単純な算術質問への応答という操作内容とも噛み合いません。**用途を説明できない宛先はバンドルに入れない**という基準を適用しました。

#### `enforce` での確認（決着）

`openai` バンドルの 2 ドメインだけを許可した `enforce` のコンテナで、同じ操作（`codex exec --sandbox read-only` で 1 往復）が**成功しました。**

**`172.64.144.52` は codex の依存ではありませんでした。** 候補として挙がっただけの宛先を入れずに済んでいます。

**これが 1 周の完成形です。** `audit` で候補まで絞り、`enforce` で目的の操作が通ることを確かめる。**IP と名前の対応が曖昧なままでも、「この集合で仕事が回る」ことは確定できます。** CDN 上で名前を特定しきれない問題に対する、現実的な回答がこれです。

**この確認で測れていないもの:** ログインは既に済んでいたため、`enforce` 下でトークンを持たない状態からの `codex login` は通していません。`auth.openai.com` が十分であることは `audit` での観測に基づく判断のままです。

### 2026-08-04（UTC）— 実行ファイルの走査

`enforce` に切り替えたあと、Datadog への送信が遮断されながら継続していた（`egress-audit-v4` の当該エントリの `timeout` だけが再送のたびに戻る）ため、送信元を特定しました。

**方法:** `claude` の実行ファイル（v2.1.221、285 MB）と、同居しているリモート接続の `relay.js` を `strings` で走査。

| 調べた対象 | 結果 |
|---|---|
| `claude` バイナリ | `http-intake.logs.us5.datadoghq.com`、`api.datadoghq.com`、`browser-intake-us5-datadoghq.com` |
| リモート接続の `relay.js` | Datadog の文字列なし |

**送信元は Claude Code 本体です。** 観測した TLS SAN（`*.logs.us5.datadoghq.com`）と一致します。**それでもバンドルには入れません。** テレメトリであることは送信元が分かっても変わりません。`enforce` で遮断したまま Claude Code も codex も正常に動いています。

**同じ走査で、バンドルの不整合が見つかりました。**

| ドメイン | バイナリ中の出現回数 | 対応 |
|---|---|---|
| `api.anthropic.com` | 79 | そのまま |
| `downloads.claude.ai` | 8 | そのまま |
| `console.anthropic.com` | **0** | **`anthropic` バンドルから外した** |
| `downloads.claude.com` | 0 | **残した。** `downloads.claude.ai` と同じ IP（`35.190.46.17`）に解決されるため allowlist は変わらず、名前が移行したときの保険になる |
| `sentry.io` / `statsig.com` | **0** | 既に外してある。**「観測されなかった」ではなく「実行ファイルに存在しない」ことが分かった** |

`console.anthropic.com` は元の 13 ドメインから引き継いだだけで、`audit` でも一度も観測されていませんでした。**`anthropic` バンドルの定義（Claude Code を動かす最小構成）に合わないため外しました。** 結果として `anthropic` は `api.anthropic.com` の 1 ドメインです。

**この 3 件は、実測だけでは見つかりませんでした。** 使われないものは観測に現れないため、「出てこない」と「元から無い」の区別がつきません。**実行ファイルの走査はその区別をつけられます。**

## バンドルを測り直すとき

* **利用者から「入れてあるのに通らない」と言われたとき** — エンドポイントが移った可能性があります
* **対象製品のメジャーバージョンが上がったとき** — 送信先が変わります（`sentry.io` / `statsig.com` が消えて Datadog になったのがその実例です）
* **少なくとも年に一度**

**測り直しの入口は実行ファイルの走査にしてください。** `audit` の実測より安く、**使われなくなったドメインを見つけられるのはこちらだけです。** バンドルは放っておくと増える一方になります。

測り直したら、この文書の「実測記録」に追記してください。**観測窓の長さと、その間に何をしたかを必ず書いてください。** それが無い記録は、後から信頼度を判断できません。
