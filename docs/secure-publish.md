# 公開経路のセキュリティ

このリポジトリのパッケージが **npm レジストリへ届くまでの経路**と、その経路をどう守っているかの記録です。

| 文書 | 内容 |
|---|---|
| [`../SECURITY.md`](../SECURITY.md) | **脆弱性の報告方法** |
| この文書 | **公開経路の設計**（脅威モデル・信頼境界・ゲート・判断の根拠） |
| [`../packages/egress-guard/docs/design.md`](../packages/egress-guard/docs/design.md) | egress-guard 本体の設計判断 |
| [`../packages/egress-guard/docs/spec.md`](../packages/egress-guard/docs/spec.md) | egress-guard の規範記述 |

この文書は**公開されていることを前提に書いています**。経路の秘匿を防御力に数えていません。ここに書かれた設計を攻撃者が全て知っていても、経路は守られるべきものとして設計しています。

一方で、**承認権限を持つ人物の一覧、緊急時の復旧手順、npm organization の管理者構成**はここには書きません。これらは設計ではなく運用の詳細であり、公開しても検証の役に立たず、標的の絞り込みにだけ役立つためです。

## 1. 脅威モデル

### 1.1 守るもの

**利用者が `npm install` で受け取るバイトの完全性。**

このリポジトリのパッケージは、開発コンテナのファイアウォールと秘密管理という、それ自体がセキュリティ境界を構成するものです。汚染された版が公開されれば、利用者が守ろうとしていた境界がそのまま無効化されます。パッケージの改竄は、利用者の環境における特権実行に直結します。

守る対象を分解すると次の 3 つです。

1. **公開されるアーティファクトの内容** — git 上のソースと、レジストリ上の tarball が対応していること
2. **公開の意思決定** — 誰かが意図せずに、あるいは意図に反して公開できないこと
3. **出所の証明可能性** — 利用者が、自力で 1 と 2 を検証できること

3 は他の 2 つと性質が違います。1 と 2 をどれだけ厳格に運用しても、**外部からそれを確認する手段がなければ、利用者は公開者を信じるしかありません**。この非対称性を解消することが、公開経路を設計する動機の中心にあります。

### 1.2 敵

* **公開者の開発マシンで動く、悪意ある依存パッケージ** — `postinstall` を通じて認証情報を窃取し、公開者の権限で別の版を公開しようとするもの
* **CI 上で特権コンテキストを得ようとするコード** — ビルド時に取得される依存や、ワークフローが呼び出す第三者製 action
* **公開者のアカウントを奪った攻撃者** — GitHub または npm のいずれか一方の資格情報を得た状態
* **リポジトリへの書き込み権限を得た内部の誰か** — 権限を持つこと自体は正当だが、単独で公開まで到達できてはならない

egress-guard 本体の脅威モデル（[`design.md`](../packages/egress-guard/docs/design.md) §1）が「コンテナ内のエージェント」を敵に置いているのに対し、この文書の敵は**公開経路に触れる全ての実行環境と人間**です。

### 1.3 守らないもの

* **npm レジストリ自身の侵害** — レジストリが配信する内容を我々は制御できません
* **GitHub Actions の実行基盤の侵害** — OIDC の発行元を信頼する以上、ここは信頼の起点です
* **公開後の unpublish による復旧** — npm の unpublish には時間制限があり、公開は実質的に不可逆です。事後の取り消しではなく、公開前のゲートで防ぎます

## 2. 信頼境界

### 2.1 現行 — 手動公開

移行前の経路は、ローカルでビルドし、2 要素認証を通して `npm publish` する形です。

```
開発マシン ──ビルド──> dist ──npm publish (2FA)──> レジストリ
   ↑
   信頼の全てがここにある
```

この構成が持つ強みは明確です。**GitHub 側の権限が全て奪われても公開は起きません。** 公開には物理的に所持している 2 要素認証デバイスが必要で、これは GitHub の権限体系から完全に独立しています。信頼する第三者のコードもゼロです。

弱点も同じ場所にあります。**ビルドが開発マシンで起きるため、開発マシンが汚染されればその成果物がそのまま公開されます。** 2 要素認証は「誰が公開したか」を守りますが、「何を公開したか」は一切守りません。開発マシンは依存パッケージ・エディタ拡張・他プロジェクトを同居させており、使い捨ての CI ランナーより攻撃面が広い環境です。

加えて、手動公開では**出所の証明（provenance）を生成できません**。§1.1 の 3 番目が原理的に満たせない構成です。

### 2.2 移行先 — OIDC による短命資格情報

```
git tag ──> GitHub Actions ──> environment 承認 ──> OIDC ──> レジストリ
              ↑                    ↑                  ↑
        使い捨てランナー      人間のゲート      数分で失効する資格情報
        （ビルドはここ）
```

信頼の置き場所が、開発マシンから **GitHub の権限体系**へ移動します。長期間有効なトークンはどこにも保存されません。

この移動を「2 要素認証を捨てて自動化を取る」と理解すると誤ります。正しくは **2 要素認証の要素を npm から GitHub へ移し、加えてビルド環境の隔離と出所証明を得る**という交換です。

GitHub organization 側で二要素認証を必須化し、パスキー・セキュリティキー等のセキュアな方式のみを許可することで、物理的な要素は維持されます。さらに §3 の承認ゲートにより、公開には**タグを打った人物とは別の人間による承認操作**が必要になり、これも同じ認証を経ます。

### 2.3 前提条件

移行が成立するには、以下が全て揃っている必要があります。**一つでも欠けた状態の OIDC 公開は、手動公開より弱くなります。**

1. organization の二要素認証必須化と、セキュアな方式のみの許可
2. 公開ワークフローに対する environment の承認ゲート
3. `main` ブランチの保護と、ワークフロー定義に対するコードオーナー指定
4. 移行完了後の、旧来の自動公開用トークンの失効

特に 4 を怠ると経路が 2 本並存し、**攻撃面は減らずに増えます**。移行の最終ステップとして必須です。

## 3. 公開経路

### 3.1 手順

```
1. 変更 PR に .changeset/*.md を含めてマージ
2. ローカルで `pnpm changeset version` を実行
     → 各パッケージの version と CHANGELOG が生成される
3. その差分を PR としてレビュー・マージ
4. タグを打って push
     git tag @himorogy/egress-guard@0.1.0
     git push origin @himorogy/egress-guard@0.1.0
5. ワークフローが起動し、environment の承認待ちで停止
6. 承認者が内容を確認して承認
7. OIDC で短命の資格情報を取得し、公開
     provenance attestation が自動生成される
```

### 3.2 各ゲートが何を防ぐか

| ゲート | 防ぐもの |
|---|---|
| `main` のブランチ保護 | 単独の権限でソースを書き換えて公開に載せること |
| ワークフロー定義のコードオーナー保護 | 公開経路そのものの書き換え |
| タグ push | 日常操作の副作用による意図しない公開 |
| 公開タグの保護 | 公開済みの版を指すタグの削除・付け替え（§4.4） |
| environment の承認 | タグを打てる人間の単独判断による公開 |
| 依存スクリプトの無効化 | 特権コンテキストでの第三者コード実行（§4.3） |
| action の SHA 固定 | 上流のタグ移動による第三者コードの差し替え |
| 実行できる action の限定 | 許可していない第三者 action の混入 |

いずれも単独では突破されうるものとして扱い、**多層で構成することを前提にしています**。

## 4. 設計判断

### 4.1 なぜ変更のマージを公開の起点にしないのか

changesets には、バージョン更新用の PR を自動生成し、それがマージされた時点で公開まで実行する運用形態があります。これを採用しませんでした。

**公開が日常操作の副作用として発火するためです。** マージはリポジトリで最も頻繁に行われる操作であり、これを公開のトリガーにすると、うっかりマージが不可逆な公開に直結します。npm の公開は実質的に取り消せません（§1.3）。

また、この形態では公開ジョブの実行に第三者製の action へ特権コンテキストを渡すことになり、§1.2 の 2 番目の敵に対する面が増えます。

バージョン計算と CHANGELOG 生成という changesets の価値ある部分は、ローカルでの `changeset version` 実行によって得られます。**自動化する範囲を、公開の意思決定の手前で切っています。**

### 4.2 なぜタグ起点なのか

公開は、明示的で、日常操作から区別され、意図を要求する行為であるべきです。タグを打つ操作はこの 3 つを満たします。

タグと公開されたバージョンが 1 対 1 で対応することには、副次的な利点もあります。**タグが公開の原因であるため、「レジストリに存在するがタグがないバージョン」は経路外の公開を意味します**（§6）。公開の結果としてタグを生成する構成では、タグ生成だけが失敗した場合にも同じ状態になるため、この検知は成立しません。

### 4.3 なぜ公開ジョブで依存スクリプトを実行しないのか

公開ジョブの実行中、GitHub Actions は OIDC トークンを要求するための環境変数を保持しています。**この状態で任意のコードを実行すると、そのコードは自力でレジストリ宛の資格情報を取得し、正規の経路として公開できます。**

依存パッケージのインストールスクリプトは、まさにこの「任意のコード」です。2025 年に発生した一連の npm サプライチェーン攻撃が利用した経路でもあります。

したがって公開ジョブでは依存スクリプトを実行せず、ビルドが必要なパッケージについては、ビルドと公開をジョブとして分離し、成果物を受け渡す構成を取ります。**特権を持つジョブでは、第三者のコードを一切動かさない**ことが原則です。

### 4.4 タグの命名

```
@himorogy/enclave-env@0.2.2
@himorogy/egress-guard@0.1.0
```

monorepo では、どのパッケージのどのバージョンかがタグ名だけで一意に定まる必要があります。

単一パッケージ時代に付けられた `v0.2.0` `v0.2.1` の 2 つのタグは、**そのまま残します**。タグは特定時点への不変の参照であり、後から名前を変えることは履歴の書き換えにあたります。既にクローンされたリポジトリとの不整合も生みます。

公開すべきバージョンの判定にタグは使われないため、旧タグが残っていても経路に影響しません。

### 4.5 パッケージマネージャのバージョン固定

`pnpm` はバージョンを固定し、更新は意図的に行います。公開経路が依存するツールの版が、ビルド日時によって変わってはいけないためです。固定は `packageManager` フィールドで行い、CI もそこから解決します。

**2026-08-04 に 11.20.0 へ移行しました。** それ以前は 10 系に留めていました。11 系の初期に OIDC による公開が 404 で失敗する回帰があったためです（[pnpm/pnpm#11513](https://github.com/pnpm/pnpm/issues/11513)）。

その回帰の原因は、`actions/setup-node` が `registry-url` を指定されたときに `.npmrc` へ書く `_authToken=${NODE_AUTH_TOKEN}` を、pnpm 11 が未解決のままレジストリへ送っていたことです。10 系で問題にならなかったのは、`pnpm publish` が `npm publish` を呼び出しており、npm 側の OIDC 経路が処理していたためです。11 系で `pnpm publish` が npm CLI に依存しなくなったことで露出しました。

**この経路は元々その条件を踏みません。** §4.3 の方針により公開ジョブでは `registry-url` を指定しておらず、リポジトリに `.npmrc` も置いていません。加えて修正（[pnpm/pnpm#11526](https://github.com/pnpm/pnpm/pull/11526)）は 11.20.0 に含まれています。

移行にあたって実際に影響したのは別の既定変更で、`strictDepBuilds` が既定で有効になったことです。判断の書かれていない依存のビルドスクリプトが残っていると `pnpm install` が失敗します。可否は `pnpm-workspace.yaml` の `allowBuilds` に明示しています。**公開ジョブは `--ignore-scripts` を付けているため、この変更の影響を受けません。**

### 4.6 許可する action の範囲

ワークフローが実行できる action を、リポジトリ設定で次に限定しています（§3.2 のゲート）。

* `himorogy` が所有するもの
* GitHub が作成したもの（`actions/*`）
* `pnpm/action-setup@*`
* `docker/setup-qemu-action@*`、`docker/setup-buildx-action@*`、`docker/login-action@*`、`docker/metadata-action@*`、`docker/build-push-action@*`

**`docker/*` の 5 つは、devcontainer ベースイメージのマルチアーキビルドのために追加したものです。** このビルドは npm への公開経路ではありませんが、GHCR へ push するジョブが `packages: write` を持つため、同じ性質の問題を抱えます。

**これは §4.3 の「特権を持つジョブでは第三者のコードを一切動かさない」という原則からの逸脱です。** 逸脱であることを承知のうえで、次の理由から受け入れています。

* 公開されるベースイメージは、それ自体が egress-guard を含むセキュリティ境界の一部であり、汚染されれば利用側の防御が無効化される。したがって守る価値は npm パッケージと同等
* 一方で、マルチアーキビルドを第三者 action なしで組むには、QEMU の登録・ビルダーの用意・タグ生成・push を自前で書く必要があり、**その自前コードの誤りの方が現実的なリスクとして大きい**と判断した

緩和として、これらは commit SHA で固定しています。上流のタグ移動による差し替えは防げますが、**固定した SHA の内容そのものが悪意を持つ場合は防げません。**

**この逸脱は解消できます。** ネイティブの arm64 ランナーとの matrix ビルドに切り替えれば QEMU が不要になり、残る工程は `docker buildx` の直接呼び出しで書けるため、第三者 action をゼロにできます。ビルド時間も短くなります。ベースイメージが安定して GHCR に載った時点で移行する予定です。

なお `.github/workflows/ci.yml` は action を SHA で固定していません。書き込み権限を持たず、特権コンテキストを持たないためです。**権限を足すときは同時に固定すること。**

### 4.7 なぜ履歴の線形化を要求しないのか

`main` へのマージは **merge commit のみ**に限定しています。squash と rebase はリポジトリ設定で無効にしています。

あわせて、ブランチ保護の `Require linear history` は**意図的に有効にしていません**。この設定は履歴の見た目を整えるものとして選ばれがちですが、有効にすると次の連鎖が起きます。

* 線形な履歴とは、`main` 上の全てのコミットが親を 1 つだけ持つこと。マージコミットは親を 2 つ持つため、merge commit 方式が禁止される
* GitHub は最低 1 つのマージ方式を有効にすることを要求するため、squash か rebase が強制される
* GitHub のマージ方式に fast-forward は存在しない。squash も rebase も**新しいコミット SHA を作る**（rebase は fast-forward が可能な場合でも committer 情報を更新するため、SHA は必ず変わる）

**結果として、レビューを通過したコミットが `main` のどこにも存在しなくなります。** ブランチを削除すると、そのコミットへの参照は PR のページに残るだけで、リポジトリからは到達不能になります。

これを避けています。この文書が守ろうとしているのは「git 上のソースとレジストリ上の成果物の対応」（§7.3）であり、その鎖の最初の環が**レビュー対象と `main` の内容の対応**です。SHA が書き換えられると、この環だけが SHA で辿れなくなります。action を commit SHA で固定している判断（§4.6）や、利用者に attestation の commit SHA の照合を求めている点（§5）と、同じ理由に立っています。

**`Require linear history` はセキュリティ統制ではありません。** §3.2 に挙げたゲートのうち `main` のブランチ保護が担っているのは、PR の必須化・コードオーナーによるレビュー・status check の通過・force push と削除の禁止であり、これらは履歴の形とは独立に機能します。線形化を外しても、防いでいるものは変わりません。

引き換えに失うものは、`main` の履歴がマージコミットで分岐すること、および `git bisect` がブランチ内の中間コミットを踏みうることです。中間コミットは CI を通していない状態を含みます。PR 単位の線形な履歴が必要な場面では、設定ではなく読み方で対応します。

```sh
git log --first-parent main
git bisect start --first-parent
```

## 5. 利用者による検証

公開されたパッケージには provenance attestation が付随します。これにより、利用者は**どのリポジトリのどのコミットから、どのワークフローによって生成されたか**を自力で確認できます。

```sh
npm audit signatures
```

attestation に記録されるのは、リポジトリ、コミット SHA、ワークフローのパスです。これらが期待する値と一致することを確認してください。

この検証は、我々が §2 の運用を守っているかどうかを、我々の主張に依存せずに確認する手段です。**§1.1 の 3 番目は、この仕組みによって満たされます。**

## 6. 監視

`.github/workflows/monitor.yml` が、レジストリ上のバージョンとリポジトリの状態を毎日照合します。

検知の対象は、**経路を通らずに公開されたバージョン**です。タグが公開の原因である以上（§4.2）、対応するタグを持たないバージョンがレジストリに存在することは、経路外での公開を意味します。

この照合はタグ名の存在確認に過ぎず、**アーティファクトの内容については何も保証しません**。attestation の検証（§5）の方が強い保証を与えるため、監視の主軸はそちらへ移行します。タグ照合は補助的な位置づけです。

タグ命名の変更（§4.4）に伴い、監視は新旧いずれの形式も受け付ける必要があります。

## 7. 受容した残余リスク

以下は、この設計では防げないものとして受け入れています。

### 7.1 複数の資格情報の同時侵害

タグを push できる人物と、environment の承認者の**双方**が同時に侵害された場合、公開は成立します。単一の資格情報の侵害には耐えますが、共謀または複数侵害には耐えません。

承認者をタグ push 者と分離することでコストを上げていますが、除去はできません。

### 7.2 信頼の起点そのものの侵害

GitHub Actions の OIDC 発行基盤、および npm レジストリの検証側が侵害された場合、経路の全ての前提が崩れます。これらは信頼の起点として扱っており、検証の対象外です（§1.3）。

### 7.3 ソースコード自体への悪意の混入

この設計が守るのは「git 上のソースとレジストリ上の成果物の対応」であり、**ソースコード自体が正しいことは保証しません**。悪意あるコードがレビューを通過してマージされた場合、それは正規の経路で忠実に公開されます。

ここを守るのはコードレビューの責務であり、公開経路の責務ではありません。

### 7.4 初回公開時の例外

レジストリ側で信頼された公開元を登録するには、対象のパッケージが既に存在している必要があります。**未公開のパッケージの最初の 1 版だけは、この経路を使えません。**

初回は移行前の手動公開で行い、登録が完了した時点で以降のすべての版がこの経路に載ります。初回公開時の成果物には provenance が付きません。
